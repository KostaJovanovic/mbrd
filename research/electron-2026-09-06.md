# mbrd as a desktop app — Electron, 2026-09-06

*The plan for shipping the board as an installable desktop application on
Windows, macOS and Linux. Decided in a question-and-answer session on
2026-09-05 and 2026-09-06; every choice below was made by the maintainer, and
the ones the maintainer delegated say so. Nothing here is built. This document
goes to `old/` on the last commit of the work it schedules, on the bargain
`plan-2026-08-14.md` and `apple-motion-2026-08-23.md` took.*

*`apps-2026-09-13.md` §1 overrides several rows of the table below: distribution
and updates (no electron-updater), the release flow (one manual workflow, no
`desktop-v*` tag), the title bar (out of the page), the Windows installer page,
the `.mbrd` association (a checkbox) and the Linux `.deb` (dropped). Read that
table first for those rows. The rest of this document stays the record.*

*It supersedes `future/code-audit-tauri-readiness-2026-07-26.md` as the plan of
record, and that audit stays where it is: it was written for Tauri, its findings
about the app itself were read against the tree for this document (§2), and the
ones that still hold are carried here rather than re-argued.*

## 1. Decisions

| question | decision |
| --- | --- |
| shell | **Electron**, decided. Not Tauri. |
| platforms | Windows, macOS, Linux. iOS and Android are discussed (§9), not planned. |
| purpose | real files on disk; no browser limits; offline and installable; native shell (menu, dock, windows); native ffmpeg and other heavy work off the wasm paths |
| codebase | **one codebase, injected ports.** Same bundle. Browser-only calls move behind interfaces the way `setPrompt()` already works; `main.ts` picks the adapter. No module but `main.ts` reads the bridge global. |
| save model | **document app.** A board *is* a `.mbrd` on disk. Save writes it atomically, Save As prompts, an untitled board prompts on first save. The title bar shows the file and a dirty mark. |
| recovery | **app data, written by the main process.** Crash snapshots and the shelf live under `userData`, not in Chromium's IndexedDB partition. |
| the shelf | **kept, in app data, and it knows about files.** Like After Effects' home screen: a row is a board on disk (path, thumbnail, title, time) or an unsaved board (a packed blob). A row with a path opens the file; the file is the only copy. See §4 *shelf*. |
| cloud (share, sync) | delegated. **Absent on desktop in v1**, the way `config.ts` already makes it absent when unregistered. The loopback design is written down in §7 for when it is wanted. |
| ffmpeg | **bundled static binary**, per platform, run as a child process from main. Works offline. |
| other native work | background removal (u2netp) on native ONNX Runtime; native decode for HEIC and other formats the browser cannot open; STEP/IGES stays on wasm (§6). |
| windows | **one window, one board.** A second file replaces the current board through the shelf, as the web app does. A second launch forwards its file to the running window. |
| menu | **thin native menu over `cmds`.** File / Edit / View / Help, each item dispatching a command name. No second command surface. |
| Windows package | **one `Setup.exe` that asks Install or Portable** on its first page, as Winaero Tweaker does. |
| macOS package | **one universal DMG** for Intel and Apple silicon. |
| Linux package | **one AppImage** that runs on every distribution, plus a **`.deb`** from the same build because an AppImage cannot register a file association and the deb costs nothing to produce. The apt repository, `rpm` and Flatpak are follow-ons (§10). |
| distribution | **GitHub Releases with auto-update** through electron-updater. |
| signing | **none for now.** Unsigned builds for testers; the layout leaves signing a config change. |
| release flow | **a tag triggers CI.** `save.bat` keeps stamping; a tag builds all three OSes and publishes a draft release. |
| repo layout | **same repo, `desktop/` directory.** |
| portable on a read-only medium | **fall back to AppData and say so.** One toast naming where the data went for this run. Nothing refuses to start. |
| macOS architectures | **two DMGs** if a universal build cannot carry both arches' native modules. The download page detects the chip and shows both links. |
| updates | **download quietly, install on quit.** One toast: "v0.281 will install when you quit". Never restarts under a person. Portable and unsigned macOS get "Download v0.281" instead. Off entirely when `!app.isPackaged`, or a dev build at `0.0.0` finds every release newer. |
| existing browser data | **not migrated.** A tester who installs the desktop app finds an empty shelf; the way across is Export in the browser, Open on the desktop. A native app cannot read the browser origin's IndexedDB, and pretending otherwise is a half-feature. |
| logging | main appends to `userData/logs/main.log`, rotated at 1 MB, and the renderer's `console.error` is mirrored into it. No crash reporter: nothing leaves the machine, which is the app's whole promise. Help → Show logs opens the folder. |
| tests | **both.** Port unit tests in `node --test` on every push; a Playwright smoke on release tags. |
| first milestone | **feature-complete v1** — everything above, including bundled ffmpeg, auto-update and three-OS CI. The phases in §8 are the order of work, not a set of releases. |

Two consequences of the Windows choice, agreed up front:

- **Portable has no auto-update.** electron-updater replaces an installed copy.
  A portable copy gets a "new version available" notice that opens the release
  page.
- **Portable has no file association.** Registering `.mbrd` is a registry
  write, which is what portable promises not to do. Double-clicking a `.mbrd`
  opens the installed copy; drag-and-drop and File → Open work in both.

And two of the macOS choice, which nobody chose and both of which are Apple's:

- **An unsigned DMG is refused by Gatekeeper** as "damaged" on first open. The
  download page has to carry the one-line `xattr -d com.apple.quarantine`
  workaround until there is a Developer ID.
- **Auto-update on macOS requires signing.** Squirrel.Mac refuses an unsigned
  update outright, so until then the Mac build behaves like the portable
  Windows one: notice, not update.

`future/code-audit-tauri-readiness-2026-07-26.md` listed five release blockers.
Three of them are closed and the other two are what this plan is.

Two things in that audit are worth carrying as warnings rather than items. The

declined: the reader is hand-written, bounds-checked and tested, and two
implementations of the format is the thing `docs/mbrd-format.md` exists to
prevent.

## 3. What Electron changes about this app, and what it does not

**Nothing about the board.** `state.ts`, the `.mbrd` schema, the renderers, the
input pipeline, the routing, the whole of `canvas/` and `ui/` are untouched. The
bundle is the same `web/assets/app.js`. A desktop build is the same app with a
different answer to seven questions the browser used to answer:

| question | browser today | desktop |
| --- | --- | --- |
| where do the bytes of a file come from | `<input type=file>`, drop, File System Access | native dialog and path, over the bridge |
| where does Save go | IndexedDB | the `.mbrd` on disk, atomically |
| where does recovery go | IndexedDB | `userData/store/`, written by main |
| what happens on close | `pagehide`, unawaitable | `close` is held until the flush resolves |
| how does a link open | `target=_blank` | `shell.openExternal`, http(s) only |
| where does heavy work run | wasm in a worker | a native process, wasm as the fallback |
| how does the app update | the service worker | electron-updater |

Everything else on the list of browser-only behaviour in `main.ts` — the
service worker, `launchQueue`, the not-found and changelog pages, the share
link — is simply not reached on desktop, and §4 says how each is turned off.

**One thing Electron makes harder, found by reading `index.html`.** The page
carries `<base href="/">`, and `mesh/occt.ts` and `errors.ts` hold absolute
`/assets/...` paths. A page loaded from `file://` resolves `/` to the
filesystem root and every asset 404s. So the app is **not loaded from
`file://`**: main registers a custom scheme, `app://mbrd/`, and serves `web/`
from it through `protocol.handle()`. That is Electron's own recommendation, it
gives the page a real origin (so IndexedDB, workers, `blob:` and the CSP all
behave as on the web), and it means `<base>` resolves to `app://mbrd/` and
nothing in `web/` learns it moved. The scheme is registered `standard`,
`secure`, `supportFetchAPI` and `stream`, before `ready`.

**One thing it makes moot.** The whole of `docs/browser-support.md` is about
WebKit. Desktop is one Chromium, pinned by the Electron version, so WebP
encoding, `volume` on iPadOS, `DecompressionStream` floors and the
`color-mix()` fallback are all not desktop questions.

**And one honest limit.** "Generally better performance for big boards" was on
the wish list. Electron does not buy that on its own: the renderer is the same
Chromium the web app already runs in, with the same V8 heap and the same
compositor. What it buys is *headroom* — no tab discard, no storage quota, no
eviction of the recovery store, and heavy work moved off the renderer into
processes that can use every core. The rendering ceilings in `canvas/display.ts`
and `canvas/stills.ts` stay exactly as argued.

## 4. The ports

The shape is the one the codebase already uses five times: a base-layer module
exports a `set*()` and a default that does the web thing, `main.ts` wires the
other implementation once, and nothing below `main.ts` knows which it got.
Unwired, every port is the web behaviour — which is what keeps every module
loadable in `node --test` and is the property `tests/imports.test.js` holds.

A new directory, **`web/assets/js/platform/`**, at the base layer beside
`notify.ts` and `prefs.ts`. `tests/layers.test.js` learns it as BASE: storage
and canvas may import it, it may import nothing above `util`.

```
platform/
  platform.ts    the interfaces, the setters, the web defaults, isDesktop()
  electron.ts    the adapter: takes the bridge object as an argument and
                 returns implementations. Reads no global at import time.
```

`main.ts` gains one block, and it is the only place the bridge global is read:

```ts
const bridge = window.mbrdDesktop;           // exposed by desktop/preload.ts
if (bridge) setPlatform(electronPlatform(bridge));
```

The six ports, each with what it replaces:

### `store` — the surface of `idb.ts`

The cheapest correct answer to "recovery and the shelf in app data" is to notice
that `idb.ts` is already a port. Its whole surface is `get / set / del / keys /
clear` and the three `*Many` forms, over four named stores, holding JSON values
and Blobs. `session.ts`, `library.ts` and `matte-cache.ts` are written against
that and nothing lower.

So `idb.ts` gains a `setStoreBackend()` and the IndexedDB code becomes the
default backend. The desktop backend is a file store owned by main:
`userData/store/<store>/<key>` — JSON for values, raw bytes for Blobs, written
to a temp name and renamed. Over the bridge a Blob travels as an `ArrayBuffer`
and comes back as a Blob, which is what the callers already handle (every
reader in `session.ts` checks `instanceof Blob`).

What this keeps: `session.ts`'s single-flight writer, its asset sweep order,
`library.ts`, the matte cache, and every test on them. What it changes: nothing
in those files. What it costs: the batch forms lose IndexedDB's "all land or
none" — a file backend writes keys one at a time. That is acceptable *because*
of the order `writeSnapshot()` already argues: assets first, snapshot second,
sweep last, so a crash between two keys never leaves a snapshot pointing at
bytes that are not there. The header of `idb.ts` has to say this.

Three things about the file backend that the ordering argument does not
cover, found in review:

- **`clear()` has to be atomic too, and a recursive delete is not.** One
  locked file on Windows and the store is half-wiped, which is the exact
  failure `clearAllData()` was fixed to refuse (§2, PERSIST-03). So `clear()`
  is a `rename` of the store directory to `<store>.trash-<stamp>` — one atomic
  step — followed by a best-effort delete, and main sweeps any `*.trash-*`
  left behind on the next boot. A clear either happened or did not.
- **Keys are file names, and two filesystems in the matrix are
  case-insensitive.** Every key this app writes today is lowercase — content
  hashes are hex, `uid()` is base36 — and the backend holds that as a rule:
  a key with an uppercase character or longer than 200 bytes is rejected with
  a thrown `Error`, not encoded round. Percent-encoding handles the rest.
- **The IPC cost is the delta, not the board.** `writeSnapshot()` writes only
  the assets not already stored (`referenced − known`), so a save moves what
  changed; a restore reads everything in chunks of 32, which is the same bytes
  IndexedDB moves across the same process boundary. `setMany` goes as one
  message and main writes the pairs in parallel. Group E measures a board of
  three hundred photographs on save and on boot before group H, and the
  escape hatch if that is slow — serving assets over a second scheme so the
  renderer streams them — is **declined now** rather than later: it turns
  `getAsset()` from a Blob into a URL across every renderer, which is a
  different project from this one.

### `files` — open, save, save as

Replaces the File System Access branch of `storage.ts` and the hidden
`<input type=file>`. The interface is about a *document*, not a handle:

```ts
interface DocumentRef { name: string; path?: string }     // path is desktop-only
files.pickOpen(): Promise<{ file: File, ref: DocumentRef } | null>
files.pickSave(suggested: string): Promise<DocumentRef | null>
files.write(ref: DocumentRef, blob: Blob): Promise<void>  // atomic on desktop
files.pickImport(): Promise<File[]>                       // pictures, clips, documents
```

`storage.ts` currently holds `fileHandle: FileSystemFileHandle | null`; it holds
a `DocumentRef | null` instead, and the web adapter wraps the handle inside its
own `DocumentRef`. `exportBoard()` becomes the body of Save on desktop:
`pickSave` only when there is no ref or on Save As, then `write`. The
`'Saved in this browser'` receipt and `ensurePersistence()` are web-only and
sit behind `isDesktop()`.

The panel's Save / Export pair reads differently on desktop and the schema is
where that is said: one row, **Save** (`Ctrl+S`), writing the file; **Save
As…**; and **Export** stays for the one thing it still means on desktop — a
copy without the history, which is Share's question and is answered in the
same dialog. This is a `when` on three rows in `ui/settings-schema.ts` and a
label change in `commands/file.ts`, not a new control.

### `recovery` — nothing new

Covered by `store`. `restoreSession()` runs at boot exactly as now, reading the
file-backed `kv` store; an unsaved untitled board is recovered the way an
unsaved browser board is. The one addition is the **document ref** in the
snapshot: a recovered board has to remember which file it was, so `kv` gains
one key, `document`, written beside the snapshot and read back into `storage.ts`
on restore. Not a `.mbrd` schema change: it never leaves the recovery store.

### `shelf` — the library learns about files

The web shelf holds packed `.mbrd` blobs because a browser has no filesystem to
point at. On desktop it does, and the maintainer's reference is After Effects'
home screen: a grid of recent projects, each a file on disk, with the ones that
have moved shown as missing. So a `LibraryEntry` gains one optional field,
`path`, and a row is one of two things:

- **A board on disk.** `path` is set, no blob is stored. Opening the row reads
  the file; Save writes it. The row shows the file name under the title. A file
  that has moved or gone shows the row greyed with "moved or deleted" and a
  Locate action that opens the picker and rewrites the path — the copy is not
  on the shelf, because the file *was* the copy and keeping a second one is
  the two-places problem this design exists to avoid.
- **An unsaved board.** No `path`, packed blob as today. Opening it restores an
  untitled document; the first Save is a Save As, and on success the row turns
  into the first kind and its blob is dropped.

**What shelving means on desktop follows from that.** On the web, opening
another board files the outgoing one silently, and that is right because the
shelf is the only place it can go. On desktop a board with a path and unsaved
changes is asked the close question first — Save, Don't save, Cancel — and
*then* filed as a path row, so the file is always the truth and the shelf never
holds a newer copy than the disk. An untitled board is filed as a blob row with
no question, exactly as now. `openFile()`'s rule that nothing is replaced until
the new board is in hand does not change.

`library.ts` changes by one field and one branch; the grid in `ui/` gains the
subtitle, the greyed state and Locate. On the web `path` is never set and
nothing is different. The thumbnails are unchanged — a data URL in the index,
made by `ui/snapshot.ts` on the way out.

### `lifecycle` — close, quit, open-with

```ts
lifecycle.onCloseRequested(fn: () => Promise<void>)   // main holds the close until fn resolves
lifecycle.onOpenFiles(fn: (files: File[]) => void)    // second instance, macOS open-file, argv
```

`main.ts`'s `flushEdits()` becomes the close handler: `flushNoteEdit()`, then
`await autosave()`, then a **save prompt if the document is dirty** — the one
question a document app has to ask that the web app was proud not to. The
dialog is `ask()`; the three answers are Save, Don't save, Cancel, and Cancel
keeps the window. The web adapter registers the same function on `pagehide`,
where it cannot be awaited, which is the behaviour today.

`onOpenFiles` takes the place of `launchQueue`. Same rule: wait for `started`,
then `openFile()`. Main gets the file from the `second-instance` argv on
Windows and Linux, from `open-file` on macOS, and from `process.argv` on the
first launch; it reads the bytes and sends them over as an `ArrayBuffer` with
the path, so the renderer receives a `File` and a `DocumentRef` and the path
never becomes a string the domain code holds.

### `links` — no port, a policy

Every outbound anchor in the app already goes through `target=_blank` with
`noopener`. Electron intercepts that in main with `setWindowOpenHandler`: allow
`http:` and `https:` through `shell.openExternal`, deny everything else, and
never create a second window. `will-navigate` is denied for anything that is
not `app://mbrd/`. Nothing in `web/` changes.

### `native` — heavy work with a native answer

```ts
native.firstFrame(bytes, name): Promise<Blob | null>         // ffmpeg, else null
native.transcode(bytes, name, opts): Promise<Blob | null>    // ffmpeg, desktop only
native.matte(rgb: Float32Array): Promise<Float32Array | null> // onnxruntime-node, else null
native.decode(bytes, name): Promise<ImageBitmap | null>      // HEIC and friends, else null
```

Every one answers `null` unwired, and every caller already has the wasm or
browser path behind it. `optimize/media.ts`, `canvas/matte.ts` and the image
decode in `import/` each ask the port first and fall through on `null`. §6 has
the per-feature detail.

### `updates` — notice or install

```ts
updates.check(): Promise<{ version: string, canInstall: boolean } | null>
updates.install(): void
```

Replaces the service worker's "new version ready — reload" toast, which is the
one place `main.ts` talks about updates. On desktop the same toast says
"Restart to update" where `canInstall` is true, and "Download vX" opening the
release page where it is not (portable, unsigned macOS). Checked once at boot
and every few hours; never on a timer that interrupts a drag.

### What is switched off

| thing | how |
| --- | --- |
| service worker registration | `if (!isDesktop())` around the block in `main.ts`. `sw.js` and `SHELL` untouched. |
| `launchQueue` | never present under `app://`; the block stays and does nothing. |
| share link (`?s=`), not-found board, changelog page | never reached: the window loads `app://mbrd/index.html` and nothing navigates. `isPatchPage()` and `isNotFoundPage()` answer false. |
| `navigator.storage.persist()` | behind `isDesktop()`; the file store needs no permission. |
| `Clear everything` → `location.reload()` | the desktop adapter asks main to relaunch (`app.relaunch(); app.exit()`), which is what "first run again" means there. |

## 5. Security boundary

Electron's defaults are the boundary, stated so nobody loosens one for
convenience:

- `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`. The
  renderer is a web page. The bridge is a `contextBridge.exposeInMainWorld`
  object of named functions and nothing else — no `ipcRenderer` handed through.
- **Every bridge function is validated again in main.** Paths only come from
  a dialog main itself opened, from `second-instance` / `open-file`, or from
  the store directory. A renderer cannot name a path.
- **The CSP is `web/_headers`, applied by the protocol handler.** Main parses
  the same file `tests/csp.test.js` parses and attaches the header to every
  `app://` response, including the four worker exemptions. One policy, written
  once, enforced on the deploy and on the desktop. The only difference is that
  `connect-src`'s jsdelivr entry is dead on desktop (ffmpeg is native) and is
  left in rather than forked.
- `will-navigate`, `setWindowOpenHandler` and `will-attach-webview` deny by
  default (§4 links).
- The embeds (`frame-src`: YouTube, Spotify) work as on the web; their frames
  run under the same CSP and cannot reach the bridge.
- No remote code. electron-updater fetches installers, not scripts, and
  verifies them against the release's `latest.yml` checksums.

## 6. Native work

### ffmpeg

A static build per platform in `extraResources/ffmpeg/`, spawned from main
with stdin/stdout pipes, one job at a time, killed on a timeout. Licence: the
app is GPL-3, so a GPL ffmpeg build is fine; the notice ships in the About
dialog beside the existing ones. Roughly 80–100 MB per platform, which is the
size cost of the whole decision and is accepted.

What it does on day one is what `optimize/media.ts` does today: a poster frame
for a clip the browser cannot decode (HEVC from a phone). What it makes
*possible*, and the header of `optimize/media.ts` says was dropped on the web
because a single-threaded wasm encoder "pins a core for the length of the clip":
**video optimisation comes back on desktop.** The Optimise row already exists
for pictures and sound; the video branch returns behind `native.transcode`,
offered only when the port answers. That is the first user-visible feature the
desktop has and the web does not.

### Background removal

`canvas/matte.ts` runs u2netp on ONNX Runtime's wasm backend in a worker, and
its protocol is exactly one `Float32Array` in and one out. `onnxruntime-node`
runs the same `.onnx` file in main with DirectML on Windows, CoreML on macOS and
CPU on Linux, which is the difference between a two-second stall and a
two-hundred-millisecond one per cut-out. The model file is already vendored;
the desktop build loads it from `app://` or from resources — same bytes. The
wasm worker stays as the fallback and as the web path.

### Image decode

HEIC is the case: a phone shoots it, no desktop browser opens it, and today the
card is a grey rectangle the same way an HEVC clip was. `sharp` (libvips) in
main decodes HEIC, big TIFFs, and — later — camera RAW to a PNG or RGBA the
renderer turns into a bitmap. Behind `native.decode`, asked before the browser's
own decoder, answering `null` for anything it does not know. RAW is a follow-on:
the formats are many and the fidelity questions (white balance, demosaic) are
their own project.

### STEP and IGES — stays on wasm

The vendored OCCT build is 7.5 MB and works. A native OCCT is a 50 MB+ binary
per platform for a speed-up on a format most boards never see. Declined; the
wasm worker runs unchanged under the same CSP exemption.

### Fonts, PDF, TIFF

Unchanged. pdf.js, the TIFF worker and `FontFace` all run as on the web.

## 7. Cloud on desktop, when it is wanted

Absent in v1, for the reason above: `config.ts` ships empty and the rows are
absent, on the web and on the desktop alike. The design for when it is not:

The implicit-grant popup in `storage/cloud/oauth.ts` cannot run in Electron —
Google refuses OAuth in embedded webviews, and a `BrowserWindow` is one. The
desktop shape is the one the header of `oauth.ts` says it is waiting for: a
**public client with PKCE**. Google's "Desktop app" client type issues one, the
sign-in opens in the **system browser** through `shell.openExternal`, and main
listens once on `http://127.0.0.1:<port>/` for the redirect, exchanges the code
for a token, and hands the token over the bridge. `oauth.ts` gains a port for
"get me a grant" and the provider modules do not change. The redirect URI and
the second client id go in `config.ts` beside the web ones, and `_headers` does
not change because the desktop never fetches accounts.google.com.

## 8. Phases

Feature-complete v1 was chosen as the milestone, so these are the order of
work and each has an exit criterion, not a release each.

### Phase 0 — ports, web only

No Electron yet. The app keeps working in the browser at every commit.

- `platform/platform.ts` with the six ports and web defaults; `isDesktop()`.
- `idb.ts` gains `setStoreBackend()`; IndexedDB becomes the default backend.
- `storage.ts` holds a `DocumentRef` instead of a `FileSystemFileHandle`;
  the web adapter wraps the handle. Save / Save As / Export split in
  `commands/file.ts` and the schema, `when`-gated on `isDesktop()`.
- `main.ts`: the close handler, the open-files handler, the SW guard, the
  bridge check.
- `tests/layers.test.js` learns `platform/` as BASE. `tests/imports.test.js`
  passes without an exemption. New `tests/platform.test.js`: every port
  unwired behaves as the web; a fake backend drives `session.ts` end to end.

Exit: the web app is unchanged to a user; `npm test` green; the CSP test still
reads one file.

### Phase 1 — a window

- `desktop/` with its own `package.json` (see §11), `main.ts`, `preload.ts`,
  `protocol.ts` (the `app://` handler and the `_headers` CSP), `store.ts` (the
  file backend), `tsconfig.json` with Node types.

## 9. Mobile — discussion, no commitment

Electron has no iOS or Android target. Three ways a phone gets mbrd, and one
fact that makes the choice cheap to defer:

**The PWA stays the mobile app.** This is today. Installs from the browser,
runs offline, has `file_handlers` and the share target. Its limits are the
ones `docs/browser-support.md` lists: WebKit's storage eviction, no File System
Access, the `volume` exception, and no store presence.

**Capacitor.** The same `web/` bundle in a WKWebView or Android WebView with a
plugin bridge, which is the same *shape* as Electron: a global exposed to the
page, native plugins behind it. Every port in §4 maps one to one — `store` to
a filesystem plugin, `files` to the document picker, `lifecycle` to
pause/resume, `native` to whatever is worth doing natively on a phone (less
than on a desktop). Needs Xcode and a Mac for iOS, Android Studio for Android,
a $99/year Apple account and a one-off $25 Google one. This is the likely
answer if the question is asked.

**Tauri mobile.** Two shells, one set of ports. The July audit's mobile
sections apply verbatim. Rust toolchain on top of everything Capacitor needs,
for a smaller binary that on a phone does not matter.

The fact: **Phase 0 is the whole of the shared prerequisite.** Every port is a
thing a mobile shell would need in the same shape, so nothing in this plan is
wasted by any of the three, and the decision can wait until desktop has
shipped and there is a reason — a tester with a phone, or a store to be in.

## 10. Linux beyond the AppImage

`apt install mbrd` needs a `.deb` (v1 ships one, for the file association) and
an **apt repository** the user adds once: a static, GPG-signed
directory of `Packages` / `Release` / `InRelease` files, built by `reprepro` or
`aptly` in the release workflow and hosted on GitHub Pages or beside the app on
Cloudflare. The user pastes three lines:

```
curl -fsSL https://apt.example/key.gpg | sudo tee /usr/share/keyrings/mbrd.gpg
echo "deb [signed-by=/usr/share/keyrings/mbrd.gpg] https://apt.example stable main" | sudo tee /etc/apt/sources.list.d/mbrd.list
sudo apt update && sudo apt install mbrd
```

After that `apt upgrade` carries new versions, so electron-updater is off in the
`.deb` build. The same shape gives Fedora an `rpm` repo, and Arch gets an AUR
package somebody writes once. Getting into Ubuntu's own archive is a different
road — Debian packaging review, months, and Electron apps are rarely accepted —
and is not worth walking.

**Flatpak** works too and is the way most Linux desktop users install things
now; it is sandboxed, so the bundled ffmpeg needs its permissions declared and
file access goes through portals, which the dialogs handle. Flathub submission
is a review. After v1.

## 11. Repository shape and the rules it has to keep

```
desktop/
  package.json         the desktop package: electron, electron-builder,
                       electron-updater, sharp, onnxruntime-node
  tsconfig.json        Node types; the root one stays types: []
  main.ts  preload.ts  menu.ts  protocol.ts  store.ts  updates.ts
  native/ffmpeg.ts  native/matte.ts  native/decode.ts
  installer.nsh        the Install / Portable page
  electron-builder.yml
  icons/
  resources/ffmpeg/<platform>/
web/assets/js/platform/
  platform.ts  electron.ts
tests/
  platform.test.js  desktop-menu.test.js
.github/workflows/desktop.yml
```

**Why `desktop/` has its own `package.json`.** The decision was "same repo,
`desktop/` directory, Electron a devDependency", and the first two hold. The
third does not survive contact with electron-builder: electron-updater, sharp
and onnxruntime-node are *runtime* dependencies of the desktop app, and the
root `package.json` says in its own description that it declares none. A second
package under `desktop/` is the standard two-package layout electron-builder
documents, it keeps the root at four devDependencies, and `npm test` at the
root still installs nothing. `npm run desktop` at the root is a one-line
delegation.

**What the rules in `CLAUDE.md` mean for this work:**

- `platform/electron.ts` reads no global at import time; the bridge is an
  argument. No fourth exemption in `tests/imports.test.js`.
- `platform/` is BASE in `tests/layers.test.js` and imports only `util`.
- `desktop/` is outside `tsconfig.json`'s `include` on purpose — it needs Node
  types and the root config closes them for a reason its header gives. It gets
  its own config, and the CI parse leg extends to `desktop/**/*.ts` through
  the desktop workflow's own typecheck.
- The `.mbrd` schema does not change. The recovery store gains a `document`
  key that never enters a file.
- `web/sw.js` and `SHELL` do not change. The worker is not registered on
  desktop; the cache is never populated there.
- No generated catalogue changes.
- `web/_headers` does not change; main reads it.
- `.gitignore`'s "Tauri (M4+)" block is replaced by `desktop/dist/`,
  `desktop/out/`, `desktop/node_modules/`, `desktop/resources/ffmpeg/`.
- The comment at the foot of `main.ts`, "The desktop equivalent lands in M4 via
  Tauri", is corrected on the commit that adds the bridge check.

**What `save.bat` does not do.** It keeps stamping `version.js` and `sw.js`.
It does not build the desktop app, does not stamp `desktop/package.json`, and
does not tag. The release workflow reads the stamp and refuses a tag that does
not match it, which is one stamp rather than three.

### Read against the tree, 2026-09-06

Every **Find** anchor in the task list was checked against `9cf7cc6` and every
one holds. Six things this document was wrong about were found at the same time
and are corrected in the task list, at the group each belongs to; none of them
changes a decision in §1, and they are recorded here only so the reasoning is
not re-derived. **The task list is where the fix is written. This is why.**

- **A sandboxed preload cannot be ESM.** Electron requires CommonJS there, and
  an ESM `main` needs `"type": "module"` or an `.mjs` name. `sandbox: true` (§5)
  is the decision and the build bends to it, not the other way round. → D.
- **An AppImage registers no file association.** Desktop integration is
  something the *user* installs, so Phase 1's "open-with on all three OSes" is
  Windows and macOS, and Linux arrives with the `.deb` in §10. → F.
- **`clear()` was not covered by the ordering argument.** §4 *store* argues the
  lost batch atomicity away with `writeSnapshot()`'s order, which holds for
  `setMany` and says nothing about a recursive delete failing halfway — and
  PERSIST-03 (§2) is closed *precisely* because `clearAllData()` surfaces a
  failed wipe rather than reloading over it. → A.
- **An unpackaged build has no version.** §11 leaves `desktop/package.json` at
  `0.0.0` for the workflow to stamp, which makes every release look newer than a
  dev run. → I.
- **`files.exists()` was missing from §4.** The shelf's missing-file state needs
  it. → A.
- **macOS 15 removed the right-click-to-Open bypass.** The `xattr` line in §1
  still works, but it is no longer the whole workaround, and unsigned is the v1
  shape — which makes that copy load-bearing rather than a footnote. → J.

And two things to **measure rather than assume**, because both have an escape
hatch that costs more the later it is taken:

- **The store's file names are percent-encoded keys.** Asset keys are lowercase
  hex (`crypto.ts`) and safe; NTFS and APFS fold case, so anything that is not
  hex needs lowercasing or hashing, and an encoded name has to stay inside one
  path component.
- **`setMany` becomes N write-and-rename pairs** where IndexedDB had one
  transaction. Time it in group E on a board with a few hundred assets. The
  escape hatch — serving assets over a second scheme so the renderer streams
  them from disk — turns `getAsset()` from a Blob into a URL, and that is a much
  larger change than group A budgets for.
