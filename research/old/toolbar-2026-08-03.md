# The toolbar, and what goes on it

**Carried out.** Planned and built 2026-08-03, all six steps. Filed here rather
than at the top level because the top level is for work that is still open; read
`docs/architecture.md` and `docs/mbrd-format.md` for what the code actually
does, and this for why.

Four things went differently from the plan below, all of them small and all of
them recorded here so the next reader is not misled by a document written before
the work:

1. **The swatch has no picker dialog.** The card *is* the editor - the colour
   well on it is a real `<input type="color">`, which `canvas/input.js` already
   yields a press to. So `addSwatch()` needed no second surface, and the item
   arrives grey rather than at a colour the app chose for somebody.
2. **`simple()` falls through to the lattice.** The plan treated "nothing in the
   way" as a case that could answer on its own; it cannot, because the two cards
   being joined can overlap each other, and the obvious L then runs back through
   the card it started from. The two ends are obstacles to the search as well.
3. **The stub is not always in the output.** `trim()` sheds it when the path
   carries straight on, which is the stub having done its job. The test asserts
   the first *turn* is a stub away, not that the point survives.
4. **`quality.threads` is gone rather than defaulted on**, and the settings row
   with it. A flag that had become a switch for hiding work the user did is not
   a quality trade, and leaving it inert would have been a control that lies.

The original plan follows, unedited.

---

Six steps, planned 2026-08-03.

A board is made by putting things on it, and today there is no surface on
Desktop that says so. Files arrive by drag, by the sidebar, or by a keyboard
shortcut nobody was told about; `#add-bar` — the one honest creation surface in
the app — is phones-only. This adds the Desktop surface, folds the phone bar
into it, and puts on it the two things a moodboard wants that the app cannot do
at all: a colour of your own, and a line from one card to another.

The largest thing in here is not the toolbar. It is that **manual connectors
replace the automatic web**, and the router that draws them around cards rather
than through them is the one genuinely new algorithm.

---

## What was decided, and what was turned down

Recorded because the rejected half is the useful half later.

| decision | why |
| --- | --- |
| Swatch is a plain colour card first | The palette hookup is a second feature wearing the first one's clothes. `paletteFromAccent()` already takes a hex, so nothing about phase 1 forecloses it. |
| Connectors replace the web | An automatic effect nobody could steer becomes a tool. |
| Connectors route around cards | A straight line through three photographs is not a relationship, it is a scratch. |
| Connectors are made by two clicks | Arm the tool, click a card, click another. No drag, so no anchor handles to design. |
| Same pair again removes it | The alternative is making connectors selectable, which means path hit-testing in `input.js` and a selection model holding things that are not items — a great deal of machinery for a delete key. |
| Desktop only | Mobile is a reading feed with no spatial map, the same reason `webVisible()` already refuses it. |
| Frames later | They touch `arrange/arrangements.js`, the Mobile pack and culling at once. |
| No measure tool | Turned down. It was the tool that would have forced the armed-state question; connectors force it anyway, so the mechanism arrives without it. |
| No freehand drawing | A second gesture pipeline and a new asset kind, for an app whose cards are things you brought in. |
| No plain text label | `note` plus its `rich` model already is one. |
| No labels or arrowheads on connectors | Both are the natural next request; neither is v1. Arrowheads imply direction, which suits some boards and clutters others. |

## What constrains all six steps

Not style notes. Each is enforced, and four of them by a test.

- **A new user-facing action is an entry in `cmds`** (`commands.js`), not a
  second event listener. Toolbar buttons carry `data-cmd`. Note that `#add-bar`
  predates this and wires itself through its own `data-add` attributes; folding
  it into the toolbar removes that one-off rather than adding a second.
- **No browser globals at module import time** — `tests/imports.test.js`, three
  modules exempt, a fourth is a regression. Every new module exports an
  `init*()`.
- **The layering graph** — `util`/`geometry` ← `state` ← {`import`, `storage`,
  `canvas`} ← `ui`, enforced by `tests/layers.test.js`. The router is pure and
  belongs at the bottom beside `web-graph.js`; the toolbar is `ui/`.
- **`SHELL` in `web/sw.js`** gains a line for every new JS module or
  `tests/sw.test.js` fails. No apostrophes inside that array, comments included.
- **Do not split `canvas/input.js`.** The armed state is one branch in the
  existing pipeline, not a second pipeline.
- **Every mutation goes through `state.js`** and pushes its own inverse.
  `addItems(items, label)` already commits, so a new item type gets undo free;
  connections need their own `commit(label, redo, undo)`.

### Schema changes

Two, both called out here so the pull request repeats them:

1. **A new item type, `swatch`.** Free-form string in `board-model.js`
   (`type: … : 'generic'`), and `buildContent()` resolves
   `RENDERERS[item.type] || RENDERERS.generic` — so a board with swatches opened
   by an older build shows plain cards rather than breaking. No `classify()`
   branch: that function is only for files arriving from outside.
2. **A top-level `connections` list.** Pairs of item ids. Connections are
   between *items*, and items are shared across both layouts while geometry is
   not, so this is top-level and not inside a layout. `docs/mbrd-format.md`
   needs both.

## Step 1 — the toolbar shell

Nothing new on it yet. Every button drives a command that already exists, which
is what makes this step a test of the surface rather than of the tools.

**Placement, Desktop.** Top-centre, horizontal. Both side edges are spoken for
— `#sidebar` opens left and `#header-panel` right, and both already shift
`#nowplaying` when they do — and the whole bottom edge is bin/history at one
end, the zoom cluster and HUD at the other, and the player between them. The
top edge is the only clear one, and a horizontal bar there is the same component
the phone gets rather than a second one.

**Placement, phone.** The bottom edge is already tiered: the bottom row is
bin / add / history at `--bar-h` (48px, 44px on the narrow tail), and
`#nowplaying` sits one tier above at `bottom: safe-area + --bar-h + --bar-gap`.
The toolbar becomes tier two, expanding upward from a button in the bottom row,
and the player moves to tier three while it is open. The idiom exists — the
player already restates its own `bottom` when either panel opens — so this is
one more rule in the same shape, not a new mechanism.

**One markup constraint.** Those rules use the general sibling combinator, so
the toolbar element must sit **before `#nowplaying`** in `index.html`.

**Idle.** It joins the `:root.is-idle` list in `chrome.css` with the bin, the
corner and the add bar. Worth knowing that this is a creation surface fading on
the same timer as a set of view controls; if it reads wrong in the hand, the fix
is a longer timer for this one element, not an exemption from fading.

**On it at this step:** add files, add note, rearrange, find. All four are
`cmds` entries today.

| file | change |
| --- | --- |
| `index.html` | the bar, before `#nowplaying`; buttons carry `data-cmd` |
| `web/assets/js/ui/toolbar.js` | new — `initToolbar()`, armed state later |
| `web/assets/js/main.js` | one `init*()` call |
| `web/assets/css/chrome.css` | Desktop placement, idle fade |
| `web/assets/css/mobile.css` | the expand button, tier two, the player's shift |
| `web/sw.js` | `SHELL` gains `ui/toolbar.js` |

**Decide while building:** whether the phone's expand button replaces `#add-bar`
outright or sits beside it. Replacing is cleaner and deletes the `data-add`
wiring; beside it is one fewer thing to get wrong on the one surface that is
already good. Recommendation: replace, and keep Files and Note as the first two
entries of the expanded bar so the muscle memory survives.

**Done when:** every button works on both layouts, the bar fades and wakes with
the rest of the chrome, the player never overlaps it at any width, and opening
either panel does not leave it stranded.

## Step 2 — the swatch

The smallest possible new item type, chosen second because it proves the schema
addition end to end while touching nothing that can break.

An item of type `swatch`, carrying `meta.hex`. No asset, so nothing in the ZIP
and nothing in `storage/assets.js`. The card is a colour field with its hex
printed under it. Creation follows `addNote()` exactly — the pattern for an item
born on the board rather than imported — including `select([item.id])`
afterwards, so the thing you just made is the thing that is selected.

It colours nothing. That is the whole of phase 1.

| file | change |
| --- | --- |
| `canvas/renderers.js` | one `RENDERERS.swatch` entry; a `defaultSize` case |
| `import/drop.js` | `addSwatch(centre, hex)` beside `addNote`/`addLink` |
| `commands.js` | `addSwatch` |
| `assets/css/items.css` | the card |
| `docs/mbrd-format.md` | the type and its `meta.hex` |

**Tests:** the `.mbrd` round-trip (a swatch survives serialize → parse), and
that an unknown-type item still falls through to the generic renderer, which is
the forward-compatibility claim being made in the format doc.

**Decide while building:** where the hex comes from. A native `<input
type="color">` is free and awful; the app already does its own OKLCh in
`ui/pigments.js`. Recommendation: native input for phase 1, and revisit when the
swatch starts driving the palette and the picker becomes a real surface.

**Done when:** a swatch can be made, moved, resized, duplicated, deleted,
undone, binned, restored, saved and reopened, on both layouts.

## Step 3 — add link, camera capture

Two small ones, both mostly wiring.

**Add link.** `addLink(centre, url)` already exists in `import/drop.js`, and
`ask({ field })` in `ui/dialog.js` already resolves to a trimmed string or
`null`. The command is the two of them joined, plus whatever URL validation
`linkURL()` already performs. Nothing new is fetched — a link card only becomes
a player per click, and that stays true.

**Camera capture.** `<input type="file" accept="image/*" capture>` into the same
import path a dropped photo takes. Phone only, and absent rather than disabled
where there is no camera — `when`-style absence is what the settings schema
already does with layout-specific rows, and a greyed-out camera button on a
desktop is furniture.

Both go through `import/budget.js` like every other import path: a captured
photo is a file from outside and gets the same byte budget as one that was
dropped.

**Done when:** a pasted URL becomes a card, a photo taken on a phone lands on
the board, and neither path bypasses the import budget.

## Step 4 — the armed state, and connections as data

The interaction and the storage, with straight lines. Splitting the router out
of this step is deliberate: it means the data model, undo, serialization and the
gesture can all be got right and tested while the drawing is trivially correct.

**The armed state.** One flag in `ui/toolbar.js`, read by `canvas/input.js` at
the top of its click path: armed, a click on a card picks an endpoint instead of
selecting. Not a second pipeline, not a second gesture — the existing single-`g`
model is untouched, because picking an endpoint completes on the press and never
becomes a drag.

The state machine is four cases and worth writing down before it is written in
code:

- nothing picked, click a card → pick it, mark it
- one picked, click a different card → commit the connection, clear the pick,
  **stay armed**
- one picked, click the same card → clear the pick
- anything, click empty canvas → clear the pick, stay armed
- Esc → disarm entirely

Staying armed is what makes connecting five things one trip to the toolbar. The
button reflects it with `aria-pressed`, the way `#zoom-lock` and `debugGrips`
already do.

**Ghosts are not connectable.** They are stripped by `serializeBoard()`, so a
connection to one would dangle the moment the board was saved.

**The data.** A list of id pairs on the board, mutated through `state.js` with
`commit(label, redo, undo)` so add and remove are ordinary undoable commands.
The bus gains a `connections` event, or reuses `items` — the second is tempting
and wrong, since every subscriber to `items` would repaint for a change that
moved nothing.

**Dangling is tolerated, not prevented.** A connection whose item is gone is
simply not drawn, and that single decision is what makes delete, undo, trash and
restore work with no bookkeeping at any of them: the item comes back, its
connections come back with it, because they never left. `serializeBoard()`
prunes pairs whose ids are not in the file, so garbage does not accumulate on
disk — and it prunes against the *shed* item list, so ghost-stripping and
connection-pruning agree.

**Drawing.** `canvas/web.js` keeps its entire drawing half — the SVG layer
inside `#world`, the culling margin, the fade state machine, the non-scaling
stroke — and takes a stored list of pairs instead of a computed one. The module
keeps its name; it is still the web, and renaming it would cost the `SHELL`
list, the layers test and three passages of `docs/architecture.md` for nothing.

**What happens to `settings.web`.** It becomes "show connections" and should
default **on**. It defaults off today because an automatic effect that appears
uninvited is an imposition; a line you drew yourself and cannot see is a bug.
The row is `opt-web` in `ui/settings-schema.js`, already `when: desktop`.

**What happens to `quality.threads`.** It existed because computing a maximal
planar set every drag frame is expensive. A dozen stored pairs are not, so the
flag loses its reason and should be retired from the web path rather than left
as a vestigial veto that silently hides work the user did by hand.

**Tests:** the state machine as a pure function (the four cases above), the
round-trip, pruning, and that undo of a delete brings the item's connections
back.

**Done when:** connections can be made, unmade, undone, saved and reopened, and
survive deleting and restoring either endpoint. They are straight lines and look
wrong. That is expected.

## Step 5 — the router

The one genuinely new algorithm, and the one place this feature can go wrong.

**Where it lives.** A pure module at the top level beside `web-graph.js` — no
DOM, no state, no viewport — for the same reason that one is there: the
algorithm is the half that can be tested without a browser, and
`canvas/web.js` is the half that draws.

**The structure.** Not a grid search: world space is infinite and float, so any
fixed cell size either misses real gaps or explodes. The lattice is built from
the obstacles themselves — the x of every nearby card's left and right edge and
the y of every top and bottom edge, each pushed out by a clearance margin. Those
lines' intersections are the only places an orthogonal route ever needs to turn.
A\* across them, cost = distance **plus a penalty per turn**, which is what
produces a path that goes around things in a few deliberate bends rather than a
staircase.

**Obstacles** come from `canvas/spatial.js` — `queryRect()` over the two
endpoints' bounding box plus margin, so a connection between neighbours never
considers the other four hundred cards. Remember the index returns a superset:
every candidate still owes a precise test, and `geometry.js` already has
`segmentMeetsRect()`, which is the same primitive the old crossing test used.
Rotated cards are registered by their circumscribed square, so the precise test
must use `corners()`/`rotatedExtents()` rather than the unrotated footprint.

**Corners follow the whimsy axis.** Rounded elbows at Softish, square at Harsh.
One branch when building the path string, and it is what keeps a connector from
being the one element on the board with an opinion of its own.

**Anchors** are chosen per route: leave from whichever side of the card faces
the target, recomputed as things move. Fixed compass anchors would be a second
thing for the user to manage for no gain.

**When there is no route** — a card boxed in on four sides — fall back to a
straight line rather than dropping the connection. A line you drew must always
be visible, even when it has to cheat.

**Cards are the only obstacles.** Connectors ignoring each other is standard and
making them avoid each other multiplies the cost for something nobody notices.

### The performance rule

The old web could rebuild everything every drag frame because a spanning-tree
edge is cheap. Routing is not, and this is where the feature dies if it is got
wrong.

- **While dragging, do not route.** Straight lines for the duration, route once
  on drop. `items.css` already has a section on what the board stops paying for
  while it is being moved; this joins it.
- **On drop, reroute selectively.** Only connections incident to the moved card,
  plus connections whose corridor the card just entered or left —
  `spatial.js` answers the second one from the card's old and new rectangles.
  Everything else keeps the path it has.
- **Never store a path.** It is a function of where the cards are now, exactly
  as the web was derived rather than saved. Nothing to invalidate, nothing to go
  stale.

**Tests** — the properties, not the pixels: a route never enters an obstacle
rectangle, a route is orthogonal, a route terminates, a boxed-in pair falls back
to a straight line, and the turn penalty actually reduces bend count on a case
built to have two equal-length options. Note the caution `web-graph.js` earned
the hard way: **assert the arithmetic, never a duration.** Its governor's test
was flaky exactly once, for exactly that reason.

**Done when:** connectors go around cards, hold up on a board of several hundred
items, and a drag stays at frame rate.

## Step 6 — connect for me

`web-graph.js` does not get deleted. Its minimum spanning tree becomes a
generator: run it over the selection (or the whole board), and it emits real,
stored, editable connections that then go through the router like any drawn by
hand.

Three things this buys:

- Several hundred lines of tested, proven non-crossing geometry keep earning
  their keep.
- Any board that had the web switched on gets it back as real connections in one
  press, instead of silently losing it in step 4.
- The no-crossing guarantee stops being a law the app imposes and becomes what
  the generator happens to produce — which is the right relationship between an
  algorithm and a user's board.

The governor is the open question. Its whole job was deciding how large a board
is worth attempting inside a frame, and a generator that runs once on demand has
no frame to stay inside. It can go, or it can stay as a guard against somebody
selecting nine hundred cards. Recommendation: keep it, lower its urgency, and
say in the toast how many connections were made.

**Done when:** a selection can be connected in one press, the result is
indistinguishable from hand-drawn connections, and an old web-enabled board can
be converted without touching anything else.

## Risks, honestly

1. **The router is the whole risk.** Steps 1–3 ship something useful on their
   own and steps 4–6 are where every hard thing lives. If the router does not
   hold up, step 4's straight lines are still a shippable feature and the plan
   degrades rather than fails.
2. **The armed state is a mode, and mbrd has never had one.** Every other
   gesture in the app is unmodal. The Esc route out, the `aria-pressed`
   reflection and staying armed after a pair are all there to keep "why is
   clicking not selecting?" from ever being a question. Worth watching in real
   use rather than trusting the design.
3. **Retiring `quality.threads` from the web path** takes a lever away from slow
   devices. Justified only because manual connections are bounded by what a
   person drew; if generated connections make that untrue, the lever comes back
   for the generator rather than for the drawing.
4. **The idle fade on a creation surface** is an assumption. It is the
   consistent choice and it may still feel wrong.
5. **`docs/architecture.md` will be wrong** from step 4 until it is rewritten.
   Its web section describes the MST as the thing that draws the board's
   threads, and that stops being true. Same commit, not a follow-up.
