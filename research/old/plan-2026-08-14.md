*Written 2026-08-14. Covers **U1–U5, L2, L3, L4, S1–S9 and V1** from
`open-work-2026-08-14.md`. **L1** (share by link) and **B1** (what `old/` should
look like) are deliberately not in it and stay open in the register.*

**Why this file is allowed to exist next to the register.** `README.md` says a
second open document at this level is the thing to argue about rather than to add
quietly, so: the register says *what each item is and why it matters*, and this
says *in what order, with what, and how you know it worked*. **It contains no
description of any item** — only ids — which is the property that stops the two
drifting. If you find yourself explaining here what an item is, it belongs in the
register instead. This file dies when the work does and goes to `old/` on the
last commit of it; the register outlives it.

## The three things that decide the order

Everything below falls out of these, and they are the reason the order is not
simply "smallest first".

**1. S8 must land before U5.** U5 wants to sample the border pixels of an image
to guess whether it is a cut-out, and the honest place to do that is the decode
the import path already performs. S8 is the item that reduces how many times an
import decodes. Doing U5 first means adding a sampling pass to a path that is
about to be rebuilt, and doing S8 first means U5 borrows a decode that is already
there. Same work, half the code, one order.

**2. L4 must land before L3, and must ship report-only.** Both turn on the word
*unreferenced*. Today `packBoard` writes only hashes an item still points at, and
it already counts **binned** items as referenced (`storage/mbrd.ts:122`) — so the
codebase already has two classes of reference and knows why. L3 adds a third:
a stored version can be the only thing pointing at an asset. If L4 ships first
with a *remove unused* button and L3 arrives later, that button becomes a
data-loss bug in files people keep. So L4 reports orphans and does not offer to
delete them, and the delete action is part of L3's batch, after the definition is
whole.

**3. S1 is the highest-risk item on the list and wants to be alone.** It is the
only one that can change what every board looks like for everybody. It also has
no dependency on anything else here, which means it can go anywhere — so it goes
where a regression is cheapest to notice, which is after the small visible fixes
are in and before the long tail of tidying that would otherwise be blamed for it.

## The batches

Each batch is one commit unless it says otherwise. Every batch ends with the
same five: `npm test`, `npm run lint`, `npm run typecheck`, `npm run build`, and
**an entry in `patch-notes.md`** — the changelog is the one at the repository
root now, its version spans have to stay contiguous, and the high end of the
newest span must equal `VERSION`. `save.bat` does the stamping and regenerates
`/patch`; it will fail the commit if the build fails, which is the point of it.

### Batch 1 — U1, the Join defect

Alone, because half of it is a data fix and that deserves its own line in the
history.

- The guard goes in `connectStep()` (`ui/toolbar.ts`), not at the call site —
  it is four pure lines with a unit test already reachable, and the selection
  path's `joinable()` is the behaviour to match.
- A tap on something that cannot be joined **must not consume the standing
  pick**, and must still return `true` so the press does not fall through into
  selection. One toast, in the voice of the connect toasts already there.
- The load-time cleanup drops pairs naming a non-join-end. Put it where the
  board is validated on the way in rather than in the renderer, so a board is
  clean in memory and not merely clean on screen.
- **This is a `.mbrd` behaviour change and gets called out as one.** Nothing in
  the format changes; what changes is that a class of already-invalid data is
  now discarded on load rather than carried.

*New tests:* `connectStep` rejects a sticker end and keeps the pick; the load
path drops an invalid pair and keeps valid ones.
*By eye:* arm Join, tap a sticker, confirm the toast and that the pick survives;
then tap two real cards and confirm the line still draws.

### Batch 2 — U2, U3, U4, the three small interface faults

All in `ui/`, all small, all needing the same by-eye pass.

- **U2** adds a `bounds` option through `openAnchored()` into the anchor branch
  of `render()` in `ui/menu.ts`, and the clamp intersects it with the window so a
  bar wider than the viewport still cannot push a panel off-screen. Degrade to
  "align to the container's left edge" when the container is narrower than the
  panel rather than inverting the clamp. The phone's More button passes no bounds
  and must be unaffected.
- **U3** guards the remembered-shelf scroll in `ui/sticker-window.ts` rather than
  zeroing it. **Check the real number in a browser first** — the register records
  that the stylesheet values do not reproduce the reported 10.4px, so one of the
  two is wrong and it is worth knowing which before writing the guard.
- **U4** is one expression in `ui/menu.ts`. Drop the accelerator from Zoom when
  the item is viewable; Open already conditions its own on `editable`.

*By eye:* hover all three toolbar flyouts, including the rightmost, at a narrow
window and a wide one; open the sticker pad with no favourites and again with
one; right-click a photo and a note and read the accelerator column.

### Batch 3 — S8 then U5, the import path and cut-outs

Two commits, in this order, for the reason in §1 above.

**3a — S8.** Collapse the repeated decodes in `import/`: measuring, thumbnailing
and video-poster measuring should share one decode. Stop `addFile` reading a
File into an ArrayBuffer and copying it into a new Blob when what arrived was
already storable — hash from the Blob.

**3b — U5.** The flag first, the guess second, so the feature is complete and
manual before anything tries to be clever:

- One meta key through `patchMeta` with a validator, copying `setItemFit` in
  `state.ts` exactly — including its type guard, since this applies to images
  and not to notes.
- The class goes on in `canvas/item-dom.ts` beside `writeAdjust`; the paint comes
  off in `item-chrome.css`, where the hairline is an inset `box-shadow` on
  `--item-border`.
- **Keep the box, drop only the paint** — hit-testing, marquee, selection ring
  and resize grips all measure that rectangle.
- The menu row goes with the other per-item writes in `commands/item-meta.ts`.
- **`ui/snapshot.ts` has to agree.** It paints its own card rectangle and hangs
  its own shadow (`shadowOn`, around `:231`), and already draws stickers by a
  different path. A chromeless image joins that exemption or a printed PDF grows
  a border the screen has not got — and nobody would notice until they printed.
- The guess reads the border ring of the decode from 3a. **Header alpha is not
  the test** and the register says why: opaque PNG-32 screenshots are common and
  would lose their cards. The guess is a default; the menu row always wins and is
  what gets saved.

*Decision needed before 3b lands:* at Softish a card can tilt and carry tape.
A cut-out should still lean; tape over nothing is tape floating in the air. The
register leaves this open on purpose and it is a taste call.

*New tests:* the validator rejects rubbish; the border-sampling helper is pure
and gets fed a synthetic opaque-alpha bitmap and a synthetic cut-out.
*By eye:* a cut-out PNG and an ordinary screenshot dropped side by side, at all
three whimsy stops, then exported to PDF and looked at.

### Batch 4 — S2, S3, S7, the cheap ones

Independent of everything, small, and a good batch to have banked before S1.

- **S2** — `selectionHasStackOverlap()` in `stacking.ts` is O(n²) and runs while
  the context menu is being built. The cheap fix is a sweep or a grid bucket; the
  cheaper one is to stop asking the exact question when the answer only decides
  whether to show a row.
- **S3** — the arrange packers. Already capped and acknowledged; the deliverable
  may honestly be a comment rather than a change, and if so, say that in the
  commit rather than leaving it looking undone.
- **S7** — fold the three near-identical geometry write loops in `layout.ts`
  (`:802`, `:904`, `:1213`) into one helper.

*New tests:* S7 is behaviour-preserving and the existing layout tests are the
check; add one that the three entry points still emit what they emitted.

### Batch 5 — S1, the theming split

**Alone, and the one to be careful with.** Probably three commits.

- **5a — the equality.** Replace the `JSON.stringify(clone(a)) === …` in
  `sameLook` with a real comparison over the known keys. This is the smallest
  change and the one with a real bug behind it, so it goes first and separately.
- **5b — one home for the token question.** `AXIS_TOKENS`, `PALETTE_TOKENS` and
  the look tokens are three answers to *what is a themeable token*. One module
  owns the vocabulary; the others import it.
- **5c — the split.** Lift extraction, the fade loop and control-building out of
  `ui/appearance.ts`, in that order — each is the least entangled thing left at
  the moment it moves. Whatever comes out must not import `state.ts` back if it
  lands below the line; `tests/layers.test.js` is the arbiter and its `DEBT` map
  may only shrink.

*By eye, and this is not optional:* **all three whimsy stops**, a saved board
reopened, a palette extracted from an image, and the Look tab driven end to end.
The visual audit's rule applies exactly here — a change looked at only on a
default board has not been looked at.

### Batch 6 — S5, S4, S6, the structure

In that order, because the first creates most of the second's opportunities.

- **S5** — move the substantial features out of `main.ts` (title editing, the
  zoom readout, the save cooldown, the clear countdown) into modules of their
  own. `main.ts` should read as boot and wiring.
- **S4** — the inversions that surface once those move. `tests/layers.test.js`
  decides what counts; anything that has to stay gets an entry and a reason, not
  a shrug.
- **S6** — the narrow half only. `window.mbrd` stays: it is a deliberate console
  handle and `CLAUDE.md` says so. What is worth changing is the ambient ability
  of any importer to mutate `board` outside the commit path. **Decide the
  ambition before starting** — a full accessor seam is a large change and may not
  be worth it; a documented boundary plus the typed bus may be the whole of the
  win, and if so, say that and close the item.

### Batch 7 — V1 and S9, the annotation pass

Low risk, high reading. Both are *decide and write down* rather than *change*.

- **V1** — sort the 27 bare-pixel `font-size` values into on-scale, deliberately
  off-scale, and never-looked. Fix the third pile; **comment the second, because
  for that pile the comment is the deliverable**. `ghosts.css:145` is the pattern.
  Count px, not every non-`var()` value — the register records that miscount and
  why it matters.
- **S9** — the long functions, taken only where Batch 6 has already been through
  the file. A function extracted for its own sake and not for a caller is churn.

*By eye:* all three whimsy stops again, since this is the axis that exposes it.

### Batch 8 — L4, the inventory sheet, report-only

- A sheet, not a settings section — `ui/credits.ts` is the precedent, and
  `ui/settings-schema.ts` is for things that change the app rather than describe
  it.
- Sizes come from `storage/assets.ts`, which already carries `size` per asset and
  a totals helper. **Nothing in this panel may decode an image** — the boards
  where the question gets asked are exactly the boards a decoding panel would
  stall.
- Hand off to `optimize/`. The reason to build this at all is that the optimizer
  is a button nobody has a reason to press; *this photograph is 12 MB* is that
  reason.
- **Report orphans. Do not offer to delete them.** See §2.

### Batch 9 — L3, the durable timeline

The largest, and the only one that changes what a `.mbrd` is.

- Versions are extra ZIP entries — additive, and they do not duplicate a single
  photograph, because assets are stored by hash and `board.json` is small.
- **The pruning is the whole of the work.** `packBoard` writes only referenced
  hashes and already counts binned items as referenced; stored versions become a
  third class, and every place that computes references has to learn about them
  at the same time — including L4's orphan report from Batch 8, which becomes
  wrong the moment this lands if it is not updated in the same commit.
- **Decide the old-build question deliberately**, do not let it happen: an older
  build opening a newer file will drop the entries it does not know about on the
  next write. Either the history is documented as losable that way, or the format
  version moves so an old build declines the file. Both are defensible; silence
  is not.
- Cadence: a shallow automatic ring that evicts, plus named marks that never do.
- **Restoring is one undoable command**, through `history.ts` — landing on the
  wrong version has to itself be undoable.
- `research/docs/mbrd-format.md` is edited in the same commit. It is a
  specification, so it moves with the format and not after it.
- **Then** L4 grows its delete action, safely.

### Batch 10 — L2, the style tile

Last because it is the only item that is blocked on taste rather than on code.

**Three decisions are needed before a line is written**, and the register leaves
all three open on purpose: whose colours (all images / selection / the tour),
which images and how many, and whether the tile follows the whimsy dial. The
third is the interesting one — `/patch` follows it and that is the house style,
but a deliverable sent to a client arguably should not change next week.

Once decided, it is a layout and not a renderer: `ui/snapshot.ts` already owns
the projection, the text drawing and the PDF container, and the command is an
entry in `commands/file.ts` beside `exportImage` and `exportPdf`. **It has to be
painted, box by box** — a DOM layout rasterised through `foreignObject` taints
the canvas, which is the whole reason this app composites in Canvas 2D.

## What this plan does not solve

**There is no browser suite, and eight of these need eyes.** `npm test` is the
whole automated bar and it is headless. U2, U3, U5, S1 and V1 cannot be verified
by it in the way that matters, and S1 is the one where that hurts — the by-eye
list in Batch 5 is the actual test for it, and skipping it means shipping a
change to what every board looks like on the strength of a green suite that never
rendered anything.

**The register has to be maintained as this runs.** An item closed and not struck
is the exact failure that produced the register in the first place: five status
blocks, three of them wrong, none of them wrong through carelessness. Close items
in the register in the commit that closes them, not in a sweep at the end.

**Batches 8, 9 and 10 are the ones most likely to be re-scoped**, because all
three came out of a discussion rather than a document and their entries in the
register are the whole of the thinking so far. The register says as much about
itself. **Writing a proper document for L2, L3 or L4 is the first half of doing
it**, not a detour — and when one exists, the register's source column should
point at it and this plan's batch should be rewritten from it.
