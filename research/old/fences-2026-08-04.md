# Fences — regions that hold the cards inside them

**Amended the same day: Decision 3 is superseded.** The rubber band now offers to
make the fence, which is Fences' own gesture and was the thing Decision 3 traded
away. The trade turned out to have been priced wrong, and the reason is worth
keeping because it is a general one.

Decision 3 rejected "drag out a rectangle" because it meant a second armed mode
beside the connector and a *new drag kind* inside `canvas/input.js` — the file
with exactly one active gesture that must not be split. That reasoning was sound
about a new gesture and wrong about this one, because **the gesture already
exists**. A marquee is a rectangle dragged over some cards, which is the whole of
what the draw tool wanted; it selects them, which is more than the draw tool
offered; and it ends in one place. So nothing was armed and no drag kind was
added. `input.js` gained a five-line read at the end of `endPointer` and one pure
predicate, `drewRectangle()`, which separates a rectangle somebody drew from a
shift-click that started a zero-size band on the press.

What that leaves:

- `ui/fence-prompt.js` is the offer — a button beside the cursor, withdrawn when
  the pointer strays ~2.5cm from its edges. The withdrawal is the point, not
  ornament: the gesture has already been made, so an offer nobody accepted has to
  cost nothing, and walking away *is* declining. A modal would need dismissing
  and a toolbar button would sit there being ignored.
- **Empty fences arrive early.** They were v2's, and they came free: a band that
  caught nothing has a rectangle, which is the only thing an empty fence needs.
  So the lay-out-first workflow Decision 3 gave up is back, and the draw-a-
  rectangle tool is off the v2 list — not deferred, unnecessary.
- `cmds.fenceSelection` stays on the group menu at two-or-more. A selection built
  by shift-clicking has no band to catch the answer, and the band has no
  two-or-more rule, because a rectangle round one photograph is still a region
  somebody drew.
- `fenceBox()` in `fences.js` is new and is the one piece of arithmetic that had
  to be got right: the marquee catches anything it *overlaps*, so a card can poke
  out of the band that selected it, and a fence cut to the band would open not
  containing its own contents. The union takes the drawn rectangle exactly as
  drawn and the items with a step of margin.

**Carried out, 2026-08-04.** v1 shipped as described below with three
deviations, recorded here because each was decided while building and none is
visible from the code:

1. **There is no `canvas/fence.js`.** It was priced at 180 lines for a label bar
   and a roll-up toggle; the label turned out to be the ordinary `.item-bar`
   every card already carries, moved to the top edge by CSS, and roll-up is v2.
   That left a module holding one empty `<div>`, so the renderer went into
   `canvas/renderers.js` where the file's own comment says a type belongs.
2. **A board with fences is repacked whole on every `completeLayout()`**, not
   appended to. A fence drawn on Desktop otherwise arrives on Mobile as a lone
   band with its members still scattered up the column. The cost is real and is
   stated in the code and in `docs/architecture.md`: on a fenced board, Mobile
   positions arranged by hand do not survive a mode switch. A board with no
   fences is untouched.
3. **`refenceArrivals()` was not foreseen.** Removing a fence heals itself, but a
   fence *arriving* does not — the cards underneath hold a remembered `null`,
   which is a real answer rather than a gap, so an undone delete put the fence
   back around contents that still believed they were loose. Three doors needed
   it (add, undo-delete, restore-from-bin) and they share one function. The test
   that caught it is "undoing the delete brings the grouping back with nothing
   recorded".

One thing this work found and did not cause, recorded because it will look like a
fence bug the next time it fires. The e2e case "a note is written on the note"
typed into the second composer without waiting for it to open, so focus was still
on the toolbar button that had just been clicked — and **a space on a focused
button is a click**, so the two spaces in "not this one" pressed *Add note* twice
more and the board grew two notes nobody asked for. It failed about half the
time, and only in a full run, because it was a race against an animation frame
and the machine had to be busy to lose it. The fix is the wait the *first* note in
that same test already had. Nothing in the app changed; the fence work only made
the frame in question slightly busier.

The suspicion this document raised about `sticky.js` was also real: `restick()`
is called from `commitGeom()`, which undo does not go through, so undoing a note
dragged from one photo to another left it lying on the first and remembered as
stuck to the second. Fixed in `layout.js` by moving the call inside the committed
pair, which fences then inherited rather than reproduced.

Everything below is the plan as it stood before any of that.

A **fence** is a labelled rectangle drawn on the board. The cards inside it
belong to it: drag the fence and they come along, name the fence and you have
named that part of the board. It is the idea Stardock's Fences puts on a Windows
desktop, and it is the answer to the thing an infinite canvas is worst at — a
board that has grown past the point where "over there, near the blue one" is a
usable address.

This document is the reasoning, and it is settled. The four decisions that were
open when it was drafted have been made and are marked **decided** below; where
the recommendation was overruled, the argument that lost is kept, because knowing
what was traded away is the point of this directory.

---

## What a fence is, precisely

| | |
| --- | --- |
| a fence *is* | a rectangle, a name, and a look |
| a fence *has* | whatever cards are inside it, right now |
| a fence *does* | carry those cards when it moves, and give them one label |
| a fence is **not** | a folder, a container that owns its contents, or a second board |

The distinction in that last row is the whole design. A folder holds things —
take a thing out and you have changed the folder. A fence *covers* things: it
holds whatever happens to be under it, and the way to take something out is to
drag it out. There is no add, no remove, no membership list, and nothing that can
disagree with the picture on screen.

That is not a novel idea in this codebase. It is exactly what `sticky.js` already
does for notes, in as many words:

> stuckness is a fact about where two things are, and a file that also recorded
> it could disagree with its own geometry — a hazard with no upside, since the
> geometry is right there and the answer falls out of it.

A fence is that sentence with a different predicate. Most of the plan below is
the consequences of taking it seriously.

---

## Decision 1 — a fence is an item

Two ways to store one, and the format decides it.

**Rejected: a top-level list**, `board.fences: [{ id, name, rect }]`, filed
beside `connections`. It reads cleaner — a fence is not content, so why is it in
`items`? — and it is wrong for one concrete reason, which `docs/mbrd-format.md`
already states about `connections`:

> An older reader … does **not** write it back, because `board.json` is rebuilt
> field by field rather than carried through. So a board saved by a build that
> predates this loses its connections. That is the one place the format's
> forward-compatibility promise does not reach, and **it is worth knowing before
> adding another top-level key.**

That paragraph was written as a warning to whoever came next. This is whoever
came next. A board with fences, opened and saved by any build older than the one
that adds them, would come back with the fences gone — silently, and with the
cards left where the fence used to hold them.

**Chosen: `type: "fence"` in `board.items`.** The same document says what happens
then:

> An unknown `type` — a reader that does not recognise one shows the item as a
> plain named card rather than dropping it, and writes it back out untouched.

So an old build shows a fence as a large empty named card, in the right place, at
the right size, and hands it back intact. That is a graceful degradation of a new
feature rather than the destruction of somebody's work, and it is the same
extension point `swatch` was added through.

Everything else follows from the choice, and it is a lot of free machinery:

| a fence gets, for nothing | because |
| --- | --- |
| independent Desktop and Mobile geometry | `board.layouts` is keyed by item id |
| a name you can edit in place | `editItemName()` in `canvas/items.js` |
| selection, delete, undo, bin, restore | `state.js` treats it as an item |
| z-order, resize grips, the context menu | ditto |
| culling | `canvas/spatial.js` indexes any box |
| save and load | `storage/mbrd.js` writes items generically |

The cost is the mirror image: a fence is a card, and every place that means
"something the user put on the board as content" now has one more thing to
exclude. That list is enumerated under **What has to change**, and it is a real
part of the work.

## Decision 2 — membership is derived, memoised, and seeded

**A card is in a fence when its centre is inside the fence's rectangle.**

Centre, not overlap fraction, and the difference matters. `sticky.js` measures a
note by area because a sticky pressed onto the *corner* of a photograph is
obviously stuck to it. A fence is the opposite case: it is a region, regions have
edges, and a card straddling the edge has to be in exactly one of the two sides.
The centre answers that with no threshold to tune and no card ever in two fences
at once.

Where fences nest, the **smallest** containing fence wins. A fence inside a fence
is then a sub-region, which is the only thing it could sensibly be, and the
containment chain terminates because each step is strictly smaller.

### Measured on Desktop geometry, always

This is the rule that is easy to miss and fatal to get wrong, and it falls out of
the Mobile decision below.

On Mobile a fence is a full-width band with its members packed *underneath* it,
so a card is never geometrically inside its fence there. Measuring membership in
the active layout would therefore dissolve every fence on the board the moment
somebody switched to Mobile — and then stamp that dissolution into the file on
the next save.

So: **membership is measured in Desktop geometry and only in Desktop geometry.**
On Mobile it is read from the memo, never measured. A card is in a fence because
of where it sits on the Desktop board; the phone renders that fact, it does not
compute it.

The consequence to state plainly rather than let somebody discover: **you cannot
change what a card belongs to from a phone.** Dragging a card around the Mobile
column reorders it and does not re-fence it. Whether a Mobile drag *into a run*
should re-fence is a genuine follow-up question and is left open at the bottom.

### Memoised, on exactly `sticky.js`'s terms

Measured once, then remembered until the card itself is handled. This is not an
optimisation; it is the behaviour. Without it, dragging a fence across the board
would hoover up every loose card it passed over, and a card dropped near a fence
would join it a frame later when something else moved. `sticky.js` names the rule
— "only picking up the note itself asks the question again" — and
`commitGeom(label, before, driven)` already implements it: the `driven` ids are
what the gesture actually had hold of, and only those are re-measured.

### One place the rule differs, deliberately

`sticky.js` says resizing a host cannot re-parent the notes on it. **A fence must
re-measure on resize.** The two are not inconsistent: a photograph's edges are
incidental to what is lying on it, and a fence's edges *are* the fence. Dragging
a fence's corner out over three more cards is the gesture that means "and these
too"; there is no other one, and requiring the user to then touch each card would
make the boundary decorative.

So: **moving a fence does not re-measure; resizing one does.** Both halves are
testable and both should be tested, because each is surprising if you only know
the other.

### Seeded from the file

`meta.fence` on the *member*, holding the fence's id or `null` — the same shape
and the same job as `meta.stuckTo`, stamped from live geometry at serialize time
and read back by a `seedFences()` beside `seedSticks()`.

It exists for the same narrow reason: a pixel of drift across save and reload
must not lose a grouping somebody plainly made. With membership measured on
Desktop only, it carries a second load: it is **the** source of truth for a board
opened straight into Mobile, where there is nothing to measure until the user
switches. A dangling id — a fence that was deleted — falls back to measuring, and
an older board with no key measures, which is correct in both cases.

Storing it on the member rather than as a list on the fence is what keeps the
format honest: one additive `meta` key, carried through untouched by older
readers, with no second place for it to disagree with the geometry.

## Decision 3 — you make one by fencing a selection *(decided, then superseded — see the head of this file)*

**v1 has exactly one way to make a fence: select some cards and run
`cmds.fenceSelection()`.** A rectangle appears around them with a margin, and the
name field opens immediately — the same beat `composeNote()` uses, and for the
same reason: an unnamed fence is a box, and the name is the entire point of
drawing one.

This was chosen over the Fences-native gesture (arm a tool, drag out a rectangle)
on cost. The draw gesture means a second armed mode beside the connector and a
new drag kind inside `canvas/input.js` — a file with exactly one active gesture
that must not be split, and the highest-risk file in the repository to add a
branch to. `fenceSelection` is one entry in `cmds` and touches `input.js` not at
all.

What that trade gives up, said plainly: **you cannot make an empty fence in v1.**
There is no "lay out the regions first, fill them in later" workflow. You group
what you already have. The draw tool is what unlocks the other order, and it is
v2.

Specifics worth fixing now:

- **Padding** around the selection's bounds: one grid step. Enough that the cards
  are not touching the border, and it is a number the board already has.
- **The fence takes a z below every member.** It is drawn behind them, and
  `bottomZ()` of the selection minus one is the value. Getting this wrong paints
  a fence over its own contents.
- **A selection containing a fence nests**, with no special case — smallest
  containing fence wins, so the new one becomes the parent.
- **The surface is the context menu, not the toolbar.** `fenceSelection` is dead
  without a selection, and a toolbar button that is disabled most of the time is
  a worse toolbar. `ui/menu.js` is a list of `{ label, action, hidden }` entries
  and already hides on `!many`; this is one more line there, plus a keyboard
  accelerator. The toolbar is not touched.

## Decision 4 — Mobile gets bands and runs *(decided, against the recommendation)*

The draft recommended making fences Desktop-only furniture, on the grounds that
Mobile is a column and a column has no regions in it. That was overruled, and the
argument against it is good: a grouping that is invisible on a phone is a
grouping that half your board's readers never see.

So: **a fence becomes a full-width band in the Mobile column, and its members are
packed as a contiguous run beneath it.**

```
DESKTOP                          MOBILE
┌─ kitchen ────────┐             ┌────────────────┐
│   ▢      ▢       │             │ ▬ kitchen ▬▬▬▬ │  ← band: full width, one row
│        ▢         │             ├───────┬────────┤
└──────────────────┘             │   ▢   │   ▢    │  ← the run, packed as usual
                                 ├───────┴────────┤
┌─ bath ─────┐                   │       ▢        │
│   ▢        │                   ├────────────────┤
└────────────┘                   │ ▬ bath ▬▬▬▬▬▬▬ │
                                 ├────────────────┤
     ▢     ▢    ← loose          │       ▢        │
                                 ├────────────────┤
                                 │   ▢   │   ▢    │  ← loose, at the bottom
                                 └────────────────┘
```

This is the honest translation. `layouts.mobile.arrangement` **names an order,
not a shape** — the format document is explicit — and a fence is, on a phone,
exactly an order: keep these together, under this heading.

### How the pack changes

`packMobileGrid()` is a row-major first-fit that computes its starting row once,
from the obstacles, and then places every item into the first open span it finds.
Two changes, and neither is deep:

1. **A band is a barrier.** The whole value of a run is contiguity, and a naive
   first-fit destroys it: a small card from the second run would happily drop into
   a gap left in the first. So the frontier resets at each band — nothing after a
   band may claim a row above it. Concretely, `packMobileGrid` takes an explicit
   `startRow` instead of only deriving one, and the run packer calls it once per
   run with the previous run's floor.

2. **A band is a forced span.** The fence is a real item in the pack with
   `cols = columns` and `rows = 1`, so it gets genuine Mobile geometry that saves,
   loads, culls and scrolls like anything else. `fitMobile()` needs one special
   case: a fence is not scaled to the column, it *is* the column.

### The order of the runs

A run's position is decided by **its first member in the arrangement's order.**
Under `date`, the fence holding the oldest card comes first; under `shuffle`, the
runs shuffle. This keeps `arrangement` meaning precisely what it means today and
adds no user-facing setting — the sort key is derived from an order that already
exists.

**Loose cards go last**, after every run. The fenced regions are the structure
somebody made; the unfenced remainder is the inbox, and an inbox belongs at the
bottom. This is a taste call rather than a forced one, and it is the one part of
the Mobile design that is cheap to reverse.

### The cases that need an answer before it is written

- **Riders.** `layout.js:228` and `:440` already split `isRider` notes out of the
  pack so they can ride their hosts. A rider must not also claim a slot in its
  host's run — it rides, and its host is already in the right place. One filter,
  at a line that already filters.
- **Nested fences** recurse: a band inside a run, with the same barrier rule one
  level down. It falls out of the run packer rather than needing its own case. If
  it proves fiddly in practice, the fallback is that only top-level fences make
  bands and nested members join the outer run — worse, but not wrong.
- **Imports** land below everything, as they do today, and therefore in no fence.
  That is consistent: their Desktop position is outside every fence too.
- **`repackMobileBoard()`** needs the same run logic, not a second implementation
  of it.

This is the largest single piece of the work — call it a third of it — and it is
worth building the Desktop half first and landing it, because the Mobile pack can
be developed against real fenced boards instead of imagined ones.

## Decision 5 — deleting a fence leaves the cards *(decided)*

The fence goes to the bin. The cards do not move.

It is free — membership is derived, so they are loose the moment the rectangle is
gone — and it has a property worth naming: **undo restores the grouping without
restoring anything about it.** The fence comes back, the cards never moved, and
they are inside it again because they are inside it. Nothing was recorded, so
nothing can come back wrong.

The alternative — delete takes its contents — was rejected on the bin. Restoring
a fence would have to bring its members back with it, which means the bin learns
about relationships between binned items, which it has none of today
(`docs/architecture.md`: the bin "holds everything thrown away with no relation to
what came after"). One gesture's convenience against a new class of bookkeeping in
the one feature whose entire job is being reliable.

Clearing a region in one go remains available and is already spelled: select the
fence, `stackLayerIds` gives you the layer, delete. It is two steps because it
destroys things.

## Decision 6 — roll-up ships, and its four questions are answered here *(decided)*

Double-click a fence's bar and it collapses to just its label; its members are
hidden. It is the Fences signature gesture and it is what makes a crowded board
legible rather than merely annotated.

**It is not in v1.** But it is settled now rather than later, because every one of
its questions is about v1's data model, and answering them under pressure after
the model is written is how you get a second model.

`meta.rolled` is **the expanded height in world units**. Present means rolled and
carries what to restore; absent means open. One key rather than a flag plus a
memo, no ambiguity, and an older reader carries it through untouched while
showing the fence as a short empty card.

### The four questions

**1. Culling.** A rolled fence's members are not mounted. `canvas/items.js`
`sync()` already decides what to mount, so this is one more term in that test —
"is this inside a rolled fence?" — against a memoised lookup. The spatial index
never needs to know.

The members keep their coordinates. A rolled fence therefore still occupies the
board space its contents claim, invisibly. On an infinite canvas nothing else was
going to use that space, and the payoff is that unrolling is free and cannot go
wrong: no geometry moved, so there is nothing to restore.

**2. Search.** A hit inside a rolled fence **unrolls it**, then jumps. Any other
answer is a search that finds something and then shows you nothing.

The unroll is a plain state write, not a command — the same shape as
`dismissGhosts()`: it marks the board dirty and pushes no history. Finding
something is not an edit you should have to undo.

**3. The HUD count.** Unchanged. Rolled members still count. The readout says
what is on the board, not what is on the screen — it already ignores everything
culled, and a rolled fence is culling with a nicer name.

**4. Export.** `meta.rolled` is written as-is, so a board opens the way you left
it — the same property `view` and `settings` already carry. Nothing special, and
worth writing down precisely because it looks like it needs a rule and does not.

**And on Mobile**, a rolled fence is a band with no run beneath it. That falls out
of the run packer at no cost, which is a good sign for both designs.

## What travels, and where that is decided

The whole "what comes along when this moves" surface is **four call sites**, and
they are already there for sticky notes:

| site | today |
| --- | --- |
| `canvas/input.js:634` | `[...selection, ...stuckFollowers(selection)]` — drag a selection |
| `canvas/input.js:720` | `stuckFollowers([id])` — drag one card |
| `canvas/input.js:1519` | `stuckFollowers(selection)` — arrow-key nudge |
| `layout.js:623` | `if (driven) restick(driven)` — inside `commitGeom` |

A fence adds `fenceFollowers()` and `refence()` at those same four, and nowhere
else. The narrowness of that seam is the strongest evidence the model is right —
if a fifth site turned up, the design would be wrong.

`stuckFollowers()` already handles the case that would otherwise bite: *"Anything
already moving is left out"*, so a marquee that catches a fence and its members
moves each card once rather than once as a selection and again as a follower.
`fenceFollowers()` must keep that property, and the two must be unioned to a
**fixed point** before either is asked — a note stuck to a card inside a fence has
to travel with the fence, which is the closure of both relations, not one applied
after the other.

**Where the two genuinely merge is z-order.** `stackRoot()` in `stacking.js` walks
a card up to the bottom-most thing that owns its layer, and it currently knows
only about sticks. A fence sits behind its members, so "bring this fence to front"
has to carry them, and `stackRoot()` has to walk fence membership too. That is the
one function where fences and stickies stop being parallel and become one
question.

## The interior is transparent

A fence is a large card, and the first thing a large card breaks is that
`left-drag empty space` pans the board. Inside a 2000-unit fence there would be no
empty space left.

So the fence's body is `pointer-events: none`. What takes a press is the **label
bar** along its top edge and a few pixels of **border**:

```
┌─ kitchen ──────────────────────┐   ← bar and border: drag, resize, select,
│                                │      and double-click to roll up
│    ▢        ▢                  │   ← interior: presses fall through to the
│                                │      board, exactly as before
│         ▢                      │
└────────────────────────────────┘
```

Pan works inside a fence. Marquee works inside a fence. A card inside a fence is
hit before the fence, because the fence's body cannot be hit at all. And "drag the
fence" is one unambiguous target rather than a guess about whether the press
landed on a card.

This also settles the resize grips — they are on the border, where the existing
grip machinery already puts them — and it gives roll-up somewhere unambiguous to
live, since the bar is the only part of a fence a double-click can land on.

Grouped by why, not by directory. Line counts are estimates.

### Changed, because a fence is not content

This is the list that gets forgotten, and each one is a small silent bug if it is
missed:

| site | why |
| --- | --- |
| `hasContent()` in `state.js` | a board of empty fences is an empty board — the ghost cards should still be showing |
| `ensureGhostCards()` / `dismissGhosts()` | ditto: drawing a fence must not dismiss the hints |
| `paletteSources` / `ui/pigments.js` | a fence has no picture; it must not count toward the Dynamic palette's sources |
| the HUD count in `ui/hud.js` | "42 items" should not include the boxes drawn around them |
| `ui/search.js` | a fence's name **should** be findable — this one is the exception, and jumping to a region is arguably the feature |
| `optimize/` | `WORTH_IT` must not see a fence as something to compress |
| `sticky.js` `measureStick` | a note must not stick to a fence, for the same reason it may not stick to the title card |
| `web-graph.js` `connectSelection` | a spanning tree over fences draws lines between regions; probably wrong, certainly untested |

`isFurniture()` is **not** the right switch for most of these. Its doc comment is
specific: it means "the app put this here, not the user", and a fence is the
user's. Read that comment before reaching for it — it exists precisely because
this question was spelled out at four sites and drifted.

### The format

`docs/mbrd-format.md` gains:

- `fence` in the `type` list.
- `meta.fence`, on any type: the id of the fence a card is inside, or `null`.
  Stamped at save, seeds the runtime memo, dangling ids fall back to measuring,
  and it is the only membership record a board opened straight into Mobile has.
- `meta.rolled` on a fence: the expanded height in world units. Present means
  rolled.
- A fence's label is its `name`. No new key — `editItemName()` already edits it.

Every one of those is an additive `meta` key or a new `type` value, which the
document's own compatibility rules call free. **No version bump.** Say so
explicitly in the changelog, because "a new item type" sounds like one and is not.

## Staging

**v1 — the fence exists, on both layouts.** `cmds.fenceSelection` from the context
menu; name it; drag it and its cards come; resize it and membership follows the
edge; it saves, loads, bins, restores and undoes; and it packs as a band and a run
on Mobile. Build the Desktop half first and land it — the Mobile pack is much

## What could go wrong

- **A fence spanning many spatial cells.** `canvas/spatial.js` buckets at 512
  world units, so a 4000×3000 fence is registered in ~48 cells and every rebuild
  walks them. Not a blocker — the module's header already anticipates it and says
  `rebuild()` can override the cell size per board — but a board of large fences
  is the case that would find out, and it should be measured rather than assumed.
- **A fence bigger than the viewport, culled by its centre.** Culling tests the
  true rectangle after the grid narrows the field, so this *should* be fine. Worth
  an explicit test: a fence you can only see by zooming out is a bad first
  impression and the failure is invisible on a small board.
- **The membership memo and undo.** Undoing a move restores geometry; it must also
  restore what was in what. The memo is keyed by member id and `restick()` is
  called from `commitGeom` — which undo does not go through. **Check whether
  sticky notes already have this bug before deciding it is a fence problem**; if
  they do, it is one fix for both and it belongs in `sticky.js`.
- **The Desktop-only measurement rule leaking.** Every `fenceOf()` call has to be
  reading Desktop geometry, including the ones that run while Mobile is the active
  layout. This is the single most likely way to ship a bug that silently eats
  somebody's grouping, and it deserves a test that switches layouts, saves, and
  asserts membership survived the round trip.
- **Two mechanisms that are 80% the same.** `sticky.js` and `fences.js` will read
  alike, and the temptation will be to abstract them into one "what follows what"
  module. Resist it until there is a third: the predicates differ (overlap vs
  containment, notes-only vs any type, live-layout vs Desktop-only, re-measure on
  resize or not), and an abstraction over two cases would hide exactly the
  differences that are the design. `stackRoot()` is the one place they should
  meet.

## Tests

Unit, in `tests/`:

- centre-in-rect membership, a card straddling an edge, and smallest-fence-wins
  for nesting;
- moving a fence carries its members and does **not** swallow what it passes over;
- resizing a fence **does** re-measure — both halves, because each is surprising
  alone;
- a card dragged out of a fence is loose after the drop and not before;
- `fenceFollowers` ∪ `stuckFollowers` reaches a fixed point: a note stuck to a
  card in a fence travels with the fence, and is moved exactly once;
- `meta.fence` round-trips through `serializeBoard`/`loadBoard`; a dangling id
  falls through to measuring; **and membership survives a Desktop → Mobile →
  Desktop round trip with a save in the middle**;
- the Mobile pack: a run is contiguous, a band is full width, nothing from a later
  run claims a row above an earlier band, and riders do not take a slot;
- deleting a fence leaves its members' geometry untouched, and undo restores the
  grouping;
- a fence does not count toward `hasContent()`, and drawing one does not dismiss
  the ghosts.

End-to-end, in `tests/e2e/board.spec.js`: fence a selection of two cards, drag the
fence, assert both moved; switch to Mobile and assert the band is above both;
refresh and assert the grouping survived.

## Still open

Two, and neither blocks a start:

1. **Should a Mobile drag into a run re-fence the card?** It is the natural
   gesture and it contradicts "membership is measured on Desktop geometry" — it
   would mean the phone can write a relation it cannot compute. Possible, via an
   explicit `refence()` on the drop rather than a measurement, but it is a second
   way for membership to change and it should not be built by accident.
2. **Loose cards at the bottom, or interleaved by the arrangement's order?**
   Bottom is planned. Interleaving is more faithful to the arrangement and makes
   every stray its own run, which complicates the barrier rule for a gain nobody
   has asked for yet.
