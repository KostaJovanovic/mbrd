## §0 — The one-paragraph version

mbrd already has a working Electron shell. FileAnalyser has a second one and an
Android shell, and both are further along in five ways: one release for every
system from one manual workflow, an updater of its own with no update files, a
title bar that lives outside the page, an installer that asks Install or Portable
on a real first page, and an Android app that injects the **desktop's own bridge
object** so the web code does not know it is on a phone. This plan brings all
five to mbrd. The Android shell wires into `main.ts` through the branch that
already exists for `window.mbrdDesktop`. It keeps boards as real files in
`Documents/mbrd/` on the phone. It updates itself from the same GitHub release
as the desktop apps.

## §3 — What mbrd already has, and keeps

The Electron groups A–J of `electron-tasks-2026-09-06.md` are done. None of this
is redone:

- **The ports** (`web/assets/js/platform/platform.ts`) and **the store seam**
  (`setStoreBackend()` in `storage/idb.ts`), wired once in `main.ts`. The
  Android shell reuses both through the same bridge (§5.2).
- **The file-backed store** (`desktop/store.ts`, envelope format in
  `desktop/format.mts`). The Android store writes the same format (§5.4).
- **The document model**: `DocumentRef`, Save / Save As / Export, shelf path
  rows, `onCloseRequested`, `onOpenFiles`.
- **Paths a renderer cannot name** (`desktop/files.ts`' `vouch()`). The Android
  file plugin takes the same rule (§5.5).
- **The CSP from `web/_headers`**, applied by `desktop/protocol.ts`. Android
  becomes the third enforcer of the one policy (§5.7).
- **Native work**: bundled GPL ffmpeg (`scripts/fetch-ffmpeg.mjs`), u2netp on
  `onnxruntime-node`, `sharp` decode.
- **The Playwright smoke test** (`desktop/test/smoke.spec.ts`), the portable dev
  copy (`scripts/portable.mjs`, rebuilt by `save.bat`), the icon generator
  (`tools/gen-desktop-icons.mjs`), the log file.

Four ways mbrd stays **stricter** than FileAnalyser, on purpose:

1. **A CSP everywhere.** FileAnalyser ships none. mbrd keeps its policy on the
   desktop and adds it on Android (#26). The bar page obeys it too (§4.1).
2. **The page never chooses ffmpeg arguments.** FileAnalyser's page passes a
   whole argument list, so its shells need `checkArgs()` and a Java port of it.
   mbrd's `NativePort` passes bytes and two clamped numbers, and main (or the
   Android plugin) builds the arguments. There is nothing to check.
3. **ffmpeg is bundled**, not looked up on `PATH`. The probe (§4.7) runs
   against the bundled binary.
4. **A smoke test drives the packaged shape** on every release (§4.4).

## §4 — Desktop

### §4.1 The title bar leaves the page

**The shape.** The `BrowserWindow`'s own web contents is the bar page,
`app://mbrd/__chrome/titlebar.html`. The board is a `WebContentsView` added to
the window and placed at `y = barHeight` by a `layout()` that runs on every
geometry change. The board gets an ordinary viewport: `position: fixed`,
`100vh` and `window.innerHeight` are right by construction.

**Why this way round.** On Windows the OS computes the drag hit-test from the
window's own web contents. So `-webkit-app-region: drag` must live in the bar,
and the bar must be the window's contents. FileAnalyser's `main.mjs` header says
so, and it is the reason not to swap the two.

**What moves out of the web app.**

- `web/assets/js/ui/window-chrome.ts` is deleted, with its call in `main.ts`.
- `#window-drag`, `#window-mark`, `#window-title` and `#window-controls` leave
  `index.html`. Their rules leave `chrome.css` (33 selector hits for
  `is-framed`, `is-fullscreen` and `#window-`). `web/404.html` follows through
  `save.bat`.
- The `window-min`, `window-max`, `window-restore` and `window-close` symbols
  move to the bar page's own markup, or leave `icons.svg`. `tests/icons.test.js`
  checks both directions, so it tells you which.
- The **frame port** goes: `FramePort` and `webFrame` in `platform.ts`,
  `electronFrame` in `platform/electron.ts`, the `win` half of the preload, and
  `windowMinimize` / `windowMaximize` / `windowClose` in `commands/view.ts`.
  The preload's `bridge` number goes to **3**, because a field was removed.

**What the bar shows.** The mark (not on macOS, where the traffic lights sit),
the four drawn menus, the board title with its dirty mark (#15), a drag
spacer, and minimise / maximise / close (not on macOS). **No back and forward
arrows**: FileAnalyser has them because its site has page history, and a board
has none.

**The menus.** `desktop/menu.ts` keeps one table and gains FileAnalyser's three
consumers:

- `buildMenu()` makes a real `Menu` only to register the accelerators. It is
  never shown (`autoHideMenuBar`, and no frame).
- `menuModel()` hands the same tree to the bar as plain data.
- `runMenuItem(id)` checks an id the bar or panel sends back against the tree
  before it runs anything.

Every entry keeps its `cmd:` string, so `tests/desktop-menu.test.js` keeps
reading the table. The Electron **roles** (cut, copy, paste, zoom, reload,
devtools, full screen) mean nothing in a drawn menu, so each becomes an action
against the board's view, as FileAnalyser spells them out. Cut, copy and paste
stay in the hidden menu only, for their accelerators.

**Each open menu is its own window.** A child view always composites above the
contents it was added to, so a panel drawn in the bar page lands under the board
and is invisible. The DOM cannot see that, which is why FileAnalyser's geometry
checks all passed while the menus showed nothing. The panel window is made
hidden at start-up and reused. It keeps its natural size. Its `blur` is the whole
of "click outside to close". A re-open of the menu that just closed is ignored
for 250 ms.

**Four details FileAnalyser learned the hard way, all carried over:**

1. **Full screen is tracked from the events**, not read back: on Windows
   `isFullScreen()` lags `enter-full-screen`.
2. **Zoom zooms the bar too**, because Chromium stores zoom per origin and the
   bar, the panel and the board are all `app://mbrd`. Main keeps the bar's CSS
   height apart from its window height, multiplies by `1.2 ^ level` at the
   moment it sets the level, and rounds up.
3. **The bar reports its own height** from its CSS, so the number lives in one
   place.
4. **Show the window when the board paints**, not the bar.

**mbrd-specific rules the bar page must keep:**

- **The CSP applies to it.** `protocol.ts` sends `_headers`' policy on every
  `app://` response, `__chrome/` included. So the bar page has **no inline
  script and no inline style**. FileAnalyser's bar has an inline theme script,
  and that shape does not port.
- **The look.** The bar reads `mbrd.appearance` from `localStorage` (same
  origin) and sets `data-whimsy` and `data-palette` before first paint, from a
  blocking classic `<script src>` in its head. It listens for the `storage`
  event, so a whimsy change in the board repaints the bar. Where the pre-paint
  logic comes from (an import of the reader in `ui/look.ts`, or a third copy
  held by `tests/appearance.test.js`) is the task's to decide.
- **Styles**: `/assets/css/tokens.css` plus `desktop/chrome/titlebar.css`. The
  bar page is not `index.html`, so the three-list stylesheet rule does not
  apply to it.

**The 9.8 fault, made impossible.** The chrome pages are built into
`desktop/dist/chrome/`, next to the two bundles, and main serves `__chrome/`
from `dist/chrome/` through an allow-list. `files:` already ships `dist/**`, so
there is no second glob to forget. Two checks back it up:

- `tests/desktop-package.test.js` asserts that every file in the allow-list has
  a source in `desktop/chrome/` and that the build script copies its extension.
- The release workflow lists `app.asar` after each pack and fails when
  `dist/chrome/titlebar.html` is not inside.

**The smoke test must find the board.** With two web contents, Playwright's
`firstWindow()` is the bar. The spec picks the page whose URL is
`app://mbrd/index.html`. It also asserts the bar page loaded, which is the 9.8
fault seen from the other side.

The changelog opens in place, in the board view under the bar, as `/patch`
does on the web. It was a separate framed window, from before the bar left the
page, and the maintainer chose in place on 2026-09-13. Leaving the board
flushes it first, as a close does, and a menu row pressed on the changelog
brings the board back before it runs.

### §4.2 The updater

`desktop/updates.ts` becomes a port of FileAnalyser's `updater.mjs`:

| copy | how it is known | what happens |
| --- | --- | --- |
| NSIS install | `Uninstall mbrd.exe` beside the exe, no `portable` marker | Download the new installer, check its SHA-256, run it `/S --updated` on quit, or at once with `--force-run` on "Restart now" |
| AppImage | `APPIMAGE` is set | Download beside it, check the digest, rename over it, `app.relaunch` on "Restart now" |
| Portable, macOS | anything else | "mbrd <v> is out", then open the release page |
| dev | `!app.isPackaged` | never checks |

- One HTTPS request to `api.github.com/repos/KostaJovanovic/mbrd-release/releases/latest`.
  The answer gives the tag, each asset's URL and its `sha256:` digest. The repo
  is public, so the request carries no token (#31).
- **A download that does not match its digest never takes over. A release with
  no digest never installs.**
- The first check runs 20 s after start, then one every 6 h. "Later" silences
  that version for the session. A background failure stays silent.
- Help > Check for updates and the panel row (#11) always answer.
- **Native dialogs answer, not toasts.** The page only starts a check. So
  `announceUpdate` in `main.ts` goes, and `UpdatesPort` shrinks to
  `check(): Promise<void>` (web default: nothing).
- The asset patterns: `^mbrd-Windows(-\d+(\.\d+)*)?\.exe$` and
  `^mbrd-linux-x64(-\d+(\.\d+)*)?\.AppImage$`. `tests/desktop-package.test.js`
  holds them against the `artifactName` lines.
- **Removed**: `electron-updater` from `dependencies` and from the esbuild
  externals, `publish:` (becomes `null`), `MBRD_SIGNED`. **Added**:
  `nsis.differentialPackage: false` and `dmg.writeUpdateInfo: false`.

### §4.3 The installer

A port of FileAnalyser's `desktop/build/installer.nsh`, in mbrd's paper look.

- **Page 1**, full window (`customWelcomePage`): "How do you want mbrd?" Two
  cards, **Install** and **Portable**. The Portable card has its own folder box.
  The Install card carries the association box (#8). An update run (`/S
  --updated`) never sees the page, and neither does the elevated second copy
  UAC starts.
- **Page 2**, the template's progress page, restyled
  (`customPageAfterChangeDir`).
- **Page 3**, "mbrd is ready" (`customFinishPage`), with a box that starts mbrd.
- `customInstallMode` skips "only for me / for everyone". An everyone-copy that
  already exists is updated in place.
- **The portable section is section 0**, declared in `customHeader` before the
  template's own install section. It unpacks the app into the chosen folder and
  writes the `portable` marker. For a portable copy, section 1 (the template's)
  is off: no uninstaller run, no registry key, no shortcut. `customInstall`
  fails the build if the install section stops being section 1.
- **Updating a portable copy**: run the new installer, pick Portable and the
  same folder. The section refuses to overwrite a running copy, clears the old
  `resources/` and `locales/`, and leaves `data/` alone.
- `allowToChangeInstallationDirectory: false`. `ManifestDPIAware true`.

**The association (#8).**

- Windows stops using electron-builder's `fileAssociations`: it moves under
  `mac:`, where the `.icns` bundle needs it. Verify that electron-builder honours
  it at platform level. If it does not, keep it top-level and delete the keys
  in `customInstall` when the box is unticked, as `installer.nsh` does today.
- When ticked, `customInstall` registers `.mbrd` under
  `HKCU\Software\Classes` (ProgID, icon, `open` command) and calls
  `SHChangeNotify`.
- The answer is stored as `HKCU\Software\mbrd\AssociateMbrd`. A silent update
  reads it and does the same again.
- `customUnInstall` removes the keys only while they still point at this
  install.
- Windows 10 and later may still ask the user once to confirm the default app.
  That is the OS, and the page copy says so.

Three NSIS failures from `electron-tasks-2026-09-06.md` group H still apply:
`MUI_HEADER_TEXT` is undefined at the include point, and a warning is an error
because makensis runs twice (wrap installer-only code in `!ifndef
BUILD_UNINSTALLER`). FileAnalyser reaches `customWelcomePage` with
`allowToChangeInstallationDirectory: false`. mbrd's comment that the hook "is
not reached" was written with the folder page on.

checks kept:

1. **version** (ubuntu): read `VERSION` and `COMMIT_COUNT` from `version.js`,
   compute the semver (§4.5), run `npm test` (no install).
2. **desktop** (matrix windows / macos / ubuntu, `fail-fast: false`): root
   `npm ci` and `npm run build`, `desktop` `npm ci`, `fetch-ffmpeg`, typecheck,
   the smoke test (xvfb on Linux), `electron-builder --<os> --publish never
   -c.extraMetadata.version=<semver>`, the `app.asar` chrome check, upload the
   one file per system.
3. **android** (ubuntu): the FFmpeg cache or build (`continue-on-error`, a
   warning when it fails), `mobile` `npm ci` and `npm run sync`, the keystore
   from secrets, `gradlew testReleaseUnitTest assembleRelease
   -PmbrdUpdateFeed=<api url>`, rename to `mbrd-android-<semver>.apk`.
4. **publish** (only when the "Publish the release" box is ticked), into
   `KostaJovanovic/mbrd-release` (#31): `gh release create v<semver> -R
   KostaJovanovic/mbrd-release --target main --latest` with every file at
   once, or `upload --clobber` into an existing one. The files are the apps
   (three until the Android job exists) and `mbrd-source-<semver>.zip` (#32).
   `GH_TOKEN` is the `RELEASES_TOKEN` secret. The notes are FileAnalyser's
   (#34): which file for which system with a direct link, how it updates, and
   the one-time warning per system. mbrd adds the "new, less tested" line for
   macOS and Linux (#35), the source zip, and the source commit. Then the same
   job tags that commit `v<semver>` in the private repo, with the job's own
   `GITHUB_TOKEN`.

**All files at once, on purpose**: an installed app reads the latest release,
and a half-uploaded one points it at a file that is not there yet.

**The source zip (#32).** `git archive --format=zip --prefix=mbrd-<semver>/
"$GITHUB_SHA"` in the publish job: the tracked files of the released commit and
nothing else, so it is the source of exactly what shipped. `export-ignore` in
`.gitattributes` leaves out `research/` (but not `research/docs/`), `scratch/`
and `CLAUDE.md`: those are plans and notes, not the app. No updater pattern
matches it. The FFmpeg that the desktop bundles is not in it:
`.github/THIRD-PARTY.md` holds that source offer, and the About sheet must show
it (§5.9).

**Why a second repository (#31).** The source repo is private. To anybody not
signed in, GitHub answers a private repo's release page, its assets and its API
with a 404. The download button and both updaters would stop. A token inside
the app is a token anybody can read. So the releases live in a public repo that
holds no source.

- **`RELEASES_TOKEN`** is a fine-grained token with access to `mbrd-release`
  only, Contents read and write. The job's own `GITHUB_TOKEN` cannot write to
  another repo. When the token expires, publishing fails and nothing else does.
- **`--target main`, not `$GITHUB_SHA`.** A tag in the release repo must name a
  commit in the release repo, and the source commit is not there. Every tag
  there points at the README commit. The tag in the private repo ties a release
  to its source.
- **The release repo needs one commit before the first release**: the README.
  It is also the page `softwareHelp` names (#9).
- **Actions minutes.** The workflow runs in the private repo, so it spends the
  account's monthly allowance, and a macOS or Windows minute costs more than a
  Linux one. Watch the use after the first releases.

`save.bat` gains option 1, **release**: save, push, then `gh workflow run
release.yml -R KostaJovanovic/mbrd --ref <branch> -f publish=true`. Not fatal:
without `gh`, it says to start the workflow from the Actions tab.
`.github/workflows/desktop.yml` is deleted. `ci.yml` is untouched and still runs
`npm test` before `npm ci`.

### §4.5 The version

- **`save.bat` reads `COMMIT_COUNT` out of `version.js`**, adds 1, and aborts
  when it cannot read it. `git rev-list --count HEAD` goes. FileAnalyser learned
  this when a squash made rev-list return 1 and its public version fell from
  8.14 to 0.02. Android makes it worse: a `versionCode` that goes backwards
  strands every installed APK.
- **Semver**: `VERSION` `0.301` becomes `0.301.0`. After the first crowned
  release, `1.05` becomes `1.5.0`. The label on the release is the `VERSION`
  string. The updaters compare numbers part by part, so both forms order
  correctly.
- **Nothing writes `desktop/package.json`.** It stays `0.0.0` in the repository.
  The workflow and `scripts/portable.mjs` pass the version to electron-builder
  as `-c.extraMetadata.version`, so a local portable copy carries the real
  number and its updater does not see every release as newer.
- **Android**: `mobile/tools/stamp-version.mjs` writes `versionName` (the
  `VERSION` string) and `versionCode` (`COMMIT_COUNT`) into
  `android/app/build.gradle`. That file is tracked, as in FileAnalyser.

### §4.6 macOS

`desktop/scripts/after-pack.cjs`: an ad-hoc `codesign --force --deep --sign -`
on the merged universal app only (skip the `-temp` halves, or
`@electron/universal` refuses to merge them). `mac.identity: null` stays. The
download page leads with **Open Anyway** in Privacy & Security and keeps the
`xattr` line as the fallback. Remove both the hook and `identity: null` once a
Developer ID exists.

### §4.7 Hardware video encode

- **`desktop/ffmpeg-accel.ts`**, pure (no Node or Electron imports), from
  FileAnalyser's `ffmpeg-accel.mjs`: `FAMILIES` (NVENC, Quick Sync, AMF,
  VideoToolbox), `crfToBitrate()`, `accelerate(args, caps)`. **Not** its
  `checkArgs()`: see §3 rule 2.
- **The probe** in `desktop/native/ffmpeg.ts`: encode one throwaway frame with
  each family's H.264 encoder and keep only those that exit 0. Cache the result
  in `userData/ffmpeg-caps.json`, keyed by the binary's path, size and mtime.
  `ffmpeg -encoders` is not evidence: a full build lists families the machine
  cannot run.
- **`transcode()`** runs the accelerated arguments first. **A hardware failure
  retries the original software arguments**, so a driver quirk never loses a
  job. `firstFrame()` does not change.
- Which families each fetched build carries (gyan.dev essentials, evermeet,
  johnvansickle static) is measured, not assumed. A build with none still
  works: the probe finds nothing and software runs.
- Measure a 10 s 1080p clip on WASM, native software and the best hardware
  family, and write the numbers into the file header, as FileAnalyser's README
  does.

### §4.8 The extras (#15)

- **Window size and place** in `userData/window-state.json`, written 400 ms
  after a move or resize and on close, restored at start (maximised too).
- **Help > Where my data is stored**: "Installed copy" or "Portable copy", the
  data folder, and a button that opens it. The portable fallback note
  (`startupNote`) stays.
- **Help > Check for updates** runs the updater at once.
- **The bar names the board.** `setDocument` already reaches main and sets the
  window title. Main also forwards the title and the dirty mark to the bar.

### §4.9 desktop.bat

FileAnalyser's loop, on esbuild rather than tsc:

1. Clear `ELECTRON_RUN_AS_NODE` (kept from mbrd's launcher).
2. On the first run, `npm install` at the root and in `desktop/`.
3. `npm run build` and `npm --prefix desktop run build` once.
4. `start /b` the web watch (`npm run dev`) inside this console, unless one is
   already running (found the way FileAnalyser finds its tsc pair).
5. Run Electron **in the foreground** with any dragged path passed on. The shell
   bundle has no watch: a change under `desktop/` needs a relaunch, and the
   launcher says so.
6. On exit, stop the watch it started.

`desktop.bat portable` stays. This replaces the "no console" design in
today's `desktop.bat`, on the maintainer's decision.

### §4.10 The download page

- One button, "Download mbrd", opening
  `https://github.com/KostaJovanovic/mbrd-release/releases/latest`. The "All
  releases" link opens `mbrd-release/releases`.
- Under it, one line per system naming the file to pick: Windows (`.exe`,
  Install or Portable), macOS (`.dmg`, Intel and Apple silicon), Linux

- The warning section stays. macOS leads with Open Anyway (§4.6). Android gains

- The macOS and Linux lines say "new, less tested" (#35). Remove that once
  somebody has used each by hand.
- `tests/download.test.js` changes from "three filenames in step" to: the one
  button points at `releases/latest` on `KostaJovanovic/mbrd-release`, no link
  names the private repo or a versionless asset, and the three prose checks

## §5 — Android

### §5.1 The package

`mobile/`, its own `package.json` (Capacitor 8, `@capacitor/android`,
`@capacitor/core`, `@capacitor/cli`, `@capacitor/assets`, `esbuild`, `sharp`).
`mobile/android/` is tracked, Java included. `mobile/node_modules/`,
`mobile/www/` and `mobile/ffmpeg/{out,work}/` are gitignored, as are the
generated assets (`mbrd-bridge.js`, `mbrd-files.txt`, `mbrd-csp.json`).

`capacitor.config.json`: `appId com.valjdakosta.mbrd`, `appName mbrd`,
`webDir www`, `server.hostname app` with `androidScheme https`,
`android.resolveServiceWorkerRequests false`, `allowMixedContent false`,
`captureInput false`, a `minWebViewVersion` taken from
`research/docs/browser-support.md`'s floor, and `SystemBars.insetsHandling
disable`.

**The host is `app`, not Capacitor's `localhost`.** `isDev()` in `util.ts`
treats `localhost` and LAN addresses as a dev server. The live-reload loop
(§5.12) still gets dev behaviour on a LAN address.

**The root stays zero-dependency.** `npm test` still installs nothing.

### §5.2 The bridge

`mobile/bridge/mbrd-bridge.ts`, bundled by esbuild into one IIFE and written to
`android/app/src/main/assets/mbrd-bridge.js` by `stage-web.mjs`. That folder is
outside `assets/public/` on purpose: `cap sync` owns `public/`, and the page has
no reason to fetch the bridge. `MbrdShell.load()` injects it with
`addDocumentStartJavaScript`, for the app origin (and the dev server) only,
before the first page. `window.mbrdDesktop` therefore exists before `main.ts`
reads it.

The object has the **same shape as `desktop/preload.ts`** at `bridge: 3`, plus:

- `shell: 'capacitor'` and `platform: 'android'`. The desktop leaves `shell`
  unset. A branch that must not run on a phone tests `bridge.shell`.
- **No `win`**: the frame port is gone anyway (§4.1).
- `setDocument` and `onCommand` do nothing. `relaunch` is `location.reload()`.
- `startupNotes()` carries the storage fallback note (§5.4).

So `main.ts`' existing branch runs unchanged: `setPlatform(electronPlatform(bridge))`
and `setStoreBackend(electronStore(bridge))`. **`isDesktop()` is true on the
phone**, and every branch behind it is right there: Save / Save As / Export, the
service worker left unregistered, `ensurePersistence()` skipped, relaunch on
Clear everything. The names `mbrdDesktop` and `isDesktop()` stay, as
FileAnalyser kept `anrDesktop`. The header of `platform.ts` says that "desktop"
now means "a native shell is wired".

**Web changes, all of them small:**

- The `Bridge` interface in `platform/electron.ts` gains `shell?: string` (it
  erases).
- `main.ts`' `onOpenFiles` handler opens a `.mbrd` with `openFile()` and hands
  every other file to the import path, so shared media lands as cards (#23).
  The desktop only ever sends `.mbrd`, so nothing changes there.
- `LifecyclePort` gains `onBack(fn: () => boolean)` (§5.10).

**The trust line.** The bridge runs in the page, and a crafted file that finds
an XSS runs there too. **Nothing in the bridge is a security check.** Every
check lives in the Java plugins, which such a script can call directly.

### §5.3 Moving bytes

Capacitor's plugin bridge is JSON, so bytes would cross it as base64: a third
larger, with several copies alive at once. mbrd moves more bytes than
FileAnalyser (the whole store), so this matters more here.

- **Page to native**: `MbrdBytes`, a `WebMessageListener` the page sees as
  `window.mbrdBytes`. `ArrayBuffer` chunks where the WebView has
  `WEB_MESSAGE_ARRAY_BUFFER`, base64 chunks of at most 4 MB where it does not.
  A begin message, the chunks, an end message. **Native acknowledges every
  message**, and the page waits for each acknowledgement, so one chunk at most
  is in flight. Transfers queue, so two never interleave.
- **Native to page**: a plain GET under `/__mbrd/`: `store/<store>/<key>`,
  `file/<token>`, `ff/<session>/<name>`. `MbrdWebViewClient` streams each one
  from disk.
- The bridge rebuilds the `ArrayBuffer`s the desktop contract promises
  (`HandedFile.data`, a store value, a transcode result), so
  `platform/electron.ts` sees the shapes it already handles.

### §5.4 The store (#19, #20)

- **Where**: `Documents/mbrd/.store/<store>/<key>`, the four stores of
  `desktop/store.ts` (`kv`, `assets`, `library`, `matte`). A `.nomedia` file in
  `.store/`, so gallery apps do not index hundreds of hash-named pictures.
- **The format is the desktop's.** The page side runs `encode()` / `decode()`
  from `desktop/format.mts` and native stores the bytes verbatim. So a store
  folder copied from a phone reads on the desktop. `format.mts` becomes
  `Uint8Array`-based (Node's `Buffer` is a `Uint8Array`) so the bridge bundle
  can import it. `tests/desktop-store-format.test.js` guards it.
- **The same rules as `desktop/store.ts`**: writes go to a temp name and rename.
  `clear()` renames the store folder to `<store>.trash-<stamp>` and deletes it
  after; a sweep at start removes leftovers. Keys must be lowercase and at most
  200 bytes encoded. `MbrdStore.java` names `desktop/store.ts` in its header,
  and the reverse.
- **Access**: `MANAGE_EXTERNAL_STORAGE` on Android 11 and later.
  `WRITE_EXTERNAL_STORAGE` plus `requestLegacyExternalStorage` on Android 7 to
  10.
- **The first run.** Before the WebView loads, `MainActivity` checks the grant.
  Without it, a native screen explains why ("mbrd keeps your boards as files in
  Documents/mbrd, so they survive an uninstall and show in Files") with
  **Allow** (opens the system's All files access page) and **Not now**.
- **"Not now"** uses the app's private files folder for this run, the way the
  desktop falls back from a read-only portable folder, and `startupNotes()`
  says where the boards are. When the grant arrives later and
  `Documents/mbrd/.store/` is empty, the private store moves there once.
- **The IPC cost is measured, not assumed.** Save and boot a board of 300
  photographs and compare with IndexedDB in the same WebView. The electron plan
  measured the same thing for the desktop store.

### §5.5 Files and Save (#21, #22)

`MbrdFiles.java` answers the `files` half of the bridge:

| bridge call | on Android |
| --- | --- |
| `pickSave(suggested)` | a native "Save as" dialog with a name field, filled with `<title>.mbrd`. It asks before it replaces. Returns `{ name, path }` with `path` under `Documents/mbrd/`. |
| `write(path, data)` | temp name and rename. Only paths under `Documents/mbrd/`, or paths this plugin handed out, are accepted: the `vouch()` rule. |
| `read(path)`, `exists(path)` | the same rule. Shelf path rows work as on the desktop. |
| `pickOpen()` | the system picker for `.mbrd`, anywhere. The file is **copied into `Documents/mbrd/`** (`name (2).mbrd` on a clash) and opened from there. |
| `pickImport()` | the system picker, several files, pictures, clips, sound, documents. Not copied: the bytes go into the store as assets. |

- **Save writes back** to the board's file on every Save. Save As asks for a new
  name in the same folder.
- **"Send file"** (the existing `share` row) sends a copy through the share
  sheet. The Android WebView has no `navigator.share`, so the bridge supplies
  one that handles **files** (through the byte channel and a `FileProvider`),
  not only text as FileAnalyser's does.
- **Downloads.** A `blob:` or `data:` link with `download` does nothing in a
  WebView. The bridge catches those clicks (a capture listener plus a wrapper
  on `HTMLAnchorElement.prototype.click` for detached links) and hands the file
  to the native save. With a shell wired, `platform.files` is the bridge's, so
  few links reach this path. It covers the rest.

### §5.6 Incoming files (#22, #23)

- Intent filters for `VIEW`, `SEND` and `SEND_MULTIPLE` on `content://` URIs:
  `application/vnd.mbrd+zip`, `application/octet-stream` (a `.mbrd` often
  arrives with no type, so the name or the ZIP magic decides), `image/*`,
  `video/*`, `audio/*`, `application/pdf`, `text/plain` for shared links.
  `file://` is refused.
- A `.mbrd` is copied into `Documents/mbrd/` and delivered with its new path.
  Anything else is delivered with no path, and `main.ts` imports it as cards.
- Delivery is the desktop's: `notifyListeners('open', …, retain)` until the page
  listens, then the bridge's `onOpenFiles` queue.

### §5.7 Routing and the CSP (#26)

- **`MbrdRouter.java`** is a port of `readPage()` in `desktop/protocol.ts`, not
  of `serve.py`: an extensionless path tries `<path>.html` first (`/patch`,
  `/download`, `/privacy`), a directory gets `index.html`, and nothing outside
  the staged tree is served. Capacitor's own server serves `index.html` for
  every extensionless path and its `RouteProcessor` only ever sees
  `/index.html`, so it cannot route.
- **`MbrdWebViewClient`** asks the router, hands Capacitor the routed request,
  and sets the content type from a table. `/_capacitor_file_/` and
  `/_capacitor_content_/` answer 404: they would hand an XSS a file reader.
  `/__mbrd/*` is the shell's namespace.
- **The service worker is never registered** (a shell is wired), but the SW
  client is still set, because `resolveServiceWorkerRequests: false` is
  FileAnalyser's guard against a stale second client.
- **The CSP.** `readPolicy()` moves out of `desktop/protocol.ts` into a pure
  `desktop/csp.mts`. `protocol.ts` and `stage-web.mjs` both import it.
  `stage-web.mjs` writes the policy and the exempt paths to `mbrd-csp.json`.
  `MbrdWebViewClient` adds the header to every response outside the exemptions.
  One policy in `web/_headers`, three enforcers, one parser. A test holds the
  staged JSON against a fresh parse.

### §5.8 Staging

`mobile/tools/stage-web.mjs` copies `web/` to `mobile/www/` with the desktop's
exclusions (`lab*.html`, `assets/lab-*.js`, `assets/app.js.map`, `sw.js`). It
builds the bridge, writes `mbrd-files.txt` (so each "does this file exist" is a
set lookup) and `mbrd-csp.json`, and copies an FFmpeg binary in when
`mobile/ffmpeg/out/` has one. `web/` holds no `.gz` files today. If one appears,
apply FileAnalyser's rename (the Android Gradle plugin unpacks every `.gz`
asset and drops the extension).

**The APK carries a copy.** An edit shows on the phone only after `mobile.bat`
runs again, or through the live-reload loop.

### §5.9 Native FFmpeg (#25)

- `mobile/ffmpeg/build-android.sh` and `.github/workflows/android-ffmpeg.yml`,
  copied from FileAnalyser: LGPL, `arm64-v8a`, MediaCodec, openh264, no network
  protocols, no capture devices, 16 KB page alignment. The binary ships as
  `jniLibs/arm64-v8a/libmbrdffmpeg.so` with `useLegacyPackaging`: an executable
  with a library's name, because the native library folder is the one place an
  app may execute from since targetSdk 29.
- **A child process**, not JNI. A crafted clip that crashes libavcodec kills the
  child, not the app.
- **`MbrdFfmpeg` exposes two methods, not an argument list**: `firstFrame(xfer)`
  and `transcode(xfer, maxEdge, bitrate)`, with the numbers clamped as
  `desktop/native/ffmpeg.ts` clamps them. Java builds the arguments. The encoder
  chain is `h264_mediacodec`, then `libopenh264`. **So there is no Java port of
  argument checks**: the page never names a file, a device or a protocol.
- The probe encodes three frames with MediaCodec and caches the answer keyed by
  the binary and `Build.FINGERPRINT`, because an OS update replaces the codec
  drivers.
- `native.can()` reports `transcode: true` only with a binary. Without one, the
  phone runs the web path, as the website does.
- **Licence**: the LGPL notice and the source offer go into the About sheet
  beside the desktop's GPL notice. That notice is still outstanding from the
  electron work too.
- **The unknown the whole Android speed-up rests on**: whether `h264_mediacodec`
  works from a standalone executable on real chipsets. Test it on two phones
  from different makers first. FileAnalyser has not measured it yet either.

### §5.10 The shell's behaviour

- **Insets, natively.** `MainActivity` pads the WebView's parent from
  `WindowInsets` and takes the keyboard into account. The page gets an
  ordinary viewport and needs no safe-area CSS: the title-bar lesson again.
- **The bar colour follows the page.** The bridge reports the page background
  whenever `data-whimsy`, `data-palette` or the body's style changes, and the
  status and navigation bands take it, with light or dark icons by luminance.
- **Landscape is full screen** (bars hidden, a swipe shows them), as in
  FileAnalyser. Keep it unless it gets in the way on a board.
- **Back (#24).** `LifecyclePort.onBack(fn)` is new: `fn` closes the topmost
  layer and returns whether it closed anything. The electron adapter wires it
  to `bridge.onBack` when present. The Android bridge answers `MainActivity`'s
  back callback with `handled` or `exit`. On `exit` the app goes to the
  background (`moveTaskToBack`) and never finishes. Twelve modules handle
  Escape today (`canvas/input.ts`, `ui/menu.ts`, `ui/drawer.ts` and nine
  more), so the task first lists them and then picks how "close the top layer"
  is known. Back means what Escape means.
- **Flush on pause.** The desktop holds a close until the flush resolves. A
  phone does not close, it pauses. `MbrdShell.handleOnPause()` tells the bridge,
  and the bridge runs the function registered through `onClose`.
- **The update check** starts from `MainActivity.onCreate` (§5.11).

### §5.11 Updates (#2)

`MbrdUpdate.java`, a port of FileAnalyser's `AnrUpdate.java` as it stands:

- **Only a build with a feed checks**: `BuildConfig.UPDATE_FEED`, set by
  `-PmbrdUpdateFeed` in the release workflow alone. `mobile.bat` builds never
  check. The feed is `mbrd-release`'s API URL, written out:
  `github.repository` names the private source repo (#31).
- At start, at most once every 6 h. "Check for updates" (#11) skips the wait and
  always answers.
- The asset `^mbrd-android(-\d+(\.\d+)*)?\.apk$`. **No digest, no install.**
- Download into the cache with a progress bar, check the SHA-256, check the
  package name and that the `versionCode` is higher, then write it into a
  **`PackageInstaller` session**. On Android 12 and later the session sets
  `USER_ACTION_NOT_REQUIRED`, which Android grants to an app that installed
  itself, so the update installs with no confirm screen. When Android still
  wants a yes, `InstallStatus` (a receiver that is not exported) opens the
  confirm screen.
- `REQUEST_INSTALL_PACKAGES` in the manifest. A Play flavour must drop both the
  feed and this permission (#27).
- `MbrdUpdateTest` covers the version comparison.
- **The key.** A new keystore for `com.valjdakosta.mbrd`, in the secrets
  `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`
  and optionally `ANDROID_KEY_PASSWORD`. `build.gradle` signs only when
  `MBRD_KEYSTORE` names the file. **Keep that key forever**: Android refuses an
  update signed with another key. Keep a copy offline.

### §5.12 The development loop

- **`mobile.bat`**: install `mobile/` on the first run, `npm run build`, `npm
  run sync` (stamp, stage, `cap sync`), find a JDK 21, `gradlew assembleDebug`,
  `adb install -r`, start the activity. `mobile.bat apk` builds only.
  `mobile.bat open` opens Android Studio.
- **Live reload**: start `server.bat`, then from `mobile/` run `npx cap run
  android --live-reload --host <LAN IP> --port 6273`. `serve.py` sends no CSP,
  so the policy is only checked in a built APK. The bridge and `/__mbrd/*` still
  work, because `MbrdWebViewClient` serves the shell's namespace for the dev
  server too.
- **Icons and splash**: `mobile/tools/make-icons.mjs` renders
  `web/assets/img/icon-maskable.svg` with `sharp` onto the paper background
  (`#faf8f3`, `manifest.json`'s `background_color`) and runs `@capacitor/assets`.
  The output is tracked.

### §5.13 What this does not fix

Carried from the old capacitor plan §9, because it is still true: **Capacitor
does not make pan and zoom faster.** The WebView is the renderer the browser
already uses. The app gains real files, open-with, a native FFmpeg and a store
that survives eviction. Framerate is separate, web-side work.

## §9 — Risks, to measure rather than assume

- **`h264_mediacodec` from a child process** (§5.9). Mixed reports. The probe
  handles a phone where it fails, but the Android speed-up rests on it.
- **The byte channel under a big board** (§5.4): 300 photographs, save and
  boot.
- **Accelerators with a hidden menu** on a frameless Windows window. FileAnalyser
  relies on it. Check each accelerator by hand on each system.
- **The platform-level `fileAssociations`** (§4.3).
- **Playwright and `WebContentsView`** (§4.1): whether `electronApp.windows()`
  lists the board's contents as a page.
- **The universal DMG with `sharp` and `onnxruntime-node`**: still open from the
  electron plan. Its fallback (two DMGs) now also changes the updater's macOS
  pattern and the release notes.
- **All files access on first run**: people refuse permission screens. "Not
  now" must leave a working app.
- **HEVC on the phone**: whether the Android WebView decodes a phone's own HEVC
  clips. If it does, `firstFrame` matters less there.
- **macOS by hand** (#35): there is no Mac. The DMG, Open Anyway, the ad-hoc
  signature and the macOS accelerators get CI's smoke test and nothing else
  until a user reports. The accelerator check stays open on macOS only.

## §10 — Later, not in this plan

- A Play flavour (#27): no feed, no `REQUEST_INSTALL_PACKAGES`, an AAB, the
  All files access declaration, the Data safety form.
- `native.decode` on Android through `ImageDecoder` (HEIF since Android 9), the

- A foreground service for long transcodes (`mediaProcessing`, Android 15).
- A folder of boards on the shelf as a tree, and cloud on the phone.
- Code signing (Windows, Apple Developer ID), which would also let macOS install
  its own updates.

## §11 — iOS, written down

Not planned (#29). The walls, from FileAnalyser's plan, so the next session
starts from them:

- **A Mac with Xcode** and a 99 USD a year Apple account.
- **No `fork`/`exec`**: FFmpeg must be an in-process library (xcframeworks with
  VideoToolbox), one job at a time, **with no crash isolation**. The LGPL build
  (#25) keeps this route open. A GPL build would close it.
- **The bridge** becomes a `WKUserScript` at document start, main frame only.
- **Page-to-native bytes**: a fetch PUT of `ArrayBuffer` chunks to a scheme
  handler. Never a `Blob` body (WebKit bug 197237). `WKScriptMessage` carries
  no `ArrayBuffer`.
- **The host stays `capacitor://localhost`**, the only way WebKit treats the
  scheme as secure. `isDev()` then reads it as dev, so each `isDev()` call site
  that matters needs a guard for a packaged shell (the bridge would need a
  `packaged` field, as FileAnalyser's has). Test `app.localhost` first.
- **No service worker** on the `capacitor:` scheme (Capacitor issue 7069,
  closed as not planned). mbrd does not register one in a shell anyway.
- **Storage**: no All files access. Boards would live in the app's Documents
  folder, shown in the Files app through `UIFileSharingEnabled` and
  `LSSupportsOpeningDocumentsInPlace`.
- App Store guideline 4.2 (more than a repackaged website) and 2.5.2 (no
  downloaded code). mbrd downloads no code, so 2.5.2 is not a question.
