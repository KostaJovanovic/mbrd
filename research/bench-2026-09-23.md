# A benchmark you can run on any device, 23 September 2026

**Status: partly done, 2026-09-24.** Built except the lab page; not yet run on a phone. See the last section.

The plan for a built-in benchmark: a fixed set of moves, zooms and animations,
run from inside the app, with the result saved as a JSON file that can be read,
compared and kept. Decided with the maintainer on 2026-09-23:

- the standard board is a special boot at `#bench`, never a board on the shelf;
- the way in is a row in the **Debug** fold of the System tab, not a public
  menu entry;
- this document is the whole plan, written down before any of it is built.

## Why

Every performance question this month was answered over adb with a throwaway
harness in `%TEMP%` - CDP over a forwarded socket, `dumpsys SurfaceFlinger`,
patches evaluated into the live page. It worked, and it found real things (the
root `:has()` restyle, `--iz` written on `#world`, the tile-memory blanking at
~80%, the culled cards that never died). But it only works with a cable, a
computer, and somebody who knows the harness; the numbers from the S10 and the
S22+ were taken on different boards; and nothing is left behind that the next
build can be held against.

A benchmark in the app turns that into: open the Debug fold, press a button,
wait two minutes, get a file. On any phone, with nobody at the other end.

## What a frame number is worth, and where it comes from

The first thing the harness taught is that the page does not know how fast the
screen is. On the S10, `requestAnimationFrame` ticked at ~60 while SurfaceFlinger
presented ~20: the WebView's compositor is driven by the app's own frames, and a
page can be told "next frame" long before the last one reached the glass. So a
benchmark that reports rAF alone reports a number that is right on a desktop and
flattering on exactly the device it matters on.

So every run records from two sources, and the file says which it had:

| source | where | what it gives |
| --- | --- | --- |
| **in the page** | everywhere | rAF gaps; long animation frames (`PerformanceObserver`, type `long-animation-frame`, Chromium 123+) with their script, style-and-layout and render split for every frame over 50 ms; the app's own counters - `cullProfile`, `viewStats()` (mounted cards, videos, decoded image MB); DOM size; JS heap where the engine reports one |
| **on the glass** | Android, through the bridge | per-frame timings from `FrameMetrics` on the activity's window - frames actually drawn, their durations, missed vsyncs, the refresh rate in force. The desktop needs none: Chromium's rAF on a desktop is paced by frames that are presented |

Why `FrameMetrics` and not SurfaceFlinger: it is readable by the app itself, no
adb, no permission. And it is the same stream `dumpsys gfxinfo` reads, which on
the S22+ matched SurfaceFlinger frame for frame (101/101 and 112/112 on the two
Feed runs) - the WebView draws on the window's render thread, so its frames are
the window's frames.

The web build gets the in-page half only, and the export marks every figure that
came from rAF as such. A web run is still worth having - it is the same app on
the same engine as the desktop - but it is never compared against an Android run
on frame rate.

Reading the gaps: the same way `perf/view-perf.ts` already does, because that
code already argues it out - the beat is the fast end of the run (5th
percentile), not the median, since these panels change their own refresh rate;
two beats is reported and not accused, three or more is a frame lost. The
benchmark reuses those functions rather than writing a second opinion of them.

## Two kinds of board

**The standard board**, for scores that compare across devices and across
builds. Opened as `index.html#bench`, a boot of its own in the way the 404 page
is one:

- no session restored, no autosave, no file in the boards folder, no timeline,
  no shelf row. `writeDocument()` already stands down for `isNotFoundBoard()`;
  the same guard is generalised to "a board that is not the user's", and a test
  holds that the bench board reaches none of `saveDocument()`, `autosave()` and
  the library;
- `freezePrefs()`, as `/patch` does, so a scenario that switches the grid or the
  quality off for an A/B cannot leave the switch thrown in the user's settings;
- generated, not shipped. A fixture `.mbrd` would be tens of megabytes in the
  repository and in every deploy. Instead a seeded generator (mulberry32, seed in
  the file) builds the same board on every device: ~120 cards - photographs at
  camera sizes (4000x3000 and 3000x4000, the decode that matters), a few
  screenshots, notes, swatches, stickers, two fences, a handful of connections.
  Eight base images are drawn once on an `OffscreenCanvas` and encoded, and each
  card's copy differs from its base by one byte in a JPEG comment segment - a
  distinct hash, a distinct asset and a distinct decode per card, for the cost
  of eight encodes. Generation is timed and reported, and happens before the
  clock starts;
- "Back to your board" is a navigation to `homePath()`, which boots normally.

**This board**, for the board somebody actually has - the only way to measure
a 400 MB board of real photographs, which is what found every problem this
month. Runs only scenarios that move the view: nothing is edited, nothing is
arranged, and the view and the board mode are put back at the end. Its file
carries a fingerprint (item count by type, total asset bytes) instead of a seed,
so two runs on the same board can be matched and a run on a different one is
never mistaken for a regression.

Both are measured relative to the board's own fit: every scenario starts from
`cmds.fit()` and is written in multiples of the fitted zoom and in fractions of
the fitted box, so a phone and a desktop cover the same part of the same board
whatever their window.

## The scenarios

Driven from inside the page - one `viewTo()` per frame from a rAF loop, never
synthetic input. `research/phone-zoom-2026-09-20.md` says why: input driven over
CDP puts the USB round trip in the gap being measured, and driven from the page
the runs repeat to the millisecond. Each scenario is: wait for idle (no long
task for a second, every mounted picture decoded), warm-up, a fixed duration,
the settle, and the record.

| # | scenario | what it is watching |
| --- | --- | --- |
| 1 | zoom sweep, fit -> 500% -> fit | the whole range, every rung and re-pin |
| 2 | zoom oscillation around 35% | the band that stuttered on the S10 |
| 3 | zoom out from 500% through 80-90% | where every card blanked for a few frames |
| 4 | pan along a fixed path at fit, 35% and 100% | culling, card rebuilds, the leak that was |
| 5 | pinch-shaped zoom about an off-centre point | the gesture's own shape |
| 6 | fling: a pan that decelerates as the real one does | the tail of a gesture |
| 7 | settle: stop, then time to the first idle frame | the 170-225 ms stall when motion ends |
| 8 | fit and recenter, animated | the app's own camera moves |
| 9 | Canvas -> Feed, Feed scroll, Feed -> Canvas | the mode switch and the native scroller |
| 10 | the star intro (`cleanTap` x7, `cleanEscape`) | the easter egg that froze for 100 ms |
| 11 | tour playback over three stops | |
| 12 | timeline scrub across the history | standard board only: it needs a history |
| 13 | sidebar open and closed, viewer open and closed | the chrome's own animations |
| 14 | rearrange | standard board only: it moves cards |

About two to three minutes in all. The overlay during a run is inert and opaque
to input, because a stray touch is a measurement of the touch.

**Switches per run**, so an A/B like the grid test of 2026-09-23 is one option
instead of an afternoon: quality level, whimsy tier, grid on/off, grain on/off,
shadows on/off, and the existing `mobilePerfFlags`. A run with switches thrown
says so in its file and in its file name.

**The leak check** cannot use the node counter the harness read, because a page
cannot force a collection and cannot see detached nodes. It uses a
`FinalizationRegistry` instead: every card `discard()` throws away is
registered, and the file reports how many were discarded and how many the
collector has since finalised. A long run allocates enough to collect several
times over; a count of finalised that stays at zero while discarded climbs is
the 2026-09-23 leak, visible from inside the page.

## The file

One JSON document per run, `mbrd-bench-<device>-<version>-<yyyymmdd-hhmm>.json`,
with a `schema` number so the compare tool can refuse what it does not know.

- **device** - user agent, platform (web, desktop, android) and shell version,
  `devicePixelRatio`, screen and window size, the refresh rate the run actually
  saw (from the beat) and, on Android, the one the display claims;
- **app** - version and commit, quality level and every quality flag, whimsy,
  the switches, the board mode;
- **board** - `standard` with its seed and generation time, or the fingerprint;
- **per scenario** - a summary (fps, beat, 2-beat and 3+-beat shares, p50, p95,
  p99, worst, long-frame count and their script / style-and-layout / render
  totals, settle time, cull cost, mounted cards and decoded MB after) and the
  frame series itself, delta-encoded in tenths of a millisecond so a whole run
  stays in the tens of kilobytes; on Android the `FrameMetrics` series beside it;
- **memory** - discarded and finalised cards, DOM size and heap before and after.

Where it goes: on the desktop and on Android, into `bench/` inside the boards
folder (`Documents/mbrd/bench/`), through the same file port the boards use; on
the web, a download. The result screen also has **Copy**, which puts the
one-line summary on the clipboard with `copyText()` from `view-perf.ts` - it
already knows how to do that on a phone with no secure context.

This is what makes it useful without a cable: somebody runs it on a phone,
sends the file, and it reads the same as one taken at the desk.

## The way in

- **Debug fold, System tab**: a row "Run benchmark", beside "Profile the frame".
  It asks one question - standard board or this board - and then either
  navigates to `#bench` or runs in place;
- the run: a full-screen overlay with the scenario name, a progress bar and
  Cancel; everything under it inert;
- the end: the summary table, **Save**, **Copy**, and on the standard board
  **Back to your board**;
- `mbrd.cmds.bench(opts)` and `#bench` for driving it from a console or over CDP,
  returning the same object the file holds.

`#bench` cannot collide with the profiler: `initPerfHash()` matches
`^#perf(\d)?$`, anchored.

## Comparing runs

- `tools/bench-compare.mjs a.json b.json [c.json ...]` - a table per scenario,
  side by side, with a change past the run-to-run noise marked. The noise is
  measured, not assumed: a scenario can be repeated (`repeat: 3`) and its spread
  is in the file. On the S22+ three identical zoom loops missed 19, 30 and 30
  vsyncs, so a single run is not a verdict and the tool says so;
- later, `web/lab-bench.html`, a fourth bench beside the pigment, sound and grime
  benches: drop several files on it and the frame series draw over each other.
  Same rules as the others - its own bundle (`npm run dev:bench`), `noindex`,
  absent from `sitemap.xml` and from `SHELL`.

## The Android half

A bridge key, `bench`, with `frames.start()` and `frames.stop()` returning the
series. `MbrdBench.java` adds a `Window.OnFrameMetricsAvailableListener` on
start and removes it on stop, collecting `TOTAL_DURATION`, `VSYNC_TIMESTAMP` and
the deadline per frame. The key is optional in `Bridge` (`platform/electron.ts`)
and the desktop's `preload.ts` answers `null`, so the page falls back to rAF;
`tests/mobile-bridge.test.js` holds the two bridges in step, and needs the new
key on both sides.

## Order of work

1. **The engine** - `perf/bench.ts`: scenarios, the idle wait, the recorders
   (rAF, long animation frames, app counters, the finalisation count), the JSON,
   "this board" mode, `mbrd.cmds.bench()`. Usable over CDP on day one, and
   testable in Node for everything that is not a frame: the file's shape, the
   delta encoding, the summary arithmetic, the seeded generator's output.
2. **The standard board** - the `#bench` boot, the guard that keeps it off the
   disk, the generator.
3. **The glass** - `MbrdBench.java`, the bridge key, the fallback.
4. **The way in** - the Debug row, the overlay, Save and Copy.
5. **Comparing** - `tools/bench-compare.mjs`, then the lab page.

## Things to keep in mind

- **A run must never write the user's board.** "This board" mode edits nothing;
  the standard board is guarded where `writeDocument()` is. Both get a test.
- **The overlay must not be the thing measured.** It updates between scenarios,
  never inside one - the same reason `view-perf.ts` skips the gap its HUD lands in.
- **Thermal state moves the numbers.** A phone that has just run the benchmark
  runs the next one slower. The file records how long the device had been idle
  before the run, and the compare tool warns when a run followed another within
  a few minutes.
- **The refresh rate is not ours.** Adaptive panels drop to 24 Hz when idle and
  take a frame or two to come back (every S22+ Feed run started with a 3- or
  5-beat gap). The warm-up exists for this; a scenario's first 150 ms are not
  scored.

## What was built - 24 September 2026

Steps 1 to 5 of the order of work, except the lab page. Where the build
differs from the plan above, this section is the one that is right.

| piece | where |
| --- | --- |
| frame arithmetic, series encoding, the byte tricks | `perf/frames.ts` (pure; `view-perf.ts` now reads its gaps through it) |
| the standard board | `perf/bench-board.ts` - `planStandardBoard()` is pure, `buildStandardBoard()` draws |
| the engine and the file | `perf/bench.ts` |
| the overlay, the Debug row's question, Save, Copy | `ui/bench-view.ts` |
| the guard | `notUsersBoard()` / `isBenchBoard()` in `onboarding.ts`, asked by `writeDocument()`, `compactDocument()`, `writeSnapshot()`, `stashCurrent()`, `shelveCurrent()`, `ensureCurrentOnShelf()`, `newBoard()`, `clearAllData()` |
| the glass | `MbrdBench.java`; the `bench` key in `Bridge`, `mbrd-bridge.ts` and `preload.ts` |
| comparing | `tools/bench-compare.mjs` |
| tests | `tests/bench.test.js`, `tests/bench-guard.test.js` |

Differences from the plan, each for a reason found while building it:

- **Every door that replaces the board is refused on `#bench`**, not only the
  writers. Opening a file, switching boards and New all go through
  `shelveCurrent()`, and on the bench board each of them ended with the arriving
  board autosaving into the user's session slot with nothing of theirs filed
  first. `shelveCurrent()` refuses with one toast; the way off is Back to your
  board.
- **"This board" refuses a board in the Feed layout, and all switches.** Leaving
  the Mobile profile drops the undo stack (`setBoardMode()` in `layout.ts`), so
  the Feed scenario is standard-only with rearrange and the timeline scrub; and a
  switch is a setting or a preference that would outlive the run.
- **Pan at fit, 35% and 100% are three scenarios** (`pan-fit`, `pan-35`,
  `pan-100`), so each has its own row to compare. Seventeen ids in all.
- **Scenarios 2 and 3 are written in absolute zooms** (35%, 500% to 50%), not
  in multiples of the fit: their point is where the app's own rungs sit.
- **Eight base photographs are four each way up**, plus four screenshots. The
  baked display and thumbnail copies are JPEG, not the app's WebP, because a
  comment segment is what makes each card's copy distinct and WebP has no slot a
  decoder is sure to skip. PNG screenshots get a tEXt chunk instead.
- **A card's asset id is not the digest of its bytes.** Hashing ~160 MB through
  the hand-written SHA-256 on a phone reached over the LAN would be most of the
  generation time; the ids are as distinct as the bytes, and nothing packs the
  board. Quality 0.82 keeps the board at ~160 MB; 0.9 made it 360 MB.
- **A scenario that never reaches the display's rate is counted in the run's
  beat.** The timeline scrub is slow on every frame, so its own 5th percentile is
  a slow frame and its drops read 75% one run and 0% the next. `rebeat()` recounts
  it in the median beat of the run and marks it `beatFrom: 'run'`.
- **Options ride the address** for the phone with no console:
  `#bench:quality=light,grid=off,repeat=3,only=zoom-sweep.pan-fit,seed=42`.
  `page.ts`'s `isBenchPage()` is anchored the way `initPerfHash()` is.
- **Run again reloads** rather than running twice on one board: the first run
  rearranged and scrubbed it.
- **The leak check works as argued**: a headless Edge run discarded 127 cards
  and the collector had taken all 127 by the end.
- **Long frames split three ways, and two overlap**: `renderMs` is the rendering
  steps before style, which include rAF callbacks, and those callbacks' time is
  in `scriptMs` too.

Not done: `web/lab-bench.html` (step 5's second half), and a run on a real
phone - the FrameMetrics path has been typechecked and not yet run. Measured so
far only in headless Edge, whose rAF runs unthrottled at ~240 Hz, so its frame
rates say that the engine works, not how fast anything is.
