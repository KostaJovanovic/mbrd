the five documents that were open here, all of which are now in `old/` with their
reasoning intact. Nothing was dropped in the move: every item below was checked
against the actual source on 2026-08-14, and the ones that turned out to be
already done are listed at the foot so nobody re-finds them.*

**Why one file instead of five.** The five documents that used to sit here were
each written in one sitting about one question, and each carried its own status

against itself that way. The reasoning behind each item is still worth reading
and is still where it was written; this file says *what* and *why it matters*,
and points at the document that says *how it was worked out*.

**How to read the pointers.** `file.ts:120` is a line number in the working tree
on 2026-08-14. They rot. The surrounding prose is written so the item is findable
without them.

## Things someone using the app would hit

### ~~U1 — The Join tool silently makes connections that never appear~~ — done

> **Closed in Batch 1.** `connectStep()` grew a `joinable` parameter rather than
> an import, so it stays pure and the caller answers the board question; a
> refused tap **keeps the standing pick** and raises a toast, and the refusal is
> checked *before* the same-card case, because a sticker cannot have been picked
> and so has no mind to change. Both file boundaries prune: `normalizeBoard()`
> holds connections to a `joinEnds` set built from the board and the bin, and
> `serializeBoard()` to the same set narrowed from `filed`.
>
> **One decision taken while doing it, and it is the interesting half.** The
> prune is `isJoinEnd()` alone, *not* `isRider()`, though the draw path refuses
> both. A rider is a note stuck to something at this moment; unstick it and the
> line is drawable again — so pruning riders would have deleted real connections
> the first time anybody opened a board with a stuck note on it. What the file
> boundary may drop is only what can never become valid, which is a property of
> the item's type. `tests/connections.test.js` asserts both halves.
>
> The original description follows, because the *why* is worth keeping.

Arm Join, tap a sticker — one of the little stars, arrows or pins — then tap a
photo. The app accepts the pair, writes it into the board, saves it, and draws
nothing. No error, no message, no mark on the sticker. The connection is real in
the file and invisible on screen forever, and the only way to find out is to read
the saved board.

Three separate pieces of code are each individually right and leave a hole
between them. The drawing code refuses to draw a line to a sticker on purpose,
and the reasoning is good: a sticker is already a remark *about* the card
underneath it, so a line from a star to a photograph is a line from a thing to
what it already says. The tapping code was simply never told that rule. The
selection path already gets this right — picking two things and choosing Connect
filters them properly — so this is two doors into one feature disagreeing about
what may go through, not a design gap.

**This is also a saved-file question, not only a screen one.** Boards saved
before this is fixed can already contain these pairs. They are state that can
never become valid, so dropping them when a board loads is the honest cleanup;
leaving them means those boards carry invisible cargo forever.

*Where:* `web/assets/js/ui/toolbar.ts:145` (`connectStep`, four lines, takes any
two distinct ids), the rule at `web/assets/js/board-model.ts` (`isJoinEnd`), and
the drawing side at `web/assets/js/canvas/web.ts`. The fix belongs in
`connectStep` where a unit test can reach it. An accidental tap on a sticker must
not throw away the pick you were already holding.

### U2 — the original entry

Hover Arrange and the panel that comes down sticks out about 28 pixels past the
right-hand end of the toolbar.

This is worse than being merely off-centre, because the panel is deliberately
styled to look like *the underside of the bar* — it drops its top border and its
top corners so it reads as part of the toolbar rather than as a second object
that has landed on it. That illusion only works while the panel is over the bar.
Past the end, the squared-off top corner is a cut edge floating over the board,
which is exactly the shape of a rendering mistake.

The cause is one line: the panel is kept inside the *window*, and the window is
nowhere near. The information needed is already in hand one moment earlier — the
code that positions the flyout already measures the toolbar and uses its bottom
edge, then throws away its left and right.

Note and Colour sit mid-bar so they do not show it today, but the rule is wrong
for all of them, and a fourth button added anywhere right of centre would show it
too. **Clamp, don't flip** — a panel that jumped to the other side of its button
would leave the pointer outside itself and close as you moved towards it.

*Where:* `web/assets/js/ui/menu.ts:1017`. There is no `bounds` option anywhere
today; adding one is the shape of the fix.

### U3 — The sticker panel opens slightly scrolled

Open the sticker pad and it starts about ten pixels down, which slices the tops
off the letters of the first heading. It reads as a font problem and is a scroll
problem, which is why it is worth naming.

The cause is the *remember which shelf you were on* line at the end of the build.
It scrolls to the category you used last — and on a fresh window that category is
the first one, so it scrolls to something already at the top and lands slightly
past it. There is no focus call and nothing else in the module touches scrolling,
so this line is certainly the mechanism.

The exact ten pixels does **not** fall out of the stylesheet values, so one of
the two numbers is wrong and it wants a real browser before anyone quotes it.
That does not change the fix.

The fix is a guard, not a reset: leave the scroll alone when the target is
already the first thing in the list. Setting the scroll to zero unconditionally
would fix the symptom by deleting the feature — and would be wrong the moment
somebody has a favourite sticker, because the Favourites shelf then sits above
everything and a real scroll is correct.

*Where:* the last two lines of the build in
`web/assets/js/ui/sticker-window.ts`.

### U4 — Two menu rows claim the same shortcut

Right-click a photo. **Open** and **Zoom to it** both print `dbl-click` in the
shortcut column. Only Open is true — double-clicking a photograph opens the
viewer. A menu that advertises the same key twice teaches the wrong thing about
both rows. Either drop the shortcut from Zoom when the item is viewable, or drop
it outright and let Open own the gesture.

*Where:* `web/assets/js/ui/menu.ts:473` (Open) and `:625` (Zoom).

### ~~U5 — A cut-out PNG still gets a card drawn round it~~ — done

> **Closed in Batch 3b.** `meta.bare` through `setItemBare()`, images only,
> stored only when true. `writeFit()` puts `data-bare` on, `items.css` takes the
> paper, the hover ring and the far-zoom edge away, and `canvas/items.ts` builds
> no shadow twin — `NO_TWIN` became `noTwin(item)`, because a cut-out is on that
> list for word-for-word the reason the four types are: the twin is a rounded
> rectangle at the item box and there is no rectangle. The menu row is **No
> card**, a tick under the two fit rows. `ui/snapshot.ts` skips the shadow, the
> rounded clip *and* the contain-band, that last one being the trap — the band
> is exactly the empty rectangle the flag exists to remove.
>
> **The guess reads pixels, not the header**, as this entry insisted. It rides
> on the thumbnail pass, which after S8 has a ~100px bitmap already drawn to a
> canvas: the outer ring is sampled once, and a picture whose ring is at least
> two-thirds transparent *and* which has something solid down its middle is
> called a cut-out. Two-thirds rather than all, because a logo often bleeds to
> one edge; the solid test refuses a wholly transparent image, which is not a
> cut-out but an accident. Only for an image that is its own thumbnail source —
> a preview pulled out of a HEIC or a frame grabbed from a clip is a different
> picture and never a cut-out.
>
> **The open question was answered: a cut-out leans, and carries no tape.** The
> lean is `.item`'s `rotate` and is untouched by any of the rules above, so it
> still follows the whimsy axis. Tape is drawn on the card, and there is no card.
>
> The original description follows.

Drop in a logo, a leaf, an arrow — any PNG or WebP saved with a transparent
background — and it lands on a card: paper behind it, a hairline round it, a drop
shadow under it. The shape was cut out precisely so it would sit on the board
rather than in a box, and the box is drawn round its **bounding rectangle**, which
for a cut-out is mostly empty. The result is a frame round nothing with a picture
somewhere inside it, and there is currently no way to turn it off.

The app already knows how to draw an item with no card at all — that is what every
sticker is — so this is not a new capability. It is a flag that says *this one is a
shape, not a photograph*, and the shape of that flag already exists too: one meta
key, written through `patchMeta` with a validator, exactly as `fit` and `adjust`
are, plus a row in the item menu and a class the stylesheet answers.

**The interesting half is the default**, because a toggle nobody finds is a toggle
nobody has. Two ways to guess:

- **Read the header.** A PNG declares its colour type, and a WebP declares alpha in
  its `VP8X` flags or its `VP8L` header — cheap, no decode, and *wrong in the
  direction that hurts*. Plenty of ordinary rectangular screenshots are saved as
  PNG-32 with a fully opaque alpha channel, and the header cannot tell those from a
  cut-out. Guessing from it would strip the card off a large share of the
  photographs on a board.
- **Look at the pixels.** The import path already decodes each image to measure it
  (see **S8**, which wants that decode reduced rather than multiplied), so sampling
  the border of a bitmap that is already in hand costs almost nothing. An image
  whose outer ring is largely transparent is a cut-out; one that declares alpha and
  uses none is a photograph. This is the honest test and it should be the one.

Either way the guess is a **default and not a verdict** — the menu row stays, and
whatever the person chooses wins and is what gets saved.

**Three things not to break while doing it.**

- **Keep the box, drop only the paint.** Hit-testing, the marquee, the selection
  ring and the resize grips all measure the same rectangle. An item you cannot
  select or resize is a worse bug than the one being fixed.
- **The export has to agree.** `ui/snapshot.ts` paints a card rectangle and a
  shadow per item on its own, in its own renderer, and it already skips both for
  stickers and fences. A chromeless image must join that exemption, or the PDF
  grows a border the screen does not have — and that discrepancy would only ever be
  noticed by whoever prints one.
- **The lean is not the card.** At Softish a card can tilt and can carry tape. A
  cut-out should still be allowed to lean, but tape over nothing is a piece of tape
  floating in the air, so the two are separate questions and the second is
  genuinely open.

*Where:* `setItemFit` in `web/assets/js/state.ts` is the closest existing pattern
to copy; the card's own paint is in `web/assets/css/item-chrome.css` (the hairline
is an inset `box-shadow` using `--item-border`); the class goes on in
`web/assets/js/canvas/item-dom.ts` beside `writeAdjust`; the menu row belongs with
the other per-item writes in `web/assets/js/commands/item-meta.ts`; and the decode
this wants to borrow is in `web/assets/js/import/`.

## Features that are not started

### L1 — Share a board by sending someone a link

None of this exists. The proposal is in `old/share-link-2026-08-14.md` and it
is mostly a record of what was ruled out, which is the reason to read it before
proposing anything:

- **Peer-to-peer cannot work for a link.** Both people would have to have the tab
  open at the same moment, which is not what a link is.
- **A link carrying the board inside it cannot hold one photograph**, and in this
  app a photograph is the whole payload.

What survives is the sender's own cloud storage: the board is uploaded to *your*
Dropbox and the link points there, with Google Drive and OneDrive behind the same
seam later. iCloud is never — that one is genuinely impossible rather than merely
expensive.

Two things to know before starting. There is already a `shareBoard()` and it
means something else — the operating system's share sheet — so the two need
different names in the panel or people will pick the wrong one. And the cost
section is the part with teeth: this adds a host to `web/_headers` and ends the
app's current claim that it makes no outbound request to anyone.

### L5 — Interface sounds

None of this exists. The design is in `cuelume-2026-08-15.md`, which is at this
level rather than in `old/` because the work is open, and which has an end
written into it: it goes down on the commit that ships the feature.

The app makes no sound of its own today — `canvas/audio.ts` plays the board's
*content*, which is a different thing. The proposal takes the engine half of
Cuelume (MIT, seventeen sounds synthesized live, no audio files, no dependencies)
into `web/assets/js/cuelume/` at the bottom of the graph beside `quality.ts`, and
throws its binder away: `bind()` is four capture-phase listeners on `document`
plus a `data-cuelume-*` markup contract, and both are things `CLAUDE.md` already
has a rule against. Call sites name one of eight cues, the whimsy tier picks the
recipe, and the sounds land through `cmds` and `notify.ts` rather than through
any new listener.

Three things to know before starting. **The whimsy axis carries it as character
rather than as volume** — same number of cues at every stop, warmer at Softish
and more synthetic at Harsh — which is what gives all seventeen recipes a job.
**The sound assignment is not settled and is not settleable by reading**, which
is why a bench page is in the same commit; this is
`old/feedback-plan-2026-08-14.md`'s lesson applied to the ear. And **a live
`AudioContext` can interrupt music playing in another app on a phone**: the
answer is `navigator.audioSession.type = 'ambient'`, it is the one claim in the
document that no test can make, and it wants a real device.

### ~~L2 — Export a style tile, not a picture of the board~~ — built

> **Batch 10, and the three open questions are answered *in `ui/snapshot.ts`***
> so the next person argues with a decision rather than rediscovering a gap:
>
> - **Whose colours** — the board's own current palette, off the live tokens,
>   not re-derived from the pictures. A style tile documents the look the board
>   *has*; where that look was extracted these are those colours anyway, and
>   where it was chosen by hand, re-deriving would print a palette the board is
>   not wearing.
> - **Which pictures** — the selection when there is one, else the largest few
>   by area. **Not the tour**, which was the tempting answer: a tour is genuinely
>   curated, but keying the export to it makes the same command produce a
>   different kind of document on a board that happens not to have one, silently.
>   One rule was worth a test: a selection of three *notes* falls through to the
>   board, because that is not a curation of pictures and honouring it literally
>   would export a tile with no images on it.
> - **Does it follow the whimsy dial** — yes, and the counter-argument is real.
>   The subject of this document *is* the look, so a tile that held still while
>   the board it describes moved would be documenting one thing and looking like
>   another.
>
> Painted box by box, as the entry insisted: a DOM layout rasterised through
> `foreignObject` taints the canvas, which is the whole reason this app
> composites in Canvas 2D. It reuses the board export's context, `roundRect()`
> and `buildPdf()` — a different layout fed to the painter that already exists,
> not a second renderer. Two `cmds` entries beside `exportImage`/`exportPdf`, and
> the artefact name gains a suffix so a tile cannot overwrite a picture of the
> same board.

The board exports two ways today, and both of them answer the same question:
*show me the board*. A PNG and a PDF are photographs of the surface, and a
photograph of a moodboard is only readable by somebody who was in the room when it
was made. What gets pasted into a deck, sent to a printer or pinned next to a
mock-up is the other document — **the summary**: the palette as swatches with their
hex values, the typefaces actually in use, three or four of the images, the board's
title and the date. A style tile.

Nothing about this is a second renderer. `ui/snapshot.ts` already owns the world →
canvas projection, the text drawing and the five-object PDF container, and the
pigment extractor already produces the colours. The tile is a different *layout* fed
to the same painter.

**One constraint decides the implementation before anything else does.** It cannot
be laid out in DOM and rasterised. Putting an `<img>` inside a `foreignObject`
taints the canvas, which is the entire reason this app composites in Canvas 2D
rather than serialising the page — so a style tile has to be **painted**, box by
box, in the same renderer as the board export. That is not a hardship, but it does
mean the tile's design has to be expressible as rectangles and text runs, and a
design handed over as HTML would have to be re-drawn rather than reused.

**Three questions left open on purpose**, because each is a taste decision and
guessing at them here would only make it look like they had been settled:

- **Whose colours?** Every image on the board, the current selection, or the tour if
  there is one. The tour is the only one of the three that is *curated* — somebody
  chose those cards and put them in an order — which is an argument for it, but it
  makes the export silently different on a board that has no tour.
- **Which images, and how many?** Largest, most recent, selected, or the first few
  tour stops. Same reasoning, same catch.
- **Does it follow the whimsy dial?** `/patch` does, and that is the established
  answer in this repo. Against it: a deliverable somebody sends to a client should
  probably look the same next week, and a slider that restyles it means two exports
  of one board are not the same document.

*Where:* `web/assets/js/ui/snapshot.ts` for the painter and the PDF writer, the
pigment modules for the colours, and `web/assets/js/commands/file.ts` for the
command — it is a `cmds` entry beside the existing exports, not a new door.

### ~~L3 — A durable timeline inside the `.mbrd`~~ — built

> **Batch 9. This is a `.mbrd` schema change** — `board.versions`, documented in
> `research/docs/mbrd-format.md`, which was edited in the same commit because a
> specification that follows the format is a specification that is wrong for a
> while.
>
> **The blocking decision, and the evidence that settled it.** The choice was
> framed as "history is documented as losable by old builds" *or* "the format
> version moves so an old build declines the file". The second turns out not to
> exist: older builds do not decline a newer file — the check is
> `if (Number(manifest.version) > FORMAT_VERSION) console.warn(…)` and the load
> continues. Bumping the number changes a console message and protects nothing,
> while costing every existing reader a warning about a file it can open fine.
> So: **documented as losable**, and the note in the spec also says what a future
> field would have to do instead (change `format`, which readers *do* refuse).
>
> **The pruning was the work, as predicted.** There are now three classes of
> reference and all three had to learn at once: `packBoard`, the autosave sweep
> in `storage/session.ts`, and L4's orphan report. The packer's missing-asset
> refusal reaches inside versions too — without that, a board would pack
> *successfully* with a version in it that restores to holes where the
> photographs were. `tests/mbrd.test.js` asserts both directions.
>
> Cadence is a ring of 8 automatic plus up to 32 named, trimmed **separately**;
> automatic versions hang off the existing `autosaved` signal on a ten-minute
> gate rather than a new timer, so they inherit its "did a person actually change
> something" answer for free. Restoring is one undoable command through
> `commit()` — not `loadBoard()`, which clears the history and would have deleted
> the undo entry it had just made. A version's document never contains versions,
> or a board left open would grow its own history exponentially inside itself.

### ~~L4 — An inventory panel: what is in this board, and what it weighs~~ — built

> **Batch 8.** `ui/inventory.ts` and a sheet beside the credits one, opened from
> System — *What is in this board*, directly above Optimize, which is the point:
> the optimizer works and was a button nobody had a reason to press.
>
> Nothing in it decodes an image and nothing re-reads an original — sizes come
> off the stored blobs, which is the rule that keeps it instant on the two
> thousand-card boards where the question actually gets asked.
>
> **It reports orphans and does not offer to delete them**, on the argument that
> a *remove unused* button written against a two-class reference union would
> become a data-loss bug the day a third class arrived. The third class then
> arrived in the very next batch. The button would have been wrong for exactly
> the predicted reason; the report was updated to count versions in the same
> commit that created them.

Undo lives in memory and dies at the refresh. Nothing anywhere remembers what a
board looked like yesterday, so the only recovery from *I have spent an hour making
this worse* is to have thought to save a copy beforehand.

**The reason this is affordable is worth stating first, because it is not obvious.**
A `.mbrd` is a ZIP, assets are stored as their own entries and referenced by hash,
and `board.json` is small. So a stored version is one more JSON entry and **does not
duplicate a single photograph** — twenty versions of a 40 MB board cost twenty
copies of a text file, not twenty copies of the images. Additional ZIP entries are
also the most additive change the format can take.

**And the reason it is nevertheless large is the pruning.** The moment old versions
exist, an asset that the live board no longer uses may still be the only thing an
older version points at. Anything that drops unreferenced assets at pack time — and
anything added later that does, including **L4** — has to count the versions as
references or restoring one shows holes where the pictures were. That is a
correctness problem, not a size one, and it is the whole of the work.

**The second trap is the one additive changes always spring.** An older build
opening a newer file will not understand the extra entries, which is fine, and will
then **write the file back without them**, which is not. Whether that is acceptable
is a decision to take deliberately — either the history is documented as losable by
old builds, or the format version moves so that an old build declines the file
instead of quietly flattening it. See `research/docs/mbrd-format.md`, which has to
be edited either way: **this is the only one of the four new items that changes what
a `.mbrd` is.**

**Cadence, and a recommendation.** Automatic snapshots and named ones answer
different questions — *what did I just break* and *the version I showed the client*
— so do both: a shallow automatic ring that evicts, plus explicit marks that never
do. Restoring should arrive as **one undoable command** rather than as a mutation
that replaces the board, so that landing on the wrong version is itself undoable.

*Where:* `packBoard` / `unpackBoard` in `web/assets/js/storage/mbrd.ts`,
`web/assets/js/storage/zip.ts`, `web/assets/js/history.ts` for the restore command,
and `research/docs/mbrd-format.md` for the entry that makes it real.

### L4 — An inventory panel: what is in this board, and what it weighs

`.mbrd` files get heavy, and there is nothing in the app that will say why. A sheet
that lists the item counts by kind, the total weight, the ten largest assets and
anything stored but no longer referenced would answer it in one look.

**The second reason to want it is the optimizer.** It exists, it works, and it is a
button you have to already know about — there is nowhere in the app that gives you a
reason to press it. *This photograph is 12 MB* is that reason, and the inventory is
where it should be offered from.

It is a **report, not a setting**, so it belongs as a sheet — the Credits sheet is
the precedent — and not as a section in `ui/settings-schema.ts`, which is for things
that change the app rather than describe it.

**Two things to get right.** Sizes come from the stored blobs, never from re-reading
the originals, and **nothing in the panel may decode an image**: a board with two
thousand cards should open this instantly, and a panel that measures by decoding
would stall the tab exactly on the boards where the question is being asked.

**And one dependency that only exists if both are built.** "Unreferenced" means
*not pointed at by the live board* today, and **L3 would change that definition** —
a stored version can legitimately hold the only reference to an asset. If the
inventory ships first, with the naive definition, and grows a *remove unused* action,
then L3 arriving afterwards turns that action into a data-loss bug in a file people
keep. Whichever is built second has to be built knowing about the first; if this one
goes first, the safe move is to **report** the orphans and not offer to delete them.

*Where:* `web/assets/js/storage/assets.ts` knows the blobs and their sizes,
`web/assets/js/optimize/` is what the panel should be able to hand off to, and the
sheet itself belongs beside the existing ones in `web/assets/js/ui/`.

## Finishing the design system

### V1 — Sort out the text sizes

The app has a whimsy slider, and nearly everything the eye can see — corners,
colours, timings — is a named value that moves with it. Text sizes mostly are
too. Twenty-seven places write a raw pixel number instead.

**The work is not "replace 27 numbers with names."** Some of those numbers are
correct: a large decorative glyph, a masthead, or world-space text that already
scales with its card should not follow the type scale, and forcing it to would
make things worse. The job is to sort all twenty-seven into three piles — on the
scale, deliberately off it, and never looked at — then fix only the third pile
and write one line of explanation above each of the second. **For the second pile
the comment is the deliverable, not the token.**

Exactly one has been sorted so far, in `web/assets/css/ghosts.css:145`, and it is
the pattern for the rest.

Nothing visible changes. What it buys is that the design system stops rotting,
and that the next person can tell an accident from a decision without asking.

*One counting note, because it has already caused one wrong conclusion:* count
bare pixel values. Counting every text size that does not use a named value gives
55, and that number sweeps in exactly the relative and clamped values this item
exists to protect.

## The big one

### T1 — An editable timeline

Every change you make becomes a step on a strip along the bottom of the screen.
You can go back to any of them, and you can **change one in the past and have
everything after it rebuild on top of it** — the way a CAD program's history
works. It is stored in the board file, so it survives closing the tab. Whether it
*travels* is asked at export, and the box is off by default: the history records
everything that was tried and thrown away, and that is not something to send
somebody by accident.

It **replaces the stored half of undo**: `Ctrl+Z` moves the marker back rather
than running a separate stack, so undo starts surviving a refresh. It does not
replace the feel of undo — a run of nudges is one step on the strip but still
unwinds one nudge at a time while you are in the session that made it.

It also **absorbs saved versions**, which become named steps rather than a second
list doing the same job.

**The design is in `old/timeline-2026-08-14.md`, and it is the whole of the
thinking** — the eleven decisions taken, why the app is unusually well suited to
it in two places, the one thing that makes it shippable rather than a six-month
rewrite, how Fusion 360 solves the same storage problem and why the answer
carries over, and a phase plan with a one-paragraph summary at its head. Read
*What this costs* at the foot of it before starting: phase 1 alone is larger than
everything done on 2026-08-14 put together, and phase 2 replaces the undo system
in a single commit.

**All five phases are built** (2026-08-14). Every change is recorded, the history
travels in the file, export asks before it goes with it, runs collapse, undo
survives a refresh, the strip opens from System → History, three commands can be
edited in the past, and the trim offer appears past 2 MB. The design's *All five
phases, as built* section says where it diverged from the plan and why, and
lists the two structural bugs the tests caught.

**What is left, and none of it is blocking:** converting more commands from
sealed to editable, one at a time, forever; a saved version ceasing to carry its
own copy of the board; reordering and *insert here*; and the trap for whoever
writes the next commit site, which is written at the foot of the design.

**The one honest caveat, stated there and worth repeating here:** most steps in
this app are absolute — *put this card here* — so editing an earlier step often
will not change a later one. The steps where it genuinely ripples are the
computed ones (arrange, align, distribute, auto-connect), and converting those
first is what decides whether the feature looks alive or looks broken.
