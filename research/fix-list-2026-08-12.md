## Phase 1 — five diagnosed defects

Each of these has a cause located in the source. They are independent of each
other and of everything below, and each is one file.

### 1.1 The note composer draws the note at 1× against the left edge (#11)

**Cause, confirmed.** `placeBox()` in `canvas/items.js:1418` writes
`el.style.transform = itemTransform(item)` — an *inline* style. `itemTransform()`
(`canvas/items.js:1506`) almost always returns a non-empty string, because
`deviceSnap()` returns a correction at any zoom and any device pixel ratio, and a
rotated item returns a `rotate()` instead. The composer's rule
(`overlays.css:1360`)

```css
#compose-mount .item { transform: scale(var(--sheet-zoom)); transform-origin: 0 0; }
```

is a stylesheet declaration and loses to the inline one. So the sheet never
scales: `openComposer()` reserves a mount of `it.w * SHEET_ZOOM` (240px for a
default note) and the card inside it draws at its natural 120px, hard against the
mount's left edge. That is exactly the reported symptom — off-centre, to the
left — and it also means the note is drawn at half the size it is meant to be.

`resnap()` (`canvas/items.js:1523`) walks every mounted node and rewrites the
same property whenever the view settles, so anything that only clears the
transform once would be undone mid-edit.

**Fix.** Two halves, both needed:

1. In `openComposer()` (`canvas/notes.js:686`), after `mount.append(node)`, stash
   `node.style.transform` and clear it; restore it in the teardown branch that
   puts the node back into the world layer, right before the `is-landing` class
   goes on.
2. Guard `resnap()`: skip a node whose `parentElement` is not `worldEl`. This is
   cheap (one property read per mounted node) and states the real rule — the
   device-pixel snap is a correction against the *board's* transform, and a node
   that has been lifted out of the world layer is not on that transform at all.

Prefer this over `!important` in the stylesheet: the invariant is "an item
outside the world layer does not wear world geometry", and that belongs in the
module that writes the geometry.

**Check.** Add a note at a fractional zoom (e.g. 87%) and at 100%; both must draw
centred at 2×. Rotate a note, then edit it: the rotation must not follow it into
the dialog, and must come back after.

### 1.2 The mobile Add button paints a square corner when pressed (#12)

**Cause, confirmed.** The desktop `#toolbar` (`chrome.css:108`) clips its
segments to its own `--leaf` radius with `overflow: hidden`. The mobile block
(`mobile.css:932`) sets `overflow: visible`, necessarily — the tools tier hangs
outside the container. `#toolbar #toolbar-toggle` (`mobile.css:947`) has no radius
of its own, and `#toolbar button:active` paints `var(--paper-3)` behind it, so the
press paints an unclipped rectangle over a rounded bar.

**Fix.** One declaration in the mobile block:

```css
#toolbar #toolbar-toggle { border-radius: inherit; }
```

`inherit` rather than a repeat of `var(--leaf)`: the toggle is the only child and
fills the bar exactly, so its corner *is* the bar's corner, and the radius token
is now driven by the Corner radius slider (see `visual-audit-2026-08-12.md`) —
a second literal would drift the day that moves.

**Check.** Press and hold Add at each of the three whimsy stops and at both ends
of the corner-radius slider.

### 1.3 The Feed has no paper tooth (#5)

**Cause, confirmed.** Grain is one image on two surfaces (`base.css:181`):
`#grain`, a full-bleed fixed layer for Desktop, and `#mobile-board-frame::after`,
which is the *world-space* Mobile sheet. `base.css:415` takes `#grain` down under
`data-board-mode="mobile"` — correct, since on Mobile the paper is the sheet and
not the window. But the Mobile board is no longer that world-space sheet: it is
the Feed (`ui/feed.js`, `mobile.css:88`), the canvas is `visibility: hidden`, and
`.feed-sheet` carries a flat `color-mix(in srgb, var(--accent) 6%, #fff)` with no
texture layer at all. The tooth was left behind on the surface the Feed replaced.

**Fix.** Give `.feed-sheet` the same pseudo-element the world-space frame has, and
join it to the existing shared block rather than writing a second texture:

- add `.feed-sheet::before` to the `#grain, #mobile-board-frame::after` selector
  list in `base.css:181`;
- in `mobile.css`, add `position: relative` to `.feed-sheet` and a
  `.feed-sheet::before { content: ""; position: absolute; inset: 0;
  border-radius: inherit; }`.

`::before`, so it paints before the tiles and its `mix-blend-mode: multiply`
blends against the sheet's own fill rather than darkening the photographs on it.
`inset: 0` covers the whole scroll height, which is what makes the grain travel
with the board — the Feed has no zoom, so the `--grain-pos` / `--grain-tile`
properties `canvas/grain.js` writes are simply not needed here and the 512px
fallback in the shared block is the whole answer.

**Check.** Both whimsy extremes; a very long board (the grain must not tile
visibly at the join between screens); and the Playlist lens, which must be
unaffected — `.feed-sheet` is shared, so decide deliberately whether the Playlist
wants it too. It should: it is the same sheet of paper.

### 1.4 The sticker window should get out of the way instantly (#9)

**Cause.** By design, not by accident: `startTileDrag()` adds `is-dragging` at
`ui/sticker-window.js:368`, and `overlays.css:1837` fades the window to 55%. The
report is that a fade to 55% is not enough — the window should go.

**Fix.** Replace the class add at line 368 with `closeStickerWindow()`. Three
things make this safe, and all three should be checked rather than assumed:

- the pointer listeners are on `window`, not on the tile
  (`ui/sticker-window.js:396`), so the drag survives its own tile being removed;
- `closeStickerWindow()` (`:151`) plays a slide-out and only removes the element
  on `transitionend` or after a 500ms backstop, so the tile is still in the
  document when `releasePointerCapture()` is called on it at drag end. If that
  turns out to be racy under a fast flick, wrap the release in a `try`;
- `closeStickerWindow()` calls `disarm()`, which the drag branch already does one
  line above.

The `win?.classList.remove('is-dragging')` at `:381` becomes a no-op (`win` is
already null) and comes out with it. The `.sticker-window.is-dragging` rule in
`overlays.css` goes too — leaving a rule nothing sets is the sort of thing the
next reader spends ten minutes on.

**Check.** Drag out a shape and drop it on the board; drag one and release off the
board (nothing placed, window stays shut); tap a tile without moving (must still
*arm* the shape, and the window must stay open for that gesture — the close
belongs to the slop threshold being crossed, not to the press).

### 1.5 Debug goes into a fold (#6)

**Cause.** `ui/settings-schema.js:498` gives Debug a plain `title`, so its three
buttons are always on screen at the foot of the System tab.

**Fix.** The panel already has exactly one mechanism for this and the `keys`
section two entries above uses it (`:491`): a section with `fold` and no `title`
renders as a `<details>` whose `<summary>` stands where the heading would
(`buildFold()`, `ui/panel.js:166`, and the `is-head` class it adds). So:

```js
id: 'debug', tab: 'system', fold: 'Debug', foldId: 'debug-fold',
```

and mark each of the three buttons `advanced: true` — `buildSection()` lifts only
`advanced` controls into the fold.

**Check.** The fold is closed on arrival; `cmds.debugGrips` / `cmds.debugWheel`
still find their buttons by `[data-cmd]` to write `aria-pressed`
(`commands.js:870`, `:886`) — they query the document, so a collapsed `<details>`
still holds them and this is fine, but the `#grips` URL route should be opened
once to confirm it.

### 1.6 The pen rides the whole Feed instead of the masthead (#14)

**Cause, confirmed, and it is the same class as 1.3.** `paintButton()`
(`ui/mobile-header.js:770`) gates the pen on the layout and the lens only:

```js
const visible = board.layoutMode === 'mobile' && lens !== 'playlist';
```

Its own comment says what it used to be — "the world-space canvas is dormant
behind the Feed, so its scroll stop (`atMobileTop`) no longer tracks the
masthead". The gate was dropped on the migration to the Feed and nothing took its
place, so a pen that edits the board's title page now floats over a wall of
photographs a thousand pixels below that page. The latch under it (`buttonShown`,
`:768`) still carries a comment about the answer changing "exactly twice in a
scroll — on leaving the top stop and on returning to it", describing behaviour
the code no longer has.

**Fix.** Restore the third condition, sourced from the Feed rather than from the
dormant viewport:

- in `ui/feed.js`, an `IntersectionObserver` on the `.feed-masthead` element,
  announcing on the bus when it enters and leaves the scroller. An observer and
  not the existing `scroll` listener: the answer changes twice in a scroll and an
  observer is the browser saying so, where a scroll handler is this module asking
  on every frame — which is the exact cost the `buttonShown` latch was added to
  avoid;
- in `ui/mobile-header.js`, a module-level `mastheadOnScreen` set from that
  event and ANDed into `visible`. The latch, the fade and the `aria-hidden` all
  work unchanged — `#mobile-header-edit-btn[hidden]` (`sidebar.css:71`) already
  carries a 0.3s opacity transition, so this comes and goes rather than blinking.

Default it to `true`, so a board that has not scrolled yet — and any path where
the observer never fires — shows the pen rather than hiding it.

**Check.** Scroll down: the pen fades out as the masthead leaves. Scroll back:
it returns. Switch to the Playlist and back. Open the header panel while it is
visible and scroll behind it (`#header-panel.is-open ~ #mobile-header-edit-btn`
at `sidebar.css:219` already zeroes it, and the two rules must not fight).
`#mobile-find-btn` beside it is deliberately *not* gated this way — it rides the
whole Mobile board on either lens (`paintFind()`, `:791`) — and stays put.

## Phase 2 — structural

### 2.1 The two layouts are not actually separate (#8)

Three symptoms, one cause and one aggravation.

**Cause A — the fallback in `completeLayout()`.** `layout.js:572`:

```js
let geometry = map.get(it.id);
if (!geometry) geometry = geometryOf(it);
```

An item with no geometry in the Desktop profile inherits the *live* item, and at
the moment `setBoardMode('desktop')` runs (`layout.js:648`) the live item is
whatever Mobile left it as: fitted to the strip width by `fitMobile()` and packed
into the column. That is the whole of "coming to Desktop for the first time keeps
the two-column vertical layout". The Mobile branch above it does not have this
problem — it packs missing items with `placeMobileItems()`.

**Cause B — ghosts are seeded into one layout only.** `ensureGhostCards()`
(`state.js:841`) forks on `board.layoutMode` and sizes the hint cards against the
column when Mobile is live (`width * g.mspan`, `g.mrows * step`). They are never
seeded for the other profile, so a switch runs them through Cause A and they
arrive on Desktop at column width, in column positions. Ghosts are never
serialised, so nothing else repairs them.

**Fix A.** Give the Desktop branch of `completeLayout()` the same shape the Mobile
branch has — known items keep their geometry, missing ones are *placed*:

```js
const known = [], missing = [];
for (const it of board.items) (map.get(it.id) ? known : missing).push(it);
```

and run `missing` through `arrange(missing, { name: 'masonry', spacing, center,
cellStep, obstacles: known })` from `arrange/arrangements.js:82`, in
`mobileOrder(missing, { name: board.arrangements.mobile })` order.

Masonry is the right catalogue entry and not an approximation: `LAYOUTS.masonry`
(`arrangements.js:307`) packs shortest-column-first, which is the identical rule
`feedMasonry()` (`ui/feed.js:422`) uses for the Feed. Feeding it the Mobile
reading order therefore reproduces the Feed's own sequence as a rectangular block
— which is what was asked for — rather than inventing a second packer.

`obstacles: known` is what keeps this honest on a board that is only *partly*
new: `arrange()` pushes newcomers clear of boxes already placed
(`avoidObstacles()`, `:118`) and leaves everything with saved geometry untouched.
So the common case — one file dropped on Mobile, then a switch to Desktop —
appends one card near the block instead of re-flowing the board, and the
first-ever switch, where `known` is empty, lays the whole board out as a masonry.

Sizes are a separate question and the answer is to leave them alone. `fitMobile()`
shrank widths to the strip on the way in and there is no record of what they were
before, because a board made on a phone never had a Desktop size. Re-placing
x/y and keeping w/h is the only thing that can be said truthfully.

**Fix B.** Ghosts are ephemeral, so re-mint them rather than teaching them to
carry two profiles. In `setBoardMode()` (`layout.js:648`), between the capture and
`completeLayout()`: if the board is showing ghosts, drop them and call
`ensureGhostCards()` again after the switch, so they are born into the new layout
by the fork that already exists. This needs a state-level helper — `layout.js`
may not import `state.js` (`tests/layers.test.js`), so the re-seed belongs in
whatever calls `setBoardMode`, or `setBoardMode` grows a callback. **Check the
layer direction before writing this line**; getting it wrong is the one way this
fix can break an invariant the tests hold.

**Check.** A board built on Mobile, switched to Desktop, is a rectangular block in
Feed order; switched back, the column is exactly as it was. An empty board
switched either way shows four hint cards sized for the layout they are on. A
board with fences is unaffected on the Mobile side (the `fenced` repack at
`layout.js:487` is untouched). `tests/layout.test.js` and
`tests/state-history.test.js` are the two that will notice.

### 2.2 The sidebar's Board tab (#7)

**What is there now** (`ui/settings-schema.js:141`–`:236`): four sections, eight
buttons over five rows in *one* of them.

```
View       [ Feed ] [ Playlist ]
Board      (name input)
           [ New ] [ Open ] [ Boards ]
           [ Save ] [ Export ]
           [ Share ]
           [ Save image ] [ Save PDF ]
Content    [ Add files ] [ Write a note ]
Arrange    Layout ▾ · [ Rearrange everything ] · hint
             ⌄ Advanced: Spacing, Snap to grid
```

The clutter is not the number of controls, it is that *Board* holds three
unrelated verbs at one level of emphasis: switch board, persist this board, and
emit a derived artefact. Nothing on the tab says which of the eight buttons is the
one you press most (Save) or which three are rarely pressed at all.

**Restructure.** Same controls, three sections, one clear primary in each — and
using only the affordances the panel already has (`h2`, one fold per section,
`className: 'primary' | 'danger'`, `when`):

```
Board      (name input)
           [ Save ]  ← primary, alone on its row
           [ New ] [ Open ] [ Boards ]
             ⌄ Share and export
               [ Export ] [ Share ]
               [ Save image ] [ Save PDF ]

Add        [ Add files ] [ Write a note ]

Arrange    View:  [ Canvas ] [ Feed ] [ Playlist ]
           Layout ▾
           [ Rearrange everything ]
           hint
             ⌄ Advanced: Spacing, Snap to grid
```

Four decisions in that, each of which can be argued with:

1. **Save gets its own row and keeps `primary`.** It is the only button on the tab
   with a deadline attached to it, and it currently sits second in a row of two.
2. **The four derived/outbound actions go behind one fold**, because a section may
   have exactly one (`buildSection()`, `ui/panel.js:153`). Export, Share, Save
   image and Save PDF are all "produce a file that is not this board", they are
   the four least-pressed buttons on the tab, and folding them takes the section
   from five rows to two. Share keeps its `when` guard.
3. **Content is renamed Add and stays a section**, rather than being merged into
   Board. It is a different verb and it is two buttons; a heading is cheaper than
   a reader working out why "Add files" sits under a heading that says Board.
4. **View joins Arrange.** They were separated on the argument that Feed/Playlist
   is navigation and belongs at the top (see the comment at `:135`), and that
   argument stands for *reaching* it — but the tab now opens with a naked pair of
   buttons above the board's own name, which reads as a toolbar that wandered in.
   Under Arrange it sits beside the other question about how the board is shown,
   and it gains a third segment naming the state it is currently in: **Canvas**.
   Today there is no button that says "you are on the canvas", only two that
   toggle you off it, which is why the pressed state has to be computed as
   `ctx.mobile && currentLens() === 'feed'`. Three segments, exactly one pressed,
   is the honest shape — and it is the same segmented-pair idiom the zoom cluster
   and the history pair already use.

Decision 4 is the one to put to the maintainer if any of this is contentious: it
undoes a move that was made deliberately and is recorded in a comment.

**Cost.** Schema-only for 1–3. Decision 4 needs a `canvas` command (or a
`board-view` command taking an argument) — `cmds.feed` and `cmds.playlist` are
toggles today, and three mutually exclusive segments want three idempotent
setters. That is one entry in `cmds` and one in the schema, which is the
sanctioned shape (`CLAUDE.md`). `tests/panel.test.js` / `tests/commands.test.js`
will need the new ids.

### 2.3 Mobile toolbar: Files, Note, More (#10)

**Now.** `#toolbar-tools` holds seven buttons; three are `data-desktop` and drop
out on the phone (`mobile.css:1035`), leaving Files, Note, Colour, Link, Stickers
— five segments across a 390px screen, which is why `mobile.css:1023` already has
to hide four of the five *words* below 360px.

**Fix.** A sixth button in `index.html`, and an attribute on the three that move:

```html
<button type="button" data-cmd="more-tools" data-mobile aria-haspopup="menu"
        aria-expanded="false"> … <span>More</span></button>
```

- `data-mobile` hides it above the phone tier, the mirror of the existing
  `data-desktop` rule (`mobile.css:1035`) — add
  `#toolbar [data-mobile] { display: none; }` to `chrome.css` and the inverse
  inside the mobile block.
- mark Colour, Link and Stickers `data-more`, and hide those in the mobile block
  only. They stay on the desktop bar untouched.
- `cmds.moreTools` opens `openAnchored(btn.getBoundingClientRect(), entries, …)`
  from `ui/menu.js:130`, with three entries pressing `addSwatch`, `addLink` and
  `stickers`. This is the sanctioned route for a non-cursor menu and reuses the
  one menu renderer (`CLAUDE.md`); it is *not* a `FLYOUTS` entry, because those
  are hover-only (`ui/flyout.js:117`) and this is a tap.

One wrinkle worth deciding rather than discovering: the bar's click handler calls
`setOpen(false)` after every `data-cmd` press (`ui/toolbar.js:63`), so pressing
More would shut the tier the button lives in. The anchored menu captures its rect
before that happens so it stays put, but the effect is a menu hanging in space.
Exempt `more-tools` from that close.

With three words on three segments the sub-360px word-hiding rule at
`mobile.css:1023` can probably come out; check before deleting.

**Check.** Every one of the three moved commands still fires from the menu; the
Stickers entry still opens the window and does not leave `aria-expanded` set on
More when the window closes (`setMenuCloseHook`, `ui/flyout.js:100`, is the
existing answer to that class of bug); the desktop bar is byte-identical in
behaviour.

## Phase 3 — text on the Feed

### 3.1 Text tiles show their words (#2)

**Now.** `kindOf()` (`ui/feed.js:193`) buckets anything with no picture as
`'file'`, and `fillFile()` (`:402`) draws the filename and the literal word
`"text"`. The desktop card does better: the `text` renderer
(`canvas/renderers.js:633`) calls `readText(hash, TEXT_PREVIEW)` and puts the
result in a `<pre class="card-text">`.

**Fix.** A `'text'` kind in `kindOf()` for `item.type === 'text'`, a `fillText()`
that reuses `readText()` from `storage/assets.js:61`, and a ratio — 0.75, taller
than wide, since a page of words is a page. Reuse `.card-text` from `items.css`
if it survives being lifted out of a card's box; otherwise a `.feed-text` beside
`.feed-note`, which is the same idea already in this file.

`readText` is async and the tile is built synchronously, so fill the tile with the
name first and swap the body in when it resolves — the same shape `fillImage()`
already has with `img.loading = 'lazy'`, and the same shape the desktop renderer
uses. Cap it well below `TEXT_PREVIEW`: a tile shows perhaps forty lines, and the
lightbox is where the rest lives.

**Note.** Markdown is `classify()`d as `'text'` (`renderers.js:86`, via
`TEXT_EXT`), so `.md` gets this for free. Whether it should be *rendered* markdown
rather than shown as source is a Phase 4 question.

### 3.2 The lightbox (#3)

Nothing like this exists — the search for `lightbox` and for a modal viewer comes
back empty, and no item on either layout is currently openable. So this is one new
module and one new `<dialog>`, and it should be built once, for both layouts, and
for more than text — Phase 4 hangs off it.

**Shape.**

- A `<dialog id="viewer">` in `index.html` beside `#ask`, `#pick`, `#compose` and
  `#credits` (`index.html:899`–`:989`), opened with `showModal()` so it takes the
  top layer, the backdrop and the Escape key without inventing any of the three.
  `canvas/input.js:1696` already stands the canvas shortcuts down while a modal
  dialog is up.
- A `ui/viewer.js` exporting `initViewer()` and `openViewer(id)` — no `document`
  at import time (`tests/imports.test.js`).
- Content by item type, one function each, dispatched from a table the way
  `RENDERERS` is in `canvas/renderers.js`. Phase 3 ships exactly one entry: text,
  read whole with `readText(hash, <no cap>)` into a scrolling `<pre>`.
- A header with the file's name and its size, and a close button. Scroll lives on
  the body, not the dialog, so the header stays put on a long file.
- Opened from a tap on a Feed tile (`ui/feed.js`), and — since it costs nothing
  extra — from a double-click on a card on Desktop, in the `dblclick` handler at
  `canvas/input.js:1655`, which already has the `note` and `title` cases and is
  the natural home for "open this". Do not take over single-click on the Feed for
  types that already do something: link tiles open their URL (`:369`), audio
  hands off to the Playlist, video plays.

**Service worker.** `web/sw.js`'s `SHELL` lists every module by hand (`sw.js:99`
onward), so `./assets/js/ui/viewer.js` must be added to it, and the `VERSION` line
must *not* be hand-edited — `save.bat` stamps it. This is a service-worker cache
change and is called out here so it is called out in the commit too.

### 3.3 The Feed has no context menu (#15)

**Cause, confirmed.** There is exactly one `contextmenu` listener in the app
(`canvas/input.js:1951`) and it is bound to `vp.el` — `#viewport`. The Feed is
`#mobile-feed`, a fixed scroller at `z-index: 2` that covers the viewport
entirely (`mobile.css:36`), so a right-click on a tile never reaches that
listener and the browser's own menu opens instead. The same for touch: the
long-press pipeline (`longPressMenu`, `cancelPress()`) is in the pointer
pipeline on `#viewport`, and the Feed's tiles are not in it.

**Why this is not a two-line fix**, and worth saying before it is attempted:

- **The Feed has no selection.** `openMenuAt()` (`canvas/input.js:1972`) selects
  the item under the cursor and hands `selection.size` to the menu; the Feed has
  no selection model at all and no visual for one. So a Feed menu acts on the one
  tile it was opened on, and `selectionSize` is always 1.
- **Half of `itemEntries()` is spatial and meaningless here.** Bring to front,
  Send to back, Align & distribute, Rearrange fence, Unstick — all of them are
  about Desktop geometry, and the Feed throws every computed position away.
  `menu.js` has no layout gate today: `grep` for `mobile` or `layoutMode` in it
  returns nothing, so every gate is a `cmds.can*()` predicate and none of them
  knows which layout is live.
- **The world point exists already, and this is the good news.**
  `feedPointToWorld()` (`ui/feed.js:465`) maps a tap on a tile to a world point
  *through the item* rather than through a pan and zoom, because there is no
  transform between the two surfaces. It was written for the sticker drop and it
  is exactly what the menu's `at` argument needs.

**Fix.**

1. A `contextmenu` listener on `#mobile-feed` in `ui/feed.js`, plus a hold timer
   for touch. Do not reach for `canvas/input.js` for the hold — that file is one
   pipeline with exactly one active gesture and must not be split (`CLAUDE.md`).
   The Feed's hold is a few lines beside the sticker drag's own slop check, which

## Phase 4 — thumbnails and documents

### 4.1 What already works

Worth stating, because the report reads as though nothing does:

| type | picture today | where |
| --- | --- | --- |
| image | full-size + 100px thumb | `import/drop.js:627` |
| HEIC / RAW | embedded JPEG preview + thumb | `import/preview.js`, `drop.js:575` |
| PDF | first page rastered via pdf.js, becomes an image card | `import/pdf.js`, `drop.js:544` |
| video | poster frame (browser decoder, ffmpeg fallback) | `drop.js:492` |
| audio | embedded cover art | `import/artwork.js`, `drop.js:634` |
| text, model, generic | nothing | — |

So "all pdfs, videos" is nearly done and the gaps are narrower than they look:

- **video has a poster but no thumb.** `drop.js:627` cuts a thumbnail for
  `type === 'image'` only, so a video card draws its full poster at every zoom.
  One line: cut the thumb from the poster blob when there is one.
- **text and model have nothing.** A model could be rastered by the existing
  renderer (`canvas/model.js`) offscreen; a text file could be drawn as a page of
  its own first lines. Both are real work and neither was asked for by name.
- **docx and the rest of the office formats have nothing**, and this is the actual
  ask.

### 4.2 Office and ODF documents without a dependency

`.docx`, `.xlsx`, `.pptx`, `.odt`, `.ods`, `.odp` are all ZIP containers, and this
repository already has a hand-written, bounds-checking ZIP reader in
`storage/zip.js` — written for `.mbrd` archives, and the same discipline
`import/preview.js` and `import/artwork.js` apply to files the app did not write.

Two entries are worth reading out of them:

- ODF (`.odt`/`.ods`/`.odp`) is **required by its own specification** to carry
  `Thumbnails/thumbnail.png`. That is a guaranteed hit.
- OOXML (`.docx`/`.xlsx`/`.pptx`) *may* carry `docProps/thumbnail.jpeg` — written
  when the authoring app was asked to save one, so it is a frequent but not
  certain hit. A `.docx` without one can still fall back to the largest image in
  `word/media/`, which is a picture *from* the document rather than *of* it — an
  honest fallback or a misleading one depending on the document, and a decision
  rather than an implementation detail.

This is the same shape as `import/preview.js` exactly: walk a container written by
something else, find one blob, trust none of its numbers, identify it by its own
first bytes, return `null` on anything malformed. It costs one new module
(`import/document.js`), one branch in `prepareFile()` beside the PDF branch, and
no network and no dependency. It is the recommended route for thumbnails.

Rendering a `.docx` *for the lightbox* is a different and much larger problem, and
that is where the open question is.

### 4.3 Optimize regenerates everything (#13)

`runOptimize()` already has two backfill passes: `backfillPosters()`
(`optimize.js:281`) for videos with no cover, and `backfillThumbs()` (`:332`) for
images whose thumbnail is missing or whose bytes were just re-encoded. Both are
deliberately conditional.

The ask is unconditional. The clean version is not "delete the filters" but
"factor the rule": one `pictureFor(item)` used by both `prepareFile()` and the
optimiser, so *every file gets a thumbnail* is one sentence in one place rather
than a rule written twice with different conditions. Then Optimize's pass drops
its `!it.meta?.thumb` guards and re-cuts everything it can.

Two things to weigh and say out loud in the dialog, since Optimize already tells
the truth before it acts (`planOptimize()`, `describeSaving()`):

- **cost.** Re-cutting every thumbnail on a 400-item board is 400 decodes. It is
  already an explicitly-asked-for, progress-reporting operation, so this is
  acceptable — but the count belongs in the plan the dialog shows.
- **the network.** If Optimize starts rendering PDF first pages, it fetches pdf.js
  from a CDN (`import/pdf.js`, ~4MB, `PDF_MB`). Optimize is currently a wholly
  offline operation. Warn, or leave PDFs to import; do not fetch silently.

Neither backfill is undoable and neither needs to be — the reasoning at
`optimize.js:325` covers the extension unchanged.

### 4.4 What the analyser actually does — read 2026-08-12

`C:\kosta\analyser` has no working tree checked out; it was read through
`git show origin/main:<path>`. Findings, because they change what Phase 4 costs:

**The document stack there is dependency-free.** `docx.js` (523 lines), `odf.js`
(490), `pptx.js` (318), `xlsx.js` (358), `markdown.js` (359), `textdoc.js` (232)
and the shared `paged.js` (419) import nothing but each other, a `util.js` and
their own `renderers/zip.js`. That zip reader inflates with the native
`DecompressionStream('deflate-raw')` and only falls back to a vendored fflate on
Safari before 16.4 — which is the same substrate `storage/zip.js` in *this*
repository already is. So DOCX, ODT/ODS/ODP, PPTX, XLSX and Markdown can be read
in mbrd with **no new dependency at all**.

**`paged.js` is the lightbox Phase 3 is about to build.** It exports
`paginateFlow()` (lays flowing content onto A4-proportioned sheets, never
splitting a block across a page), `pagedPreviewCard()` (thumbnail grid),
`pagePreviewSkeleton()` (page-shaped placeholders while the real sheets are
built) and `openDocLightbox(pages, startIndex, label)` — a full-page reader with
prev/next. `pdf.js`, `docx.js`, `odf.js`, `legacy-office.js`, `textdoc.js` and
`comic.js` all present through it, which is exactly the "one viewer, a table of
types" shape 3.2 proposes. **Build 3.2 as a port of `paged.js`, not as a fresh
design.**

**What is dependency-free there, and relevant here:** Markdown (own CommonMark +
GFM parser, everything HTML-escaped), SVG, CSV, Jupyter `.ipynb`, EPUB, CBZ/CBT
comics, Krita `.kra` and Procreate (`paint.js` — reads the baked-in
`mergedimage.png` / `Thumbnail.png`), iWork Pages/Numbers/Keynote (`iwork.js` —
reads the QuickLook `Preview.pdf` or the largest baked thumbnail), Fusion `.f3d`,
and Illustrator `.ai` (modern `.ai` *is* a PDF, so it routes straight to the
pdf.js mbrd already loads on demand).

**What costs a new dependency there:** DjVu (DjVu.js), `.xlsb` (SheetJS), MOBI
(foliate-js), Access `.mdb` (mdb-reader), fonts (opentype.js), DWG (libredwg),
STEP/IGES (OpenCASCADE), HEIC (heic2any), RAW conversion (ImageMagick), OCR
(Tesseract), PostScript/EPS (Ghostscript, ~15MB). PSD is a split case: the header
and the embedded composite thumbnail are a hand read, and only the *full layer
composite* pulls a library in.

### 4.5 Decisions taken — 2026-08-12

Eight questions were put to the maintainer and answered. Phase 4 is unblocked.

**1. Dependencies: vendor them locally.** The largest of the three options. This
ends the "no runtime dependency" claim, which is not a side effect to discover
later — it is written into `CLAUDE.md` ("no bundler, no build step and no runtime
dependency"), the head of `docs/architecture.md`, `README.md` and the two module
headers that currently describe themselves as *bending* the rule
(`import/pdf.js`, `optimize/media.js`). All of them have to be rewritten on the
commit that vendors the first library, and the two CDN paths should come home at
the same time — pdf.js fetched from jsdelivr while a `vendor/` directory sits
beside it is the worst of both. A `web/assets/vendor/` with a licence file per
library, the way the analyser has it, and `THIRD-PARTY.md` extended to match.

Consequences worth naming before the first `import`: `sw.js`'s `SHELL` grows a
line per vendored file and the offline install stops being small; the repo stops
being readable end to end; and `tests/imports.test.js`'s "loads without a
browser" guarantee has to survive whatever the libraries do at module scope
(lazy loaders with no top-level side effects, which is the analyser's own rule).

**2. Viewer types: Office + ODF, text/Markdown/CSV/SVG, EPUB + CBZ — and photos
and video.** The last two were added to the list and change the viewer's shape
for the better: it is not a *document* lightbox, it is **the** lightbox, and an
image or a clip opened full-screen is the most ordinary thing to want from a
moodboard. Jupyter notebooks were not selected and are out.

That makes 3.2 the load-bearing piece of the whole list. Build it as a port of
the analyser's `paged.js` (`paginateFlow`, `pagedPreviewCard`,
`pagePreviewSkeleton`, `openDocLightbox`) with a dispatch table, and ship the
image and video entries *first* — they need no parser at all, they are the two
types every board is full of, and they prove the surface before a single document
format is ported onto it.

**3. Baked-in previews: all of them.** Krita `.kra`, Procreate, iWork, Fusion
`.f3d` and PSD. One `import/document.js` in the idiom of `import/preview.js`,
over `storage/zip.js` for the container formats and a bounded header walk for
PSD's image-resource block.

**4. Illustrator: yes.** `.ai` routes to the existing pdf.js path.

**5. A `.docx` with no `docProps/thumbnail.jpeg`: render page one.** So the
thumbnail path and the viewer path are the same code — `paginateFlow()` produces
the sheets either way, and the thumbnail is sheet one rastered. That is a real
cost at import (unzip, parse, lay out, raster) and it must not run on the main
thread for a folder of documents; batch it the way the existing import passes are
batched, and let it fail to a named card like every other preview here.

**6. Optimize: only what is missing or stale, extended to every type.** This
narrows the original report (#13, "regenerate all thumbnails") and the narrower
version is the better one: the two existing backfills already re-cut anything
whose bytes were replaced, so "stale" is already handled, and the exhaustive pass
was only ever going to burn four hundred decodes to re-make four hundred
identical files. What changes is *coverage*, not aggression — `backfillThumbs()`
stops being image-only and picks up video posters, documents and every baked-in
preview, through the shared `pictureFor()` in 4.3.

**7. Markdown: rendered, on the card and in the lightbox.** The analyser's
self-contained CommonMark + GFM parser (`markdown.js`, 359 lines, no dependency),
with its escaping rule kept exactly as written — all text HTML-escaped, raw inline
HTML rendered as literal text, never executed. That rule is not a detail: mbrd
opens files it did not write, and a card that executes markup out of one is an
XSS in a moodboard.

**8. Sidebar: merge View into Arrange** as `Canvas | Feed | Playlist`. Decision 4
of 2.2 stands; the comment at `ui/settings-schema.js:135` that argues for the old
placement gets rewritten rather than left contradicting the code.
