# Fix list, 2026-09-14

The maintainer sent a list of 35 general items, 7 tour items and 3 late
additions (the mbrd-release README, the unsaved `*` in the title bar, and
archives dropped as folders). Every question about them is answered, and the
answers are written into the items below. The goal: every item fixed, one
commit per batch, nothing pushed without asking. Items are ticked as their
batch is committed. Numbers (G1, T3) are the maintainer's.

## How each batch runs

1. Read the head of every file before changing it. Keep the module-header and
   WHY-comment conventions.
2. `npm test`, `npm run lint`, `npm run typecheck`, `npm run build`; for
   `desktop/` changes also `cd desktop && npm run typecheck`.
3. Tick the items here, then one `git commit` with the rebuilt
   `web/assets/app.js`. No version stamp, no push. `save.bat` is the
   maintainer's, when a version is wanted.
4. Call out `.mbrd` schema and service-worker (`SHELL`) changes in the commit
   and the report.
5. For UI changes that no test reaches, launch the app (`desktop.bat` or
   `python tools/serve.py`) and look before the commit.

      very fast while menus and sheets open, while the whimsy slider moves, and
      in general use.
      - Likely cause: a flood of bar-colour updates. `installBars()` in
        `mobile/bridge/lifecycle.ts` watches `style` and `class` on `<html>`
        and `<body>`, so every slider step and every menu reports again (and
        again 400 ms later). The whimsy slider moves the paper colour through
        many values, so each step reaches `MbrdShell.bars`. Each call runs
        `setBarColor()` in `MainActivity.java`: a new window background
        drawable, and both `setAppearanceLight*Bars` calls, which also flip

        changes, since `onResume` and every `onConfigurationChanged` call it.
      - No device here: the maintainer confirms on the phone before and after

## G. .mbrd and archives (G16)

The format is sound, so no rewrite. The maintainer picked these fixes from the
problems `research/docs/mbrd-format.md` lists, and added archives.

- [x] Keep unknown `board.json` keys. The loader keeps keys it does not know
      in a side bag, and the serializer writes them back (`storage/mbrd.ts`,
      `board-schema.ts`). This protects only builds from now on: an older
      build still drops what it does not know.
- [x] Check `mimetype`. The reader checks the first ZIP entry and says "This
      is not an mbrd board" when it is wrong.
- [x] Append-only save on desktop. A save writes only new and changed entries
      and a new central directory at the end of the file (`storage/zip.ts`
      writes the tail, a new bridge call in `desktop/files.ts` and
      `desktop/preload.ts` appends it). The file stays one `.mbrd`. Save As,
      Optimize, and waste over half the file compact it. `platform/electron.ts`
      and `mobile/bridge/mbrd-bridge.ts` stay in step
      (`tests/mobile-bridge.test.js`). Tests feed it broken tails. The web has
      no file to append to and keeps the whole write.
- [x] Archives. **.mbrd schema addition** (two new card kinds). Built with
      one change: gzip goes through the browser's DecompressionStream, which
      the ZIP reader already needs, rather than through pako.
      - A dropped archive arrives as its own named card: the archive's name,
        and an Unzip button in the middle with an arrow pointing up. A
        `classify()` branch and a `RENDERERS` entry (`canvas/renderers.ts`).
        The archive file is the card's asset.
      - Unzip: the card goes away (undo brings it back), and what was inside
        lands in a spiral around where it was, from the centre out in the
        archive's own order.
      - A folder inside the archive lands the same way: a named folder card
        with an Open button, which spirals its own contents out and goes
        away. It points into the archive asset by path, so the archive stays
        in the file until nothing points into it.
      - An archive inside the archive lands as another archive card.
      - A folder dragged in from Explorer or Finder spreads its top-level
        files over the board as now, but each subfolder arrives as a named
        folder card with an Open button. Its files are stored with the board
        as assets, and the card lists them by name and hash.
      - On the Feed, Unzip and Open put the files into the column in the
        card's place. The canvas gets the spiral.
      - Readers: ZIP and TAR through the bounds-checked readers, gzip through
        pako, 7z and RAR through vendored libarchive.js (MIT, WebAssembly,
        about 1.2 MB, loaded only on the first unzip). Size ceilings through
        `consent.ts` (`CeilingId`, `oversize`, `lift`). libarchive.js gets a
        credit and a THIRD-PARTY.md entry, and the CSP (`wasm-unsafe-eval`,
        the worker) is checked in `tests/csp.test.js`.
      - `itemHashes()` / `timelineHashes()` and `boardAssetHashes()` in
        `storage/mbrd.ts` learn the archive asset (CLAUDE.md: a new class of
        asset reference).
