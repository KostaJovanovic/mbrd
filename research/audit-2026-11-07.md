# Repo audit, 7 November 2026

**Status: done.** All five were carried out the same day.

Audit of the whole repository at v0.797, done in the main session with no
subagents. One change from the plan below: fix 1 answers from the cache only
for the three shell pages (`/`, `/patch`, `/privacy`). Every other path still
goes to the network first, because `oauth.html` is the Google sign-in popup,
and answering it with the app would boot a board inside the popup.

**What this repo does:** mbrd is a moodboard app. You drop pictures, clips,
notes, documents and 3D models on an endless board, and it saves the board as a
`.mbrd` file (a ZIP). The same `web/` code runs as a static website (boards
kept in the browser's IndexedDB), as a desktop app (Electron, one file per
board in `Documents/mbrd`) and as an Android app (Capacitor).

**Load assumed:** one person per install. On the web, a few tabs of one
browser at once. The site is static, so many visitors but no shared server
state. Every deploy reaches every returning visitor through the service worker.

**Checked:** `npm test` passes (3243 tests, 1 skipped). Read in full: the
desktop trust rule and file I/O (`desktop/files.ts`, `boards.ts`,
`board-names.mts`, `trust.mts`, `atomic.mts`, `store.ts`, `protocol.ts`, the
IPC list and window guards in `main.ts`), the Android file plugins
(`MbrdFiles`, `MbrdStore`, `MbrdBytes`, `MbrdWebViewClient`) and the byte
channel's page half, the ZIP reader and writer, the autosave and its one-tab
lock, the board-file save and append path in `storage.ts`, the cloud sync,
the OAuth popup, the service worker, and every `innerHTML` in the app. Most
of this is careful and well tested. Path checks, ZIP bounds and bomb caps,
atomic writes, the one-writer tab lock and the updater's digest check all
hold up.

## Must fix

### 1. After a deploy, the first page load runs new HTML with old code (`web/sw.js:157-182`)

- **What this is:** the service worker answers page loads from the network
  first, but scripts and stylesheets from its own cache first, matched with
  `ignoreSearch`.
- **Problem:** right after a deploy, the old worker still controls the page.
  The page load fetches the *new* `index.html` from the network, and then
  `assets/app.js` and every old stylesheet come from the *old* cache. A
  stylesheet that is new in that HTML is fetched fresh, so the CSS is mixed
  too. `index.html` changed in 15 of the last 50 commits, and the app finds
  its furniture by id (`tests/element-ids.test.js` exists for that reason). If
  an id was renamed, the old bundle throws at boot, so `web-update.ts` (which is
  inside that bundle) never offers the reload either.
- **Fix:** in the `navigate` branch, answer from this version's cache first
  and go to the network only on a miss:
  `const cache = await caches.open(VERSION); return (await cache.match(page, { ignoreSearch: true })) || fetch(req);`.
  HTML and code then always come from one version, and `web-update.ts` already
  moves the page to the next one. Add one case to `tests/sw.test.js`: an online
  navigation with a cached shell answers from the cache. Call out the
  service-worker change in the commit.
- **If we skip it:** after some deploys, a returning visitor gets a broken or
  half-styled page once, and has to reload by hand.

## Should fix

### 2. A board pulled from Drive trusts the file names as content hashes (`web/assets/js/storage/cloud/sync.ts:330-341`)

- **What this is:** opening a synced board downloads each picture from the
  Drive folder and files it under the hash its file name claims.
- **Problem:** nothing checks that the bytes match the hash. `unpackBoard()`
  in `mbrd.ts` does check (its comment calls that "the only enforcement of
  content addressing"), and it refuses the whole file when one asset fails.
  So one wrong file in the Drive folder (replaced by hand in Drive, or a bug
  in an old push) is written into the next `.mbrd` save under a hash it does
  not match, and that `.mbrd` then refuses to open: "does not contain the data
  its name claims". On the desktop and on Android that file is the board's only
  copy. The rolling backups in `.autosave/` are what would save it.
- **Fix:** before `putAsset`, check
  `await sha256(await blob.arrayBuffer()) === hash`, and on a mismatch
  `continue`, which treats the picture as missing, as a hole already is. About
  2 lines. Add a test in `tests/sync.test.js` with a fake store whose bytes do
  not match their name.
- **If we skip it:** one bad cloud file can make a saved board unopenable.

### 3. `sameRuns` is written twice in the editor (`web/assets/js/ui/editor/view.ts:234`, `web/assets/js/ui/editor/vomit.ts:35`)

- **What this is:** both files compare two runs of styled text the same way.
  `view.ts` uses it to decide whether a block re-renders, and `vomit.ts` uses it
  to decide whether text behind Vomit Mode's lock was changed.
- **Problem:** the two copies are identical today and must stay that way. Add
  a new field to `Run` (as `raw` was added) and change only one copy, and the
  lock sees a change where the view sees none, or the other way round: an edit
  is refused for no visible reason, or locked text slips through.
- **Fix:** export one `sameRuns` from `ui/editor/model.ts`, next to the
  `sameMarks` both copies already import from there, and delete the two
  copies.
- **If we skip it:** the editor and the lock can quietly disagree after a
  future change to `Run`.

## Nice to have

### 4. The same one-line `str()` in five modules, and `urlOf()` in three

- `const str = (v: unknown) => (typeof v === 'string' ? v : '')` is in
  `import/unpack.ts:20`, `storage/json-canvas.ts:128`, `ui/feed.ts:56`,
  `ui/playlist.ts:48` and `ui/viewer.ts:45`. `session.ts:85` has a variant
  that returns `undefined`, so leave that one alone.
- `urlOf()` is the same line in `ui/feed.ts:58`, `ui/playlist.ts:49` and
  `ui/viewer.ts:47`.
- **Fix:** put `str` in `util.ts` beside `isRecord`, and `urlOf` beside
  `assetURL` in `storage/assets.ts`, then import them. About 6 lines fewer.
  Check `tests/layers.test.js` for `ui/` reaching `storage/assets.ts`. It
  already does, through `assetURL`.

### 5. `mergeBoardFile` only passes its call on (`web/assets/js/storage/storage.ts:829`)

- `export const mergeBoardFile = (file: File) => mergeFile(file);` adds a name
  and nothing else. Export `mergeFile` as `mergeBoardFile` and change the one
  internal call at line 902. One line fewer.
